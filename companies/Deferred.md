# Deferred: what the companies kit does not do yet

5 November 2026, first slice of B58. "Revisit when" is the trigger; nothing here is claimed anywhere as built. Items marked **owner** need a decision or a yes from the owner.

## Named in the brief

- **OAuth and other auth.** Guard reads the API's key from one file and adds it as one header. An API that needs a refreshed OAuth token, mutual TLS or a signed request (an HMAC over the body) is not handled. The bundle's Google token refresher (a sidecar that writes a fresh token to a file and asks Guard to reload it, `POST /admin/reload`) is the pattern for refreshed tokens, but it is written for Google. The draft also does not read OpenAPI `securitySchemes`, so the header name is `Authorization` unless the engineer edits `guard.toml`. Revisit when: the first company's API uses OAuth client credentials (the likeliest case). Evidence of done: a refresher beside Guard for that API, and an end-to-end test where the token expires.
- **gRPC, streaming, WebSockets, GraphQL.** Guard matches HTTP method and path and reads JSON, query and path arguments. gRPC and WebSockets are other protocols. Server-sent events and long streamed replies have not been tried against Guard's 15-second upstream timeout. GraphQL puts every operation behind one `POST`, so a route-based spec cannot tell a read from a payment. Revisit when: a company's agent talks to one of these. Possible answers differ by case (a REST gateway in front, a route per persisted query), none chosen.
- **AP2, ACP and other payment rails (B41).** Checking a mandate against the limits, and a record of the work around the payment. Plan: built only on a company's demand. Revisit when: a company names the rail.
- **Several tenants behind one Guard (B19, phase 2).** Today one Guard fronts one API for one tenant (an environment or a business), the way Guard is built. A company with many customer environments runs one Guard each, or waits for routing by client. Revisit when: a company needs more than a handful of Guards to operate by hand.
- **The self-serve crash test (B52).** The faults (lost replies, duplicate and late events, an expired key) tried against the company's own agent through Guard, with "Held N of M" as the output. This kit has the pattern only: `test/end-to-end.test.ts` and `examples/refunds-api/fake-api.ts` show a lost reply and a repeat against a made-up API. Nothing yet runs them against a company's agent. Revisit when: the first company asks to see its agent tried. Evidence of done: a command that starts the fault-injecting stand-in from the company's OpenAPI file, runs the agent through Guard, and prints held and refused counts.

## Other gaps in this slice

- **Certificates per agent version.** The plan lists them for the company door. The kit gives the evidence pack, the anchor and the open verifier, plus the spec and the bundle's digest. Geometer's `geo assessment` certificate is made from a finished check of an agent project, and nothing connects it to Guard's decisions on a company's API. Revisit when: a company's security review asks for a certificate. Needs a decision on what a certificate would say for an agent Geometer did not check.
- **YAML input.** The reader takes JSON only. Most real OpenAPI files are YAML. A tiny parser would have to handle anchors, multi-line strings and flow sequences correctly, and a mistake there would feed wrong numbers to a limits spec. Revisit when: a company only has YAML and cannot convert it. Lower risk: a documented conversion step, or a vetted parser as an optional, separate tool.
- **Reading the API back.** The record says `sent` when the API answered. It does not ask the API whether the refund exists. Guard supports a `receipt` lookup and `retry_safe` with `key_lifetime_seconds` for an API that keeps idempotency keys; this kit writes neither, because both are claims about the company's API. Revisit when: a company's API documents a lookup. Evidence of done: an accept option that writes a `receipt`, and a test where a lost reply is settled by the lookup.
- **An approvals inbox for companies.** Approving is done with Guard's admin API (an approver credential, `GET /admin/reviews`, `approve` or `deny`). The WhatsApp relay in the pathway is for a shop's owner. A Slack, Teams or email front, and a plain list of who may approve what, are not built. Guard can take signed answers from such a front (`POST /admin/notify`); nothing here signs them.
- **An incremental export.** `export-record.ts` reads Guard's 500 most recent decisions each time and says so. B51's record keeps the newest time read from each Guard and writes a gap entry when decisions fell out of the list between runs. The company kit should do the same. Revisit when: a company's Guard decides more than 500 calls between exports. Until then the evidence pack is the complete record.
- **The backup folder in Kubernetes.** `--backup-dir` needs a folder both Guard and the reader can reach (`--backup-read-dir` names the reader's view). In Compose that is a bind mount. In Kubernetes the Guard image has no `tar`, so `kubectl cp` does not work; a second pod on the same claim, or a job, would. Not written.
- **`scope` and `fail_policy`.** The accept step accepts a `scope` on a limit (a counter per customer, for example) and validates it against the call's fields, but no test runs it against a running Guard. `fail_policy` (hold instead of refusing when Guard cannot decide) is not offered; Guard fails closed by default, which is the right default.
- **Fields a rule cannot read.** Amounts inside arrays, and nested non-numeric fields, cannot be bounded by a Guard rule; the draft says nothing about them. A body sent as a form is noted on the route, not read. A string-typed amount gets no suggestion, but Guard reads a numeric string as a number, so a bound would bite; the draft could offer one with a note.
- **Swagger 2.0 and files with outside `$ref`s.** Refused or noted. A bundling step first is the answer.
- **The "Talk to us" flow (`/for/teams`)** and the contract itself (economics section 7: platform fee, protected agents, bands of guarded actions, support) are the website's and the owner's, not this kit's.

## Needs the owner or a licence

- **The Guard container image is not published** (plan decision 7: Guard stays closed for now). A company gets the `geo-guard` program or image with a licence. Until an image is published, no recipe here has been started with it. Revisit when: the first licensed image goes to a company; run both recipes on that company's staging first.
- **The terms.** The monorepo has no TERMS file. The README says "licensed separately" and the alpha terms in the releases repository are a draft. A company contract needs real terms. **owner**
- **Hosting.** A private deployment that Geometer runs for a company is a contract line (economics section 7) with no code behind it, and needs the owner's yes on any spend. **owner**
