# Deferred: what the deploy bundle does not do yet

Newest first within each part. "Revisit when" is the trigger; nothing here is claimed anywhere as built.

## Needs a decision or an approval from the owner

- **The Guard image is not in a registry.** A builder cannot `docker pull` it; the README says so and tells them to `docker load` a file. Publishing a signed, versioned image needs the owner's yes (plan decision 7, "Guard stays closed for now"). The deploy refuses with a plain message when the image is missing. Revisit when: the owner approves a registry. Also needs both architectures (the local image is arm64; an Intel server needs the x86_64 build that `tools/release/build-linux.sh --arch x86_64` makes).
- **Geometer's own bucket for the partners' shops, and the server that hosts them.** The bundle takes any S3-compatible bucket; creating Geometer's own, and provisioning the partner server, are spending the owner has not approved.
- **Docker Engine's own account on a builder's server** (a rootless Docker, or a dedicated user): the README uses the `docker` group, which is root-equivalent on that machine. Revisit when: a builder with more than one person on the box asks.

## Bring your own agent (B51, 5 Nov): what the first slice leaves out

The first slice puts the bundle's Guards in front of an agent's calls to Razorpay, WhatsApp and Google Calendar (`geometer agent add`). Not built:

- **The Claude Code plugin (B11), the n8n importer (B15) and the Lovable door (B18).** Each becomes a way to reach `agent add` (a skill that runs it and rewrites the agent's base URLs; an importer that finds the consequential steps and fills in the settings; a payment module for imported apps). None exists. Revisit when: B51's first slice has been used by a real builder's agent.
- **Any web service beyond the three (B58).** A limits spec from an API's OpenAPI file, Guard as a sidecar in the builder's own cloud, approvals bound to the exact action, the record exported for a company's reviewers, certificates per agent version. `agent add --upstreams` refuses a service it does not know, saying so. Revisit when: a company conversation needs one.
- **A self-serve crash test of the builder's own agent (B52).** The fault-injecting stand-ins (lost replies, duplicate and late events, silent calendar failures, an expired key, haggling in four languages) run against the agent through Guard, on each client's settings, before go-live and before every update, with the output "Held N of M". Until then an agent has **no go-live certificate**, and its monthly report lists "no go-live certificate" among what was not tested, as a template's does before its checks have run.
- **Prices and opening hours are not checked for an agent we did not write.** Guard has no rule kind for either (its rules are bounds on a number, exact lists, an owner's approval above an amount, once-only effects, caps and forbidden calls). A template's agent checks them itself. They are in the settings file, and so in the report's policy digest, and nothing enforces them. Revisit when: Guard grows a rule on a field it can read from a call (a price floor on a payment link's amount for services that are not deposits is the likeliest).
- **A rule's name in the report.** Only Guard's refund rules map to the report's rule list ("Refunds over your limit"). A refused payment link, a calendar event on another calendar, a message from another number and a payout are in the record (as `blocked`, with Guard's reason) and in the report's table by action, but not in its "what the limits stopped" counts, because that list is the template's nine rules. Revisit when: the report's rule list is open to rules it did not write.
- **WhatsApp has no read-back,** so a message is "confirmed" when the service accepted it (Guard recorded HTTP 2xx), the way a template's is, and its language is the settings' first language (or the owner's, for the relay's notices), not read from the text.
- **The calendar is read one page (250 events) and matched by title and start time.** A booking whose event is not on the first page, or whose title the agent changed, stays "unconfirmed" until a later read shows it. A calendar with more than 250 events in range needs paging, and a better match (an extended property the agent sets).
- **The owner's words.** The approval request uses the templates' wording: "refund ₹200 for +91... (payment pay_X, 5 Nov 6:00 pm)", where the customer is the number on Razorpay's record of the payment and the time is when they paid. The wording that follows ("...and they will be told") is true only if the builder's agent tells the customer, which Geometer cannot make it do. A wording for an agent we did not write needs new templates under the pathway's `src/language`, which is another change's ground. Revisit when: the templates are open for it.
- **The heartbeat's `errors` is 0** and its `steps` counts every call the Guards decided on, the reading agent's and the relay's among them: Guard's status gives a count of decisions, not of provider failures. (Guard's decision list does carry "the provider answered 502" in words; it is read for the record, not yet for a count.) The alert fleet sends for a down Guard says "runtime" because the agent has no runtime; it means the agent's Guards. Revisit when: fleet's text can say which.
- **Not in the panel.** An agent lives in `agents/<name>/`, beside `shops/`, so the panel's shop list, its connection checks and its go-live certificate do not see it. `status/<agent>.json` is written in the panel's shape and `geometer status` shows the agent. Revisit when: the panel is asked to show "agents we did not write".
- **No `agent remove`, no rotation of the agent's credential.** Removing an agent is stopping it (`geometer stop`) and deleting its folder and state by hand. The credential is made once and kept, as the other tokens are.
- **One credential for the agent's three Guards.** A leak reaches all three (each still refuses everything outside its limits). A credential for each Guard is a change to what `agent add` prints.
- **The record's own file is not in the nightly snapshot.** `state/records/<agent>.json` is derived (the Guards' stores are backed up, and hold every decision), but the sequence numbers a rebuilt record would get could differ from the ones certificates quote. Revisit when: a record must be restorable byte for byte.
- **Razorpay's webhooks.** The agent takes its own; Geometer's inbox has no Razorpay route for an agent.
- **Not run against Docker.** The generated compose file with an agent in it, Caddy's `handle_path` cutting the prefix, the `gate` network and the services' paths inside containers were checked as generated text and by the fake machine, not started. The Guards, the relay, the inbox, the record and the report were run for real in the end-to-end test (the real binary, the stand-ins). No real Razorpay, Google or WhatsApp account was used. Revisit when: the next Docker proof run (`test/proof/run.ts` has no agent in it yet).

## The licence lease (B13): where it slots in. Not built (decided 4 Nov)

Day 0 is the invoice due date. Days 0 to 14 are normal, 15 to 30 are warnings, wind-down starts at day 30 (Guard's `subscription_suspended`), a final stop comes no earlier than day 60, and there is then a 90-day free export. The offline lease is valid until the paid-through date plus the grace. Nothing in the bundle checks a lease; it is built so that one can be added without reshaping anything:

- **The check** is a deployer job beside the others (`runDueJobs` in `apply.ts`: relay credentials, exports, snapshot, drill). It would read a signed lease file from `state/`, compute the day, and call the same `ops stop` the panel's stop request uses for the wind-down.
- **Guard's side** is one more optional block in `TomlOptions` (`generate/guards.ts`), written into every guard.toml by the same generator and re-verified by `verify-bundle`; a changed lease is a changed file and a Guard restart, as for any config change.
- **The heartbeat's answer** is read today only for its status (`sendHeartbeat` in `services/heartbeat.ts` returns `accepted`); fleet's 200 body is where a fresh lease would come back, and the same function is where it would be picked up.
- **What the panel shows** would go in `status/<shop>.json` beside `deploy` and `limits`, which the panel's checker ignores fields it does not know.

## Contract changes the bundle needs from other parts

- **A first snapshot that never succeeds, and the order of deploys.** The heartbeat now sends `backup_age_s` and `drill` (fleet's optional backup fields, ADR-0055 addendum 2), but a field is left out when there is no snapshot or drill yet, and fleet reads "absent" as "nothing to report". So a shop whose very first nightly snapshot fails every night stays silent on this channel (it still shows in `geometer status` and the panel). Fixing it needs the bundle to say "backups are set up, none has succeeded" (for example a `null`) and fleet to alert once the shop has been reporting for longer than its 36-hour limit. Separately: **fleet must be deployed before a bundle that sends these fields**, or every heartbeat is refused with a 400 (the sender prints the refusal once). Revisit when: the first live client with backups on, and when fleet is first hosted.
- **The ops container reading `status/` was not run in Docker.** The mount is read-only and the files are 0644 in a 0755 folder, the same as the panel's, and the generator, the compose file and the heartbeat are tested; the next Docker proof run should check that `observe` shows `backups` for a shop after `backup now`. Revisit when: the next proof run.
- **The monorepo's Guard templates have no panel routes.** The generator adds `read_number` and `get_calendar` (and the panel agents); `test/drift.test.ts` names them as the additions it allows. The fixtures in `deploy/pathways/bookings/` should gain them, or stay as the generator's older shapes.
- **The panel's view of the runtime.** The panel can ask a shop's runtime for `/status` (`PANEL_RUNTIME_URL`) to say "runtime not ready" or "refunds need the builder" on the shop page. The bundle does not set it: that needs the panel to be on the runtime's door network with the runtime's bearer token, which widens what an internet-facing program can reach. The deployer's refresh instead stops moving `updatedAt` when the runtime does not answer, so the page says "Not confirmed yet" after the panel's stale time. Revisit when: the panel is shown to hide a runtime that is down.
- **The continuous copy's time.** `backups.lastCopyAt` is the last nightly snapshot; Litestream's last sync is not read (it has a metrics endpoint, not wired).
- **A read-only approver credential in Guard.** The relay's reading credential is an approver credential (it can approve, not only read). The deployer issues a fresh one every day with a seven-day life, so a stolen one is short-lived, but Guard has no role that can only list holds. Revisit when: Guard grows one (the approvals notes already list it).
- **Per-Guard panel tokens.** The panel reads one token file and presents it to every Guard (`golive.ts`), so the panel has one token, valid at every shop's Guards for the connection-check reads only (`list_links`, `read_number`, `get_calendar`, `list`). If the panel read `PANEL_GUARD_AGENT_TOKEN_FILE` with `{shop}` and `{kind}` filled (as it does for the URL), each Guard could have its own and a leak would reach one Guard. The calendar `list` read also lets that agent read the events of the shop's own calendar, which the check needs only for the access role. Revisit when: the panel's token file is templated, or Google's calendar check can use something narrower.
- **The connection checks before the first deploy.** They go through the shop's running Guards, so `check` runs them only once the shop has been deployed (`geometer check` says "not run" before). Nothing confirms, before the first deploy, that the WhatsApp number id is the shop's or that the calendar is shared and writable; the first deploy uses the ids as typed, the panel's checks then confirm them and write `pins.json`, and the next deploy pins the Guards to what the providers reported.

## Not measured

- **CPU, disk and the Docker daemon on a 2 vCPU / 4 GB machine under load** (plan B14 item 4), and **the demo salon through Guard for two weeks** (item 5). The memory numbers are Docker Desktop's cgroup memory on an Apple-silicon Mac, idle, with the heartbeat every 10 s; the cap of 25 shops per server is a guess to test on a real VPS. Revisit when: a Hetzner or DigitalOcean machine is available for a day.
- **The proof against a real Guard release for another architecture.** It ran on the arm64 image only; the x86_64 image (`tools/release/build-linux.sh --arch x86_64`) has not been put through it.
- **The proof is a script run by hand** (`bundle/test/proof/run.ts`, about 25 minutes, one hold of the heavy lock), not part of any CI. It names everything it creates `geometer-proof-*` and removes it, and it needs the Guard image, `node:26-alpine`, Caddy, Litestream, BusyBox and MinIO.

## Not built

- **Age encryption of the continuous copy.** The plan says the Litestream stream is encrypted with age before it leaves the server. Litestream 0.5 (the line that is maintained) dropped client-side encryption and refuses to start with an `age:` block; 0.3 had it. The stream is protected by TLS in transit and by whatever the bucket does at rest (server-side encryption is a bucket setting). The nightly snapshots are age-encrypted. Revisit when: Litestream restores client-side encryption, or the builder accepts pinning 0.3.x. A second option is to replicate to a folder and have the snapshot job encrypt and ship it, at the cost of the one-second loss window.
- **Restoring a snapshot in one command.** `restore` uses the continuous copy (and a moment, `--at`). A nightly snapshot is age-encrypted and the key is not on the server, so it is downloaded and opened on the machine that has the key with `node bundle/backup/restore-snapshot.ts <folder> --identity <key> --out <folder>`; putting the opened database into the shop's volume is by hand. Guard's own store restore (`geo-guard restore`, which needs the Guard stopped) is not wired into `restore` either; the snapshot has the files.
- **The weekly drill does not open a snapshot** (same reason: no key on the server). It checks the continuous copy and the record; the snapshot's age and size are not checked. Revisit when: a builder keeps the key on a second machine that can run a drill.
- **Rotating a shop's tokens.** Agent, admin, internal and relay tokens are made once and kept. Rotation (and the Google service-account key changing) means deleting the file and deploying; there is no command, and a rotation of the owner's approver secret needs the Guard restarted.
- **Several shops on one WhatsApp provider account sending webhooks to one URL.** A shared Meta app posts every number's messages to one callback. The bundle gives each shop its own path (`/c/<shop>/...`), checks the signature and drops a body for another number, but does not route one shared callback to the right shop by `phone_number_id`. Revisit when: a builder runs several shops on one app and cannot configure a callback per number.
- **A per-shop `limits.json`.** The caps that settings do not carry (messages an hour, calendar events, the model's calls a day) are server-wide defaults in `geometer.json`. Plan 4.6 has a `limits.json` per client with a history.
- **Per-shop model caps.** The model is included in Geometer's flat fee, bounded by a monthly cap per shop (plan decision 6): above it the agent falls back to its rule parser and the builder is told. Today the model Guard has one cap for the whole server, so nothing stops one shop from using all of it and nothing tells the builder. The panel's cost line does not read model use at all any more; it only says the model is included. Revisit when: the model Guard can count per shop (Guard work), then the cap and the "you were told" notice.
- **Postgres for Guard, Guard behind several replicas, and Guard on its own host.** One SQLite store per Guard, one replica.
- **Upgrading the bundle itself** (a signed release, a `geometer upgrade`). Today the builder pulls the repository and runs `deploy`; services whose compose entry changed are recreated, those whose files changed are restarted.
- **CI for the bundle's tests.** The repository's workflow does not run `node --test bundle/test/` or the pathway tests. The proof (`bundle/test/proof/run.ts`) needs Docker and about twenty minutes and is run by hand.
- **Windows.** The deployer assumes a Linux or macOS host with Docker Engine or Docker Desktop. The plan's Windows route is WSL2, not tested.
- **Cheaper forwarders.** Each Guard has a 1 MB `busybox nc` forwarder and each shop a door. That keeps the admin port off the runtime's network without TLS on the Guard's agent port. If Guard ever serves its admin port with its own TLS cleanly, the forwarders can go.
