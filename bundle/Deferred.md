# Deferred: what the deploy bundle does not do yet

Newest first within each part. "Revisit when" is the trigger; nothing here is claimed anywhere as built.

## Needs a decision or an approval from the owner

- **How long a shop waits for a Guard that is down, and for which outages (B14, 10 Nov).** Built: a task waits for its Guard for at most 15 minutes from when the message arrived. While it waits, the shop's later messages wait behind it: order is shop-wide (`modules/Explanation.md` says why). A provider that is away (`provider_unreachable`) does not wait. To decide:
  - whether 15 minutes is right, given that it is also the whole shop's silence at its worst;
  - whether a provider's own outage should wait too (a one-line change, and a wider promise);
  - whether per-conversation order (reserved case ids, a place in line for payment events) is worth building before shops with heavy traffic;
  - whether the customer's words when the wait ends should be a template of their own: today they are `couldnt_tell_owner` ("Sorry, I couldn't reach the owner just now. Please try again in a few minutes."), though nobody tried the owner on WhatsApp.
- **A package's `settings.json` holds the shop's own list of people in plain text** (the owner's and approvers' numbers; a Fees centre's students with their parents' numbers), and so does `history/settings-history.jsonl`. The fingerprints (B69) cover the record and the cases, not the settings, and the README in every package says so. A version for handing around would leave those two files out or replace the numbers and names in them. Revisit when: the owner decides whether the export is only the shop's own copy, or also something to pass on.
- **An own agent's key is in no snapshot.** The snapshot goes through shops; an own agent's record is the deployer's own file (`state/records/<agent>.json`), which is not backed up either. A new key on a new server changes only how the next labels look: references already recorded keep theirs, and one that looks like a phone number may be asked about again. Revisit when: an own agent's record is backed up.
- **The weekly drill does not check the shop's fingerprint key.** The key travels inside the snapshot's encrypted manifest, and the drill runs without the owner's age key, so it cannot see it. Whether it is there is what the monthly full restore test shows (`person_key` comes out with the rest). A key lost with its server and in no snapshot is gone, and the shop's older papers and packages then match nobody; the live database still holds the numbers, so its next export is consistent under a new key. Revisit when: a shop first goes live, with a clear flag in the snapshot's seal that its manifest holds a key.
- **The Guard image is not in a registry.** A builder cannot `docker pull` it; the README says so and tells them to `docker load` a file. Publishing a signed, versioned image needs the owner's yes (plan decision 7, "Guard stays closed for now"). The deploy refuses with a plain message when the image is missing. Revisit when: the owner approves a registry. Also needs both architectures (the local image is arm64; an Intel server needs the x86_64 build that `tools/release/build-linux.sh --arch x86_64` makes).
- **Geometer's own bucket for the partners' shops, and the server that hosts them.** The bundle takes any S3-compatible bucket; creating Geometer's own, and provisioning the partner server, are spending the owner has not approved.
- **Docker Engine's own account on a builder's server** (a rootless Docker, or a dedicated user): the README uses the `docker` group, which is root-equivalent on that machine. Revisit when: a builder with more than one person on the box asks.

## The folders moved by domain (5 Nov): what an existing server must do, and what is left as it was

The repository's `pathways/` became `templates/<domain>/<name>` (`templates/commerce/bookings`, `templates/education/fees`) and the example agents moved to `examples/<domain>/<name>`. A server that already runs shops is affected in three places.

- **Run `geometer deploy` once right after pulling this layout.** The state file stores, for every running shop, the absolute folder it was deployed from (`applied.pathwayDir`, for example `<app>/pathways/bookings`), and the compose file on disk mounts that folder as `/pathway`. After the pull that folder is gone, or is left empty by untracked files. Docker makes a missing bind-mount source an empty folder, so a runtime restarted before the deploy would start on an empty `/pathway` and die with a missing module, with no clear error. `deploy`, `update` and `rollback` no longer trust the stored folder: `appliedPathwayDir` (`lib/pathways.ts`) uses it only while it still holds the version the shop was applied at, and otherwise looks the version up again from the pin. The next deploy therefore rewrites every shop's compose entry with the new folder (each runtime is recreated once, as for any deploy). Until then the old compose file stays as it was. Tests in `test/layout.test.ts` hold this (the lookup, the stale stored folder, and a compose file written while another shop is deployed).
- **Kept versions in the old layout are still found.** A server that holds a held-back version at `<server>/pathways/<name>@<version>/` (B53) keeps working: `pathwayDirFor` looks at `<server>/templates/<domain>/<name>@<version>/` first and at `<server>/pathways/<name>@<version>/` second, and the shared code is still `<server>/modules` for both (`modulesOf` in `generate/compose.ts` counts two folders up from the old shape and three from the new one). Nothing is moved for the server. The old checkout keeps its old imports, which is right: it is the code of that version. The folder to PUT a new kept version in is now `<server>/templates/<domain>/<name>@<version>/` (the domain is the one this checkout keeps the template in; the message `update` prints names it), and it must be a checkout laid out like this repository, with `<server>/modules` beside `templates/`, because its imports go three folders up. A version whose tag is from before the move belongs at the old place, with its own old modules.
- **The panel's template folder.** `PANEL_PATHWAYS_DIR=/app/pathways` is now `PANEL_TEMPLATES_DIR=/app/templates`, the folder that holds the domain folders (`templates/<domain>/<name>/template.json`). The compose file generated by this bundle sets it; a builder who set the old variable by hand must set the new one, or the setup page lists no template (an unreadable folder shows an empty list, not an error).
- **Not renamed, on purpose:** `pathway.lock` and its `bookings@0.1.0` line, the `pathway` and `pathwayVersion` fields in the heartbeat and in `ops.json`, `versions.pathway` in a shop's status file, `applied.pathway` and `applied.pathwayDir` in `state/state.json`, the `pathway-pin` rule name in a refusal, the container mount `/pathway`, and the Guard image tag `geo-guard:0.1.0-alpha.2-pathways.1`. Fleet's validator and every deployed server store them; a rename would need a migration of the state file and a change on fleet's side, and nothing a person reads is gained by it. The word the person reads is "template".

## The owner's monthly report, switched on (5 Nov: the bundle half of B54): what it leaves out

How it works is in Explanation.md, "The owner's monthly report, switched on". The template's own Deferred.md (`templates/commerce/bookings/Deferred.md`, "The monthly report on WhatsApp") still lists three rows as open for the bundle ("Serving the report pages", "The bundle writing the report block", "The panel's own report does not carry the badge"). They are done here; the template's file was not touched from this branch.

- **Caddy and Docker have not run any of this.** The Caddyfile is checked as text and its one regular expression is run against 26 near misses; the compose file passes `docker compose config -q` and its resolved form shows the sub-path mount and the dependency. Nobody has started Caddy to ask it for a report file and a folder, or started the `rd-<shop>` one-shot on a fresh volume and then the runtime on it. Revisit when: the next Docker proof run (`test/proof/run.ts`): after a runtime has written a report, `GET /r/<shop>/<hex>/<file>` is 200 and `GET /r/<shop>/<hex>/` and `/r/<shop>/` are 404, and a fresh shop's runtime can write into a folder `rd-<shop>` made.
- **An older version's code runs inside the deployer.** To ask a pinned version whether it accepts a setting, the deployer imports that version's `server/config.ts` (the way it already imports today's), so a kept checkout's module graph is loaded into the deployer process once. It is a checkout of a tag the builder put there, but it is code the deployer now executes; `update` reads a version's data layout in a child process instead, which cannot return a function. A version of another shape gets neither optional setting. Revisit when: templates other than bookings are deployed, or a builder keeps versions that are not their own tags.
- **The reports are not signed and carry no go-live certificate.** The block has no `signingKeyFile` and no `goLiveFile`, so each page says "Not signed" (it still carries the digest and the check code) and "no go-live certificate was given". A key per shop in `secrets/rt-<shop>/` and the shop's go-live certificate in its data folder are the next step; nothing shows who holds a key unless the reader already knows it, so a key alone adds little. Revisit when: the verify page exists, or the panel's go-live certificate can be handed to the shop's runtime.
- **A link works for as long as the page exists, and nothing deletes pages.** The only secret in the address is the random folder name (128 bits). There is no expiry, no way to switch one link off but deleting its folder by hand, and each month adds a small folder per shop. Revisit when: an owner asks for a link to stop working, or a server's volume fills.
- **A new domain or HTTPS port does not redeploy shops.** `pageBaseUrl` follows the server, and the shop's hash is the shop's own files and fleet's answer. Run `deploy` after changing either. Links already in owners' WhatsApp stay on the old address and stop opening.
- **A name or badge change restarts the runtime.** The runtime reads both again when `runtime.json` changes, so it needs no restart, but the deployer restarts any service whose mounted file changed. Revisit when: restarts for a badge flip bother anyone.
- **Every shop is redeployed once** on the first `apply` after this lands (the hash gained the report facts). That restarts each runtime once.
- **An unreadable `fleet/<shop>.json` takes the badge away** (and, as before, button mode), until a good answer is written. The file is written whole (`writeAtomic`), so the likely cause is a hand edit. Keeping the last badge needs the deployer to remember it between runs.
- **"your builder" is English in every language.** It is the name that goes into a Hindi, Malayalam or Kannada message when a shop has neither `report.json` nor `owner.json`; the line around it is translated. A shop made in the panel never needs it.
- **`source` follows the pin, not the money.** A shop whose Razorpay account was never checked by the panel says `test-mode` even if its key is live. The panel's own report does the same.
- **Caddy is recreated when a shop is added or removed** (its mounts change): a few seconds without the front door (the webhooks and the panel). The providers retry a webhook that gets no answer. Revisit when: a server holds many shops that come and go.
- **The pages are in no backup.** The nightly snapshot holds the runtime's database (`agent.db`) and the Guards' stores, not the rest of the data folder. If a shop's volume is lost, the record comes back and a report can be made again, but under a new random folder name, so the links already in owners' WhatsApp stay dead. Revisit when: a lost volume is real, or links must outlive one.

## Update every client at once (B53, 5 Nov): what it leaves out

`geometer update` and `geometer rollback` (README, "Update every client at once") move template clients one at a time, each hand-checked on its own settings. Not built:

- **Agents you wrote (B51) are updated by the crash test (B52), with limits.** Built in 5 Nov (`agent/update.ts`; Explanation.md, "A crash test for any agent"): the crash test at the version in service and at the version in `agent.json`, then moved or held back with the same comparison. What it does not do is in the section "A crash test for any agent (B52)" below: nothing is deployed and nothing is rolled back (Geometer does not run the agent), an agent with no `run` command or no `version` is skipped, and a run command that never uses `{version}` compares the same code with itself (the output says so in a note).
- **The check is the hand check, on stand-in services.** The counts are "Held N of M" over its situations, on the settings of the client; it is not the engine's crash test (B8) and not a test of the live providers. It is run by starting the version's own `scripts/hand-check.ts` and reading the lines it prints, so it works with any version that prints them; a version whose output no longer reads is held back, saying so, not guessed at. A structured answer (a `--json` option on the hand check) would be sturdier. Revisit when: B8 or B52 gives the check a machine-readable result.
- **A renamed situation holds every client back.** Situations are matched between the two versions by their title. One that held before and has another title now reads as "no longer checked at the new version". The summary says so, apart from "now failing".
- **A client that has not been deployed yet is skipped.** It has nothing running to move; its first deploy uses its pin as it is. Change the pin before then to start it on another version.
- **No live booking was in the middle.** A move restarts the client's runtime as any deploy does, and the runtime is built to be restarted (each event saved before it is answered, each step saved whole). What was run: the template's own tests stop a runtime between a payment link and its payment and finish the booking once after the restart, and the Docker proof restarts the runtime and its Guard with a refund held for the owner. `update` does not wait for a quiet moment and no test moved a client while a conversation was in the middle. Revisit when: a builder with busy clients asks for "only when idle", or a real client's booking is lost across a move.
- **`update` and a running `apply --watch` can deploy the same client at the same time.** `update` writes the new pin and runs the deploy; the deployer, seeing the pin differ from what is applied, may start the same deploy. That race already exists between `deploy`/`rollback` and the deployer, and was not solved here. The deploy is the same, so the outcome should be the same, but the state file is written by both. Revisit when: they are seen to collide (a lock file in `state/` is the fix).
- **The rollout is one client at a time and stops at the first refused deploy.** No waves, no soak time between clients ("wait ten minutes and look at the heartbeat before the next"), no percentage canary. Revisit when: a builder has enough clients that one at a time is too slow or too brave.
- **Rolling back across a change in the runtime's saved-data layout is refused, not repaired.** The layout is asked by importing the version's `server/store.ts` and reading `SCHEMA_VERSION`; a version that keeps it somewhere else cannot be asked, and a rollback then goes ahead and its runtime may refuse to start (`geometer deploy` says so; `geometer restore` is the way out). There is no way to run a layout change backwards.
- **Versions are put beside the server by hand** (`<server>/templates/commerce/bookings@0.2.0/` with `<server>/modules/` beside `templates/`, a checkout of the tag). Nothing fetches one, and nothing removes old ones.
- **A pin with modules.** The plan's `pathway.lock` can list modules, each pinned (section 4.6). The runtime refuses a lock with more than one line, so `update` moves the one template line only. Revisit when: modules exist.
- **After a refused deploy the client's status file says "failed"** with the refusal, as any refused deploy does, though the client is still running the version it ran. The update's own record (`state.update`) and the summary say it was put back. Revisit when: the panel is asked to tell "the last deploy failed" from "is not running".
- **The panel's go-live certificate is made with the panel's own build.** `panel/golive.ts` runs the hand check and writes the certificate from the template code the panel container is built from, not from the version the shop is pinned to. For a client that `update` held back on an older version, the certificate would name, and be made by, the newer one. The panel only keeps a pin now (it no longer re-pins on an edit); it does not yet read the pin to run the check at the shop's own version. Revisit when: a held-back client is taken through "Ready to go live" in the panel. Until then, make the certificate for a held-back client with `templates/commerce/bookings/scripts/go-live-certificate.ts` from that version's folder.
- **Not in the panel.** Results of an update are in the command's output and in `state/state.json`; the panel's shop page shows the version that runs (`status/<shop>.json`, `versions.pathway`). One screen of every client's version across servers is for the fleet view.
- **Clone a shop's setup for the next client** (the other half of B20) is not part of this.

## Bring your own agent (B51, 5 Nov): what the first slice leaves out

The first slice puts the bundle's Guards in front of an agent's calls to Razorpay, WhatsApp and Google Calendar (`geometer agent add`). Not built:

- **The Claude Code plugin (B11), the n8n importer (B15) and the Lovable door (B18).** Each becomes a way to reach `agent add` (a skill that runs it and rewrites the agent's base URLs; an importer that finds the consequential steps and fills in the settings; a payment module for imported apps). None exists. Revisit when: B51's first slice has been used by a real builder's agent.
- **Any web service beyond the three (B58).** A limits spec from an API's OpenAPI file, Guard as a sidecar in the builder's own cloud, approvals bound to the exact action, the record exported for a company's reviewers, certificates per agent version. `agent add --upstreams` refuses a service it does not know, saying so. Revisit when: a company conversation needs one.
- **A self-serve crash test of the builder's own agent (B52): built 5 Nov.** `geometer agent crash-test`, `agent go-live`, `agent set` (README, "A crash test for your agent"). What it leaves out: "A crash test for any agent (B52)" below. An agent without a go-live certificate still has a monthly report that lists the go-live checks as not given.
- **Prices and opening hours are not checked for an agent we did not write.** Guard has no rule kind for either (its rules are bounds on a number, exact lists, an owner's approval above an amount, once-only effects, caps and forbidden calls). A template's agent checks them itself. They are in the settings file, and so in the report's policy digest, and nothing enforces them. Revisit when: Guard grows a rule on a field it can read from a call (a price floor on a payment link's amount for services that are not deposits is the likeliest).
- **A rule's name in the report.** Only Guard's refund rules map to the report's rule list ("Refunds over your limit"). A refused payment link, a calendar event on another calendar, a message from another number and a payout are in the record (as `blocked`, with Guard's reason) and in the report's table by action, but not in its "what the limits stopped" counts, because that list is the template's nine rules. Revisit when: the report's rule list is open to rules it did not write.
- **WhatsApp has no read-back,** so a message is "confirmed" when the service accepted it (Guard recorded HTTP 2xx), the way a template's is, and its language is the settings' first language (or the owner's, for the relay's notices), not read from the text.
- **The calendar is read around the booked times, one page (250 events), and matched by title and start time.** The window is a day either side of the events the agent booked; one with more than 250 events in it needs paging, and an event whose title the agent changed after booking stays "unconfirmed". A better match is an extended property the agent sets (the template sets `bookingRef`). An event that was changed or deleted is asked for by its id.
- **Guard lists only its 500 most recent decisions, newest first, with no "since".** The record reads them every five minutes, and does not ask the services about what it has already settled (each question asked through a Guard is itself a decision in that list), so an agent would have to make 500 calls in five minutes to outrun it. If the list ever starts after the newest decision the record had read, the record says so: a `record_gap` entry the report lists among what could not be confirmed, and a line in `agent record` and the deployer's log. The calls that fell out are not recoverable from the admin API (they are in the Guard's own store and evidence ledger). The fix is a "since" or a cursor on Guard's side. Revisit when: Guard has one. Until then, an agent that looks at a payment link every second would fill the list with its own reads: the example looks every 15 seconds, and a Razorpay webhook is better still.
- **The owner's words.** The approval request uses the templates' wording: "refund ₹200 for +91... (payment pay_X, 5 Nov 6:00 pm)", where the customer is the number on Razorpay's record of the payment and the time is when they paid. The wording that follows ("...and they will be told") is true only if the builder's agent tells the customer, which Geometer cannot make it do. A wording for an agent we did not write needs new templates under the template's `src/language`, which is another change's ground. Revisit when: the templates are open for it.
- **The heartbeat's `errors` is 0** and its `steps` counts every call the Guards decided on, the reading agent's and the relay's among them: Guard's status gives a count of decisions, not of provider failures. (Guard's decision list does carry "the provider answered 502" in words; it is read for the record, not yet for a count.) The alert fleet sends for a down Guard says "runtime" because the agent has no runtime; it means the agent's Guards. Revisit when: fleet's text can say which.
- **Is an agent a billable shop?** It is one more entry in the heartbeat (`pathway: own-agent`), so fleet's month report and the live-day rule (B13) may count it like a shop's. Nothing here decides whether a Geometer plan applies to an agent someone else wrote. Revisit when: B13's invoice rule is settled.
- **Not in the panel.** An agent lives in `agents/<name>/`, beside `shops/`, so the panel's shop list, its connection checks and its go-live certificate do not see it. `status/<agent>.json` is written in the panel's shape and `geometer status` shows the agent. Revisit when: the panel is asked to show "agents we did not write".
- **No `agent remove`, no rotation of the agent's credential.** Removing an agent is stopping it (`geometer stop`) and deleting its folder and state by hand. The credential is made once and kept, as the other tokens are.
- **One credential for the agent's three Guards.** A leak reaches all three (each still refuses everything outside its limits). A credential for each Guard is a change to what `agent add` prints.
- **No backups for an agent.** The nightly snapshot and the weekly drill walk the shops' runtime databases and their Guards' stores. An agent has no runtime database, and its Guards' stores (every decision, the approvals, the once-only ledger) and `state/records/<agent>.json` (the record, whose sequence numbers a rebuilt one could not repeat) are in no snapshot. Revisit when: the snapshot job is taught the agents' Guards, before the first agent that matters is run.
- **Razorpay's webhooks.** The agent takes its own; Geometer's inbox has no Razorpay route for an agent.
- **Not run against Docker.** The generated compose file with an agent in it, Caddy's `handle_path` cutting the prefix, the `gate` network and the services' paths inside containers were checked as generated text and by the fake machine, not started. The Guards, the relay, the inbox, the record and the report were run for real in the end-to-end test (the real binary, the stand-ins). No real Razorpay, Google or WhatsApp account was used. Revisit when: the next Docker proof run (`test/proof/run.ts` has no agent in it yet).

## A crash test for any agent (B52, 5 Nov): what it leaves out

`geometer agent crash-test`, `agent go-live`, `agent set` and the agent step of `update` (README, "A crash test for your agent"). Not built, or not run:

- **It needs the `geo-guard` program on the machine that runs it.** `--guard-bin`, `GEO_GUARD_BIN`, the PATH, or, on a Linux server, out of the loaded Guard image (`docker create` and `docker cp` of `/usr/local/bin/geo-guard`). That last step was written from the image's Dockerfile and run against a fake Docker in the tests; **it was not run against a real Docker or on a Linux server**. A builder on a laptop without the program, or without Docker, cannot run it yet. The plan's answer is Geometer's Linux runner (B8 phase 2, B9a): the crash test run for a builder who has neither. Revisit when: the runner exists, or the first builder on a laptop asks.
- **Only an agent that is a web server with the two webhook paths can be driven.** An agent that polls Razorpay instead of taking its webhook, runs as a script, is driven by a queue, or lives in a hosted builder (Lovable, n8n cloud) is not started by a command and not reached by a webhook: its situations come out as "not run", each with the reason, and the output tells the builder to say where the webhooks are (`driver`). The doors for those builders (B15, B18) are the way in. Revisit when: they exist.
- **No third-party agent has been crash-tested yet.** Only the two examples (`server.js`, `server-broken.js`) were run. A real agent written by Claude Code or n8n will find the contract's rough edges (a WhatsApp reply to the number without the plus, a template message the stand-in has not approved, a webhook answered before the work is done). Revisit when: the first builder's agent is run through it.
- **"Booked" is read as words.** It is the one place a situation reads text: the WhatsApp stand-in's outbox against `driver.bookedWords` (default `\b(booked|confirmed)\b`, so an agent in Hindi, or one that says "all set", declares its own). The match is on words, not meaning: "could not be confirmed" contains "confirmed" and counts as saying it is booked, so a failure message has to avoid the words of the success one (the example says "could not save your slot yet"). The price situation also reads the outbox for the lower price, so an agent whose refusal repeats the customer's number shows as failing there; `driver.says.haggle` can use another number.
- **The owner's yes is given to Guard directly, not through the inbox and the relay.** Where the refund is above the limit (the usual case: B51's example has a limit below the deposit) the crash test signs the owner's answer itself, with the secret of the Guard it started. The relay, the inbox and the owner's wording are in `test/own-agent.test.ts`; the crash test does not run them. A refund the owner **denies**, one that **runs out** (24 hours), and an agent that stops resending after the yes are not situations yet.
- **Not tried: the agent restarting in the middle of a step, two customers at the same instant, a lost reply on the calendar or on a WhatsApp send, a WhatsApp window that has closed, a model that answers nonsense, haggling in four languages** (only the lines in `agent.json`, one language, are written), and the 24-hour expiry. The NOT TESTED line says the first two, languages and the stand-ins. Revisit when: a builder's agent is hurt by one.
- **A refund above the limit needs a limit below the deposit.** The crash test runs on the settings as they are (the decision: changing them would test other settings, and the certificate would say so wrongly), so with a limit at or above the deposit that situation is named as not run and the refund-lost-reply situation goes straight through without a hold. A builder who wants the held path tried for such a client has to lower the limit in the settings for the crash test.
- **The agent's version is the builder's word.** Geometer starts the command with `{version}` filled in and in `GEOMETER_AGENT_VERSION`; it does not fetch, build or check out anything, and it cannot tell that the code that ran is the code of that version. A command that ignores the version tries the same code twice (the output says so in a note). The version "in service" is the last one that was crash-tested with everything holding (or that an update moved); a builder who runs another version without saying so is not noticed. Revisit when: a builder's deploy can tell Geometer (a webhook from their CI is the likeliest).
- **`update` records and certifies; it does not deploy or roll back an agent.** A new version of the agent is not a change to its Guards, so nothing is deployed (and `run`, `version` and `driver` in `agent.json` are left out of the hash the deployer compares, or saving a version would redeploy the Guards unchecked). "Held back" means: keep running the old version, and the new one gets no certificate. `rollback` says there is nothing for it to do.
- **The go-live certificate is English only, and unsigned without the server's key.** The template's is in four languages, from Bookings' strings, which this change did not edit. Without `secrets/panel/signing_key` the certificate is sealed with a digest and a code but unsigned, and the monthly report reads an unsigned certificate as untrusted (as it does for a template). The same key is the panel's: a server with no panel has none until one is made.
- **Not in the panel, and not in `status`.** The version in service and the last crash test are in `state/state.json` (`agents.<name>.service`) and in `exports/<agent>/go-live-certificate.*`; `geometer status` does not show them.
- **A crash test that is killed outright leaves its agent and Guards running.** Ctrl-C and a plain kill end the agent (which has a process group of its own) and the Guards it started; SIGKILL cannot be caught. `update` starts the crash test as a program with a 30-minute limit, and the runner ends one that runs past it with SIGKILL, so that case leaves the agent's port and three Guards running until someone ends them. Revisit when: a crash test is seen to run that long (ten situations take about 35 seconds).
- **The time.** About 35 seconds for ten situations on a laptop that was not busy (each situation starts three Guards, the stand-ins and the agent, and waits for a quiet moment of about a second after each step). A computer at a high load, or an agent that is slow to start or to answer, will need `driver.startSeconds` and `driver.situationSeconds`. A run at a load of 17 to 26 (the level this computer has been at) was not measured.
- **Situations are matched by their title** across versions in `update`, as a template's are. A title that changes is "no longer checked" for every agent that held it.

## The innovators' template vote (B56, 9 Nov): the heartbeat field fleet must accept

The panel keeps each innovator's vote on the next template in its own store (`bundle/panel/votes.ts`, one file per account, counts shown only to a person who has voted). The votes are meant to reach Geometer as **counts per option in the heartbeat**. Fleet refuses a field it does not know (ADR-0059 decision 12), so **nothing sends it yet**; `votes.heartbeatField()` already returns the exact shape.

- [ ] **Fleet: accept one new optional top-level heartbeat field, counts only.**

  ```json
  "template_votes": { "round": "2026-11", "counts": { "orders": 1, "fees-extensions": 0, "equipment-rental": 0, "social-posting": 0, "course-packs": 0 } }
  ```

  - `round`: `YYYY-MM`, the poll's round (`bundle/panel/vote-options.json`).
  - `counts`: an object of option id to a whole number 0 or more. An option id is `^[a-z][a-z0-9-]{0,39}$`; at most 20 options. Fleet adds a server's counts per round; it does not need to know the options in advance, and it must not store anything else from the field. No account id, name, shop id or address is in it, and there is no per-voter detail to ask for.
  - Optional on both sides: a heartbeat without it is valid (a server with no innovator, or no vote yet, leaves it out).
  - Fleet side: `src/schema.ts` allows the field and checks the shape above; `src/store.ts` keeps one row per (deployment, round, option) with the latest count; the README row `template_votes | object, optional | Counts of the innovators' votes on the next template, by option; counts only`.
  - Bundle side, once fleet is deployed (deploy fleet **before** any bundle that sends it): `services/heartbeat.ts` reads a plain, counts-only file that the panel writes after each vote, the way `status/` and `fleet/` files are shared (for example `<server>/panel/vote-counts.json`, `{ schema: 1, round, counts }`, no account ids, outside the sealed `panel/data/`, which the heartbeat process must not be able to open), and sends `template_votes` only when at least one vote is in the current round. The panel does not write that file yet: the per-account votes in `panel/data/votes/` are sealed by the data key when there is one, and the ops process must not hold that key.
- [ ] **The totals Geometer reads are for a whole programme, the panel's are for one server.** Until fleet accepts the field, the results an innovator sees are the votes counted on the panel they use (the page says so). Revisit when: fleet accepts the field and can hand back the programme's totals.

## Not built

- **What a shop did after its snapshot is lost by a restore.** A snapshot is up to a day old (and `--at` can pick an older one). After `restore` the runtime moves its ids on and every payment link, refund and calendar write is looked up at the provider before anything is sent, so nothing is paid, refunded or booked twice. But the shop's own record and cases go back: a booking cancelled after the snapshot is "confirmed" again (its reminder can go out, and its calendar event, deleted at the cancel, is not there); a payment that came in after the snapshot is found again only when that booking's hold runs out or a person asks to look again from the to-do list; a UPI payment the owner marked after the snapshot is unmarked (there is no provider to read it back from); messages the agent sent are not in its record; a refund Guard began to hold after the snapshot (the customer was told it is pending) is unknown to the restored shop, so when the owner approves it the runtime records that no refund waits on that approval and nothing goes out, and nobody is told: it is on no to-do list. Revisit when: a shop is restored for real (a "look at every open case at the provider now" pass at the first start, or the owner told what to check).
- **A restore behind the last daily fingerprint.** When the restored record is shorter than the last published fingerprint, new entries take sequence numbers that were already published with other content: from then on the daily fingerprint is refused for that shop and the weekly drill fails its fingerprint comparison, and both say the record no longer matches what was published (which is true). `restore` says so when it happens. Revisit when: a restore is done for real (a fingerprint line that marks a restore, chained to the last one, and geometer-verify reading it).
- **A Guard's own store is not put back by `restore`.** The snapshot has each Guard's backup folder (`guard-<kind>.tar.gz.age`); putting it back is `geo-guard restore` with the Guard stopped, by hand. For a refund that is the safer way round: a Guard whose store is not restored still remembers a refund sent after the snapshot. Revisit when: a server's disk is lost for real.
- **The weekly drill does not open a snapshot.** The owner's key is kept off the server, so the drill checks what it can without it (the objects read back unchanged, the copy's integrity check when it was made, its record against the live one and the fingerprints). That a snapshot decrypts and restores is the full restore test, by a person with the key, monthly, on their own machine (README, "Backups"). Nothing reminds them or records that it was done. Revisit when: the panel can remind the owner and take "done, it opened" as a fact for status and the heartbeat.
- **A bucket key that may not read.** The drill's read-back and `restore` need to read; with a create-only key the drill says every week that it could not complete (and fleet alerts), and `restore` cannot fetch. Revisit when: the bucket's account is set up (the monorepo's Terraform gives the partner server a create-only account today).
- **No per-shop retention setting.** The runtime empties a failed message's text, and Orders a finished order's delivery address, 30 days later for every shop (`CONVERSATION_RETENTION_DAYS`; the core takes `retentionDays`, but nothing sets it yet). Revisit when: a shop or a law asks for another period.
- **Rotating a shop's tokens.** Agent, admin, internal and relay tokens are made once and kept. Rotation (and the Google service-account key changing) means deleting the file and deploying; there is no command, and a rotation of the owner's approver secret needs the Guard restarted.
- **Several shops on one WhatsApp provider account sending webhooks to one URL.** A shared Meta app posts every number's messages to one callback. The bundle gives each shop its own path (`/c/<shop>/...`), checks the signature and drops a body for another number, but does not route one shared callback to the right shop by `phone_number_id`. Revisit when: a builder runs several shops on one app and cannot configure a callback per number.
- **A per-shop `limits.json`.** The caps that settings do not carry (messages an hour, calendar events, the model's calls a day) are server-wide defaults in `geometer.json`. Plan 4.6 has a `limits.json` per client with a history.
- **Per-shop model caps.** The model is included in the shop's Geometer plan, bounded by the plan's message allowance and a monthly cap per shop (plan decision 6): above it the agent falls back to its rule parser and the builder is told. Today the model Guard has one cap for the whole server, so nothing stops one shop from using all of it and nothing tells the builder. The panel's cost line does not read model use at all any more; it only says the model is included. Revisit when: the model Guard can count per shop (Guard work), then the cap and the "you were told" notice.
- **Postgres for Guard, Guard behind several replicas, and Guard on its own host.** One SQLite store per Guard, one replica.
- **Upgrading the bundle itself** (a signed release, a `geometer upgrade`). Today the builder pulls the repository and runs `deploy`; services whose compose entry changed are recreated, those whose files changed are restarted.
- **CI for the bundle's tests.** The repository's workflow does not run `node --test bundle/test/` or the template tests. The proof (`bundle/test/proof/run.ts`) needs Docker and about twenty minutes and is run by hand.
- **Windows.** The deployer assumes a Linux or macOS host with Docker Engine or Docker Desktop. The plan's Windows route is WSL2, not tested.
- **Cheaper forwarders.** Each Guard has a 1 MB `busybox nc` forwarder and each shop a door. That keeps the admin port off the runtime's network without TLS on the Guard's agent port. If Guard ever serves its admin port with its own TLS cleanly, the forwarders can go.
- **Several approvers (B37, 8 November): what is left.**
  - The approval roles are written only for a shop's Razorpay Guard. An agent someone else wrote (`agent add`) has one owner.
  - **Upgrade every Guard replica before a shop names a two-person amount** (Guard's ADR-0061: a replica of an earlier release would approve a two-person refund on one answer). The bundle runs one Guard per upstream per shop, so it has one replica, but the Guard image it loads must be one built after `e99d5d47`.
  - Removing a person from the settings leaves their secret file in the two folders. It is unused, and Guard no longer lists them.
  - The panel's go-live checks and the certificate do not yet say who approves. The record still labels every approval an owner's decision (`agent/record.ts`).
  - Revisit when: the first shop with a manager goes live. Done when: the certificate names the approvers and the two-person amount, and the record labels each approval by who gave it.

- **A UPI shop's deploy has not run on a real server.** `test/upi-shop.test.ts` deploys one against the test world (no Razorpay Guard, no key, no relay). Revisit when: the
  first partner shop on UPI goes live.
- **Switching a live shop between UPI and Razorpay.** The deploy plans the new set of Guards, but a Razorpay Guard left over from before is not taken down by name, and its
  secrets stay in their folders. Revisit when: a shop switches.

## Records anyone can check (B28, B35, B36; 8 November 2026)

- **No public target is switched on.** The git repository and the OpenTimestamps calendars wait for the owner's yes, and for the choice of the public repository; until then the fingerprints stay in `state/fingerprints/` on the server, where the shop's operator could rewrite them. Revisit when: the owner says yes and names the repository.
- **A server with no panel key writes unsigned fingerprints.** They cannot be used as geo-verify anchors (geo-verify needs a signed checkpoint and a key log). Revisit when: every server has a signing key (the runtime's `report.signingKeyFile` is not given to the deployer either).
- **A shop moved to another server keeps its agent id only if that server's operator copies `identity.json` from the export into the new shop folder** (the B38 export now carries it, with the evidence pack, its anchor and the fingerprints). Nothing imports an export yet. Revisit when: import from an export is built.
- **A shop deployed before this change gets `report.tenant` (and so an anchored monthly report) at its next deploy**, because the deployer redeploys a shop only when its own files change. Revisit when: a fleet-wide redeploy is next run.
- **The ledger is rebuilt from the whole record on every export** (every quarter of an hour). Fine at today's sizes (a few thousand entries); a shop with hundreds of thousands of entries would want the head kept and only new entries chained. Revisit when: an export takes more than a few seconds.
