## One source for every spec

`generate/guards.ts` defines each Guard once (its `tool` name, its upstream, the header it adds) and generates both files of the pair from that definition, so the tool name is written in one place. A Guard checks the same thing at start (`cannot start: the policy bundle names tool "razorpay" ... but guard.toml says tool = "whatsapp"`); the generator also compares the spec, the guard.toml and the compiled bundle's tool and tenant before anything is started (`tool-names-match`).

The Razorpay spec still comes from `templates/commerce/bookings/src/guard-limits.ts`: the deposit bound and the refund threshold are the shop's own settings, not typed. The WhatsApp spec pins the shop's `phone_number_id` with `"match": "exact"` (not a number that merely ends the same way) and the Calendar spec pins the shop's `calendarId` the same way on every event operation. The monorepo's `deploy/pathways/bookings/*` are now **fixtures**: `test/drift.test.ts` reads them from a sibling path (and skips, saying why, when they are absent) and compares routes, rule ids and kinds, limits, intents and the guard.toml keys and headers. It found one real difference on its first run: the Anthropic template says `anthropic-version = "2023-06-01"` and the template's parser sends `2026-10-21` (structured output needs the newer one). The generator writes the parser's value (exported from `model-llm.ts`, one source), and the test does not compare that value. **Not checked against the real API:** which of the two a Guard keeps when the agent also sends one.

**The approval window is one setting**, `approvalHours` in `geometer.json` (default 24). It becomes Guard's `approval_ttl_seconds`. The owner's message used to say "within 24 hours" from a constant; the relay already computed the hours from Guard's `expires_at_ms` less the hold's time, and the remaining `24` (a default in the relay's store) is gone, so the words can only come from Guard. A test with a six-hour hold shows "within 6 hours".

## Why a Guard per shop

A Guard binds one tool and one bundle (`tool` in guard.toml, one policy in force), and its per-agent configuration cannot restrict argument values: an `[[agents]]` entry has an id, a token hash, a tenant and an optional list of **operations** (`config.rs` lines 11-27; `engine.rs` 783 checks `agent.tenant == cfg.tenant` and 802 checks the operation against `agent.operations`; nothing reads an argument). A WhatsApp or Calendar Guard shared by two shops would have one bundle for both, so the exact-allowlist that pins the shop's number could only list both numbers, and shop A's runtime could send from shop B's. Hence three Guards per shop, each pinned to that shop's own ids. The model Guard is shared because the thing it pins (the model) is the same for everyone; every shop's runtime is an agent of it, in the server's tenant.

## The shape of the server

`generate/compose.ts` documents the layout at its top. The points that took a decision:

- **The runtime's network holds the runtime, its three Guards, the model Guard and its door, and nothing else.** Docker has no one-way network: a container on the runtime's network is a container the runtime can connect to. The inbox, the relay and ops must reach the runtime, so they are **not** on its network. A `door-<shop>` (a busybox `nc`) is on the runtime's network and on the `admin` network, listens only on its `admin` address and passes bytes to the runtime; the runtime is not on `admin`, so it cannot connect to the door. The relay reaches the shop's WhatsApp Guard on that Guard's `admin` address. The proof tries each of these from inside the runtime.
- **Guard's admin port.** Guard's production profile refuses `admin_listen` on any address but loopback unless `listen_tls` is set (`config.rs` 608), and `listen_tls` also puts the agent port behind TLS. The runtime would then need a certificate authority. The bundle keeps the admin port on loopback and puts a 1 MB busybox forwarder (`fwd-<shop>-<tool>`) in the Guard's network namespace, listening only on the Guard's address on the `admin` network. The forwarder **owns** the namespace and the Guard joins it, as the TLS front does in `deploy/compose`: a Guard that crashes and restarts leaves the namespace and the forwarder as they were (the other way round, a restarted Guard strands its sidecar). This sidesteps the TLS rule rather than meeting it, on purpose: the forwarder's network has no route to anything that is not a service of the bundle, and every admin call needs the admin token. It costs three small containers per shop; Deferred.md has the way out.
- **Reaching the admin ports from the host.** On Docker Desktop the host cannot reach container addresses, and on Linux not those of an internal network. So the deployer never connects to a Guard: it runs `docker compose exec ops node ops.ts admin <guard> ...` and `ops` (the one container that holds every Guard's admin token and is on the `admin` network) makes the call. No admin port is published.
- **Secrets.** One folder per container under `secrets/`, mounted into that container only. The Razorpay key is in `secrets/g-<shop>-razorpay/` and nowhere else; the webhook secrets in `secrets/inbox/`; the owner's approver secret in `secrets/g-<shop>-razorpay/` and `secrets/relay/<shop>/`; the Google key in `secrets/refresher/`. The runtime's folder has its own internal token and its credentials for its Guards. File modes are in the README. The panel has no secrets folder and no Docker socket.
- **Users.** Our Node programs run as the image's `node` user (uid 1000), the Guard as its own uid 65532, both read-only, no capabilities, `no-new-privileges`. A named volume mounted at `/home/node` is created with the image's ownership, so a non-root runtime can write its database without a root `chown` step. The Google token volume has one sub-folder per shop, and a Calendar Guard mounts only its own (Compose `volume.subpath`, Docker Engine 26 or newer).
- **The Guard image.** Not in a registry. The deploy checks it is on the machine and says how to load it.

## Deploy, in the order it happens

`check` and `deploy` share one path (`prepareShop`, `compileAndVerify`). `check` stops before writing; `deploy` goes on.

1. The secrets handed in are taken (each checked for shape; a bad one stays in the inbox and is named). The shop's files are read; every problem with them is collected, not just the first.
2. **Generator rules** (each names itself in a refusal): `runtime-timeout-exceeds-guard` (the runtime's `services.timeoutMs` must exceed Guard's `upstream_timeout_ms`, 15 s; the template's own default is 10 s, so the bundle writes 20 s when runtime.json says nothing and refuses 15 s or less), `runtime-mode-live` (a deployed shop never runs the in-process stand-ins), `calendar-id`, `whatsapp-number-id`, `model-matches-guard` (the shop's parser must ask for the server's one model on its wire), `pathway-pin`, `secret-missing:<name>`, `guard-image`, `tool-names-match`, `no-secret-in-files`.
3. **Versions.** Guard ignores a bundle whose `version` is not higher than the one in its store, and compose does not recreate a container when a bind-mounted file changes. So each Guard has a counter in `state/state.json`: the same spec content keeps its number, changed content gets the next, and a rollback of settings gets a *new* higher number, never the old one.
4. Every spec is compiled and every guard.toml verified with `verify-bundle --config` in the image (`--network none`, read-only). **Every tripwire must pass**; a failure names the rule. The model Guard is verified again whenever a shop is added, because its agent list changes.
5. Files are written, `docker compose up -d` brings up what is missing or whose entry changed, and **only** the services whose mounted *files* changed under an unchanged entry are restarted. Nothing else is touched.
6. **The proof is read from the running Guards**, not from the offline check: each Guard's `/admin/status` must report the policy digest that was compiled and `tripwires.ok`. "N of M limits proven to bite" is their `passed` of `of`; what a tripwire cannot test without writing (every spend or count limit, the at-most-once rule) is named and never counted. If a running Guard disagrees, the shop is stopped with the kill switch and the deploy is refused. A Guard also repeats its tripwires every five minutes, and a failure turns `/readyz` to 503.
7. The relay's reading credential (an approver credential, which production requires to expire) is issued through ops and written where only the relay reads it; the deployer renews it daily.
8. `status/<shop>.json` is written for the panel.

`stop` sends `POST /admin/kill` to the shop's three Guards and `POST /admin/agents/runtime-<shop>/stop` to the model Guard (so the other shops keep working). The reason carries who stopped it and when; Guard writes it, with its own admin id, into its evidence ledger, and the deployer keeps it in `state/` and `status/`. Guard keeps the kill switch in its store, so it survives a restart (the proof restarts the Guard); the deployer also re-applies it after a deploy.

## The inbox, the relay, the refresher, the heartbeat

- **Inbox.** `/c/<shop>/webhooks/...`; each shop has its own `inboxHandler` (extracted from `startInbox`; the checks are the template's) with that shop's secrets and its own runtime. A test proves that A's signature does not open B's door, that an unprefixed path is not served, and that with **two shops on one Meta app** (one app secret, so a valid signature does not say whose message it is) a body for B's number posted to A's door is verified and then dropped: `metadata.phone_number_id` must be the shop's. Routing one shared callback URL to the right shop is Deferred.
- **Relay.** The template's relay, one instance per shop, each with its own state folder, its own approver secret and its own reading credential, re-read from its file on every call so a renewed credential needs no restart. The WhatsApp Guard has a second agent entry for the relay, limited to the `send` operation.
- **Refresher.** Per shop: a signed assertion (RS256) to the service account's token endpoint, `Bearer <token>` written for that shop's Calendar Guard only, then `POST /admin/reload` on that Guard. About every 45 minutes and always before the token runs out. The token is never logged and is not in any URL; the exchange is tried once, and a failure waits 1, 2, 4 ... 10 minutes instead of repeating; the key file is only read. There is no refresh credential in this flow to rotate; the discipline items that apply are kept and the others do not arise. The Calendar Guards wait for the refresher's first token.
- **Heartbeat.** Every 60 seconds from `ops`: the exact body of the fleet contract, built field by field from numbers and booleans (never copied from a reply), with `ready=false` for a Guard that is not ready, whose admin port cannot be reached, or whose tripwires failed. `since_last` is the difference since the last heartbeat fleet **accepted**, and a runtime that restarted (its `startedAt` changed) starts again from zero. The runtime's `/status` gained `steps`, `errors` and `startedAt` for this (a small change in `server/`; steps counts finished tasks, not ticks). The body is run through fleet's own `checkHeartbeat` in a test. Shop names are checked when the shop is added against the rules that make fleet refuse a whole heartbeat. **Backups (4 Nov):** two optional fields per shop, `backup_age_s` (seconds since the last good nightly snapshot) and `drill` (`{age_s, ok}` for the last weekly restore drill). The deployer's backup jobs write the times to `status/<shop>.json`; `ops` now mounts that folder read-only (the panel already did) and `readBackups` takes three fields from each file: `lastCopyAt`, `lastDrillAt` and `drillOk`. They are **ages, not times**, worked out on the host from its own clock, because fleet's counts stop at 999,999 on purpose (a phone number cannot pass as one) and a time as text looks like a phone number to its check. A field is left out when there is nothing to say (no file, no snapshot yet, text that is not a time), never sent as 0, because fleet reads "absent" as "nothing to report". The drill's free-text reason is never read into the heartbeat. A failed drill is still **not** `ready=false`; fleet judges it with its own rule, so billing is untouched. The contract tests run the body through fleet's validator and are skipped, saying why, when the validator found is older than the fields. Not run: the ops container reading the file inside Docker (the file is mode 0644 in a 0755 folder, as the panel's is; no Docker was run for this change).

## The cost meter, plans and button mode (5 November: B45, B48, B56)

Fleet's contract grew two things (`apps/fleet/README.md`, "the cost meter's counts" and "What fleet tells each shop"); this is the bundle's half. All of it is counts, never message text.

- **Counting.** `lib/usage.ts` turns a shop's record entries into cumulative totals: customer messages (a `receive_message` that was `confirmed`; a repeated delivery is `blocked` and is not one), the same messages by the step that understood them (`rules`, `decision`, `model`), the model spend in micro-rupees, and outgoing WhatsApp messages by Meta's type with a gross estimate (GST included, before the month's free replies). **The path is the 15-minute export**, not the runtime: `backup/export.ts` already reads every record entry of every shop, so it counts them through the adapters and the deployer writes the totals into `status/<shop>.json` under `usage`. Nothing in `templates/commerce/bookings` changed. The price is a delay: counts, and so button mode, can be up to 15 minutes behind.
- **The one adapter.** `understandingOf(entry)` is the only code that knows the new record fields the `understanding` branch adds (step, provider, model, tokens, estimated cost). Their guessed names are one constant, `FIELDS` in `lib/usage.ts`; align it at merge and the tests follow it. An entry without them is a `rules` message with no spend. A message that has a step but no usable cost (the template leaves `costMicroInr` out when the call had no price in its rate table) is **unpriced**: unknown, never 0. The totals count those apart (`unpriced`), so `modelMicroInr` is a floor and says by how many calls. The count is kept in `status/<shop>.json` and read by the panel's `parseStatus`, but it is **not sent in the heartbeat**: fleet refuses a field it does not know and has no slot for it, and a test keeps the body without it (`bundle/Deferred.md` has the exact fleet change, and the bundle's four edits for after it). `whatsappTypeOf(entry)` types a sent message from what the record holds today: a notice to the owner or a reminder is **utility**, any other reply is **service**, nothing is **marketing**. It leans high (an owner's notice sent as plain text inside the owner's own window is counted as utility).
- **Sending.** `buildHeartbeat` sends `usage` as the **difference** against a baseline, with the contract's 999,999 cap per count. The baseline moves only by what was sent (so the excess goes in the next heartbeat) and only when fleet answered 200, and it is a file, `fleet/usage-baseline.json`, so a restart of ops does not replay the record. A shop with no baseline **starts at its current totals and sends nothing**: months of history put into one day would be a lie. A total that went down (the record was restored) restarts the baseline. A shop with nothing new has no `usage` field.
- **Fleet's answer.** `sendHeartbeat` returns the parsed `shops` of a 200 (`lib/fleet.ts`, field by field; an unknown `ai` makes no entry). Ops writes `fleet/<shop>.json` for each shop in it and leaves every other file as it was: **no answer means keep the last mode, never "normal"**. `fleet/` is the only folder ops can write (a new rw mount; ops runs as the deployer's user, as the panel does, so the deployer and the panel, which mounts it read-only, can read what it writes).
- **Button mode.** `readShop` reads `fleet/<shop>.json`; if it says `ai: "buttons"` for a shop that has a plan, `planShop` puts `"ai": "buttons"` into the **generated** runtime config (never the panel's `runtime.json`, which the panel rewrites and whose checker refuses unknown keys), and the fleet mode is part of the desired hash, so a flip redeploys the shop. **It is written only if the template's own `validateRuntimeConfig` accepts the key.** Today's does not know `ai`, so today the override is skipped with a note (`fleet asked for button mode, but this template version does not know the ai setting yet`) and the shop keeps its AI; the tests cover that case and, with a stand-in validator that knows `ai`, the written and the removed case. The day the button-mode work merges and the validator accepts `ai`, the same code writes it, with no change here.
- **The price list.** Every list is in the repo's one price folder, `prices/` (its README says who reads it; the lists were in `bundle/prices/` until 9 Nov). `prices/2026-11-05.json` was written as a proposal (`status: "proposed"`, linked to `docs/product/economics-and-pricing.md`); the owner decided it on 5 Nov and `prices/2026-11-07.json` put it in force. On 9 Nov the owner made it two price lists and nothing else, and `prices/2026-11-09.json` is in force: partners (Geometer's templates on Geometer's servers) pay a plan per live shop, with an allowance, extra messages, WhatsApp and the recharge's payment fee at cost, and the month's AI cap; builders (always their own server, AI key and WhatsApp) pay one flat licence per live client business (`licence.builder.fee`). There is no first-100 price and no self-host share of a plan; the Innovator badge and its places stay. `latestPriceList()` skips a proposed list and reads the newest list in force; the panel's cost line, its plan block and the health page read it through one rule (`panel/cost.ts` `chargeOf`). A changed price is a new dated file (`node prices/new.ts <date>`), never an edit.
- **The panel.** The shop page gains a plan block when `fleet/<shop>.json` exists: the plan, the included messages, Geometer's charge (the plan's fee on Geometer's server, the builder licence on a builder's own), the Innovator badge, button mode with its reason in plain words, and the warnings (`allowance_80`, `balance_80`, `whatsapp_unsettled`, `ai_cap`), in four languages (hi, ml and kn machine-written, in section 7 of the REVIEW sheets).
- **Against fleet's real server.** `test/fleet-end-to-end.test.ts` runs this sender against fleet's own server and billing engine (not a stub) when the monorepo is at hand: the first heartbeat sends no `usage` and is answered with the plan and allowance; a second with 1,100 more messages is accepted by fleet's own validator and answered `ai: "buttons"` with the reason `overage_unfunded` (the partner has no balance), and what the bundle's `parseFleetAnswer` reads is what fleet said. It skips, saying why, when fleet is not there or does not have the billing engine yet. One consequence worth knowing: because history is not replayed, fleet counts a shop's messages only from the day its meter started, so a shop already in the middle of a month is metered from then.
- **Rollout order** (as for the backup fields): deploy a fleet that knows `usage` and `shops` before any bundle that sends `usage`; an older fleet refuses the heartbeat whole, which looks like a dead server. A new bundle against an older fleet is therefore the thing to avoid; an older bundle against a new fleet is fine.
- **What the tests show.** The counting with and without the new fields, the adapters' malformed inputs, the cap and carry, the restart, the refused-heartbeat case, fleet's own validator accepting the body (when the monorepo is found), the answer parse, the files, the compose mounts, the button-mode cases above, the price list and the panel page in two languages. **Not run:** ops writing the fleet folder inside Docker as the deployer's user, and the real runtime reading `ai`.

## The owner's monthly report, switched on (5 November: B54's bundle half)

The template's runtime writes each month's report into `<dataDir>/reports/<32 random hex digits>/` and sends the owner a link. It was off unless `runtime.json` had a `report` block, because nothing served the folder and nothing wrote the block. Both are now the bundle's. Three pieces:

**1. Serving the pages (`generate/compose.ts`, `generate/shop.ts`).**

- **The address** is `https://<domain>[:port]/r/<shop>/<32 hex digits>/<file>`. The shop is in the path because one server holds many shops and each has its own data volume. The runtime is told `report.pageBaseUrl = https://<domain>/r/<shop>` (`reportBaseUrl`), so the link it builds is a link Caddy serves; a test builds one and runs it through the matcher.
- **Caddy mounts one folder of each shop's data volume, read-only**: the volume `rt-data-<shop>`, sub-folder `data/reports` (Compose `volume.subpath`, as the Calendar Guard's token folder already is), at `/srv/r/<shop>`. It does not mount the volume. Caddy is the one container the internet talks to, and the rest of the volume is the shop's database and its record, with customers' numbers. With only the reports folder in reach, a mistake in Caddy's routing could show a report but never the record. The mount point is chosen so Caddy's file root is `/srv` and the address `/r/<shop>/<hex>/<file>` is the file's own path, which needs no rewriting.
- **Why a one-shot makes the folder (`rd-<shop>`).** Docker cannot start a container that mounts a volume sub-folder that does not exist, and the runtime makes `data/reports` only when it writes its first report, a month later. So a tiny service runs `mkdir -p /home/node/data/reports` in the runtime's own image (`node`, user 1000) with the shop's volume mounted at `/home/node`, the runtime's own path: a fresh volume then gets the same owner the runtime would give it, and the runtime can write the folder. No network, no capabilities, read-only filesystem, restart `"no"`, and it waits for nothing, so a shop whose Guards are down does not hold Caddy back. Caddy waits for it (`service_completed_successfully`) and nothing else. `docker compose up -d` runs it again each time, which is harmless (`mkdir -p`).
- **How the 404s are enforced, in two layers.** First, one regular expression is the only thing served: `^/r/(a-shop|b-shop)/<32 x [0-9a-f]>/[A-Za-z0-9][A-Za-z0-9._-]*\.(html|json|txt)$` (`reportsMatcher`; the 32 digits are written out, not `{32}`, so no curly brace sits in a Caddyfile word). The folder, the shop's folder, `/r`, a shop this server does not have, capital letters or the wrong number of digits in the folder name, a hidden name, a name with a slash or `..` or an encoded one, and any other extension do not match. Everything under `/r` that does not match meets `respond 404` in a catch-all `handle` written inside the same `handle` as the file server, not beside it, so the answer does not depend on how Caddy orders separate `handle` blocks whose matchers are a regular expression and a path list (a bare `handle` is always last in its block). Second, the file server is the plain `file_server`, with no `browse`: even a folder that reached it would be a 404, because Caddy lists a folder only when told to. Pages are sent `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer` and the same Content-Security-Policy the panel gives the same pages (no script, nothing external, no frame).
- **A shop added or removed changes Caddy's mounts**, so Caddy is recreated and its connection drops for a few seconds. Provider webhooks are retried. This is the same kind of recreation as the model forwarder's when a shop is added.

**2. The `report` block (`withReport` in `generate/shop.ts`, `readShop` in `lib/server.ts`).** Next to `withFleetAi`, and by the same rule: it goes into the **generated** runtime config only, and only if `validateRuntimeConfig` of **the version the shop is pinned to** accepts it. A runtime from before the report refuses a `report` key as an unknown setting and would not start; a shop that cannot start is worse off than one that sends no report, so the block is skipped and a note says why (with that version's first error). "The pinned version's" matters: `prepareShop` used to judge `ai` by this checkout's validator, which is right only for a client on today's version. A client `update` held back on an older version, kept in `<server>/pathways/bookings@<v>/`, would have been handed a key its own runtime refuses, and the deploy would still have said it succeeded, because the proof reads only the Guards. So `prepareShop` now resolves the pin's folder first and loads that folder's `server/config.ts` (`pinnedRuntimeCheck` in `lib/pathways.ts`, in the deployer's own process; the module cache makes today's version the same one the generator already imports), and gives it to both `withFleetAi` and `withReport`. A version whose check cannot be loaded (another layout, a file that does not import) is treated as knowing neither setting, with the reason in the note. The block is `{ preparedBy, innovator, pageBaseUrl, pagesDir, source }`:

- `preparedBy`. The bundle did know who set a shop up: the panel writes `shops/<shop>/owner.json` (account name and role) when it makes a shop, and its own report and go-live certificate already build "Divya, local partner" from it. That string is now made in one place (`preparedByOf` in `panel/contract.ts`, which the panel and the deployer both read), cut to the 120 characters the runtime accepts and put on one line. A shop made by `shop add` has no `owner.json`, so there is one shop-level setting: `shops/<shop>/report.json`, `{"schema": 1, "preparedBy": "..."}`, written by `shop add --prepared-by`. It wins over `owner.json` (a person's word over the record), and with neither the message says "your builder" and the deploy prints a note. A `report.json` that cannot be read is a refusal that names the file, as `pins.json` is, not a silent fallback. The panel's own report reads the same two files in the same order.
- `innovator` is fleet's answer for the shop (`fleet/<shop>.json`, which billing writes), a plain `true` only. No answer, an unreadable one or a non-boolean is no badge.
- `pageBaseUrl`, `pagesDir`: above. `pagesDir` is written out (`/home/node/data/reports`) instead of left to the template's default, so the folder Caddy mounts and the folder the runtime writes are named in the same constant.
- `source` is `live` only when the panel's connection check pinned a live Razorpay account (`pins.json`), otherwise `test-mode`, the rule the panel's own report uses. Left out, the template says `test-mode`, and a live shop's owner would be told their real money was test money.

**The desired hash** (`desiredOf` in `deploy.ts`, used by both `desiredHashOf` and the deployer's signature) now holds `{ preparedBy, innovator }`, so a change of the name or of fleet's badge redeploys the shop and rewrites its `runtime.json`; changing back restores the old hash. It is always in the hash, not only when the badge is on, so every shop deployed before this is redeployed once, which is what writes its block. The runtime reads the name and the badge again whenever `runtime.json` changes, but the deployer restarts a service whose mounted file changed, so it restarts. **The domain and the HTTPS port are not in the hash**: they belong to the server, not the shop, and a changed domain moves every webhook address as well.

**3. The panel's own report** (`panel/server.ts`) passes `innovator` from the same fleet file (`shops.fleet(id).innovator`) and the name from `shops.preparedBy(id)`, so the builder's copy and the owner's agree.

**What the tests show.** Of the Caddyfile: the exact file shape is served and 26 near misses are 404 (run through the Caddyfile's own regular expression, with the mounts standing in for Caddy's root); the `handle` order; no `browse`; the headers; a server with no shop still answers 404 under `/r`. Of the compose file: Caddy's mounts are the reports folders and nothing else, read-only; `rd-<shop>`'s command, user, image, network and hardening; Caddy waits for it and it waits for nothing; the folder Caddy mounts is the folder the runtime is told to write. Of the block: its values, the badge on and off and for every wrong shape of answer, the address with and without a port, live and test, the name from each source and the cut, the skip for a template that refuses the key (a stand-in check, and a real older version kept beside the server: no block, one note, it starts, and it gets the block once moved to today's version; and a version whose check will not load), the hash, the deployer redeploying on a badge flip and on a new name and writing the block, a pre-existing shop redeployed once, `shop add --prepared-by`, and the failed-`up` message leaving the one-shots out. Of the panel: the badge and the name on the builder's copy. `docker compose config -q` accepts a generated file with two shops, and its resolved form has the sub-path mount and the dependency. **Not run:** Caddy itself (no container was started, so the matcher and the `handle` nesting are checked as text and as a regular expression, not as Caddy reads them), and Docker starting the one-shot and mounting the sub-path on a fresh volume.

## Data redundancy

Read the table in the README. The decisions:

- **One copy a night, no continuous copy** (since 9 November 2026; the section at the end of this file says why). The runtime leaves checkpointing to SQLite's own automatic WAL checkpoint (a test opens a store and reads `PRAGMA wal_autocheckpoint`); nothing holds a long read open on its file any more. The data lives on a named volume, not a bind mount.
- **Guard's store** is backed up with Guard's own `POST /admin/backup` (a `VACUUM INTO` copy of the store plus the evidence ledger and a signed anchor, verified with `geo-verify`, taken while it runs), written into the Guard's own volume and picked up by the nightly job.
- **Nightly snapshot.** One short-lived container with the volumes mounted: `VACUUM INTO` on a read-only connection (SQLite's own consistent copy while the runtime writes; nothing is done to the live file), integrity check, then ONE object per database file: the runtime's copy gzipped, each Guard's backup folder as one `.tar.gz` (its ledger grows a file every 500 decisions, so file by file it would cost more each month), and a gzipped manifest with each file's size and digest before compression and the record's length, last sequence number and a digest of its last entry. Each is age-encrypted (`backup/age.ts`, the standard `age-encryption.org/v1` format with X25519 recipients) to the owner's key (its secret half is not on the server), then, only as a fallback for a bucket with no lifecycle rule, pruned by the date in the key (30 days). A bucket key that may not list or delete does not fail the night: the line says "pruning left to the bucket's lifecycle rule". The job also hands back each snapshot's seal in the clear (each object's sha256 as uploaded; the copy's record length, last entry digest and hash-chain head), which the deployer keeps in `state/snapshots/<shop>.json`. It runs as root with every capability dropped except the two that read and write files it does not own, on the egress network only when the target is a bucket. Snapshots written before 9 November (one plain `.age` per file) are opened by the same code, told apart by the name, not by the first bytes (a Guard file may itself start like gzip).
- **Weekly drill, without the key.** One container reads every object of each shop's newest snapshot back by the keys in its seal (one GET each, no LIST) and compares its sha256 with the seal's; a bucket that refuses the read is a drill that could not complete, with the bucket's reason. Then the seal's record against the live database: the live entry at the copy's last sequence number has the same digest, and the live record's hash chain at that entry is the copy's chain head, so the copy is the start of the live record entry for entry (the live record may have gone on since); and against the shop's published daily fingerprints, the copy must hold every entry of the last fingerprint published before the snapshot was taken, and the chain must match the newest fingerprint it holds. A fingerprint published after the snapshot is newer than the copy, which is how a nightly copy is, not a fault. The copy's soundness is SQLite's integrity check, run on the plain copy when it was made (no snapshot is written otherwise). The result is in `state/`, in `status/<shop>.json` and in `geometer status`. That a snapshot opens is the monthly full restore test, by a person with the owner's key on their own machine (README, "Backups").
- **`restore`** takes the owner's key from the person restoring (`--identity`, mounted read-only into the one container that opens the snapshot), fetches and checks the snapshot while the shop runs (nothing of the shop's is touched if that fails), then stops only the shop's runtime, copies the file in as the runtime's own user beside a `restored.json` note, keeps the file it replaces as `agent.db.before-restore-<time>`, and starts it. The runtime's restored mode is below.

## The panel's contract (added 4 November)

The panel (`bundle/panel/`, merged into main separately) shares files with the deployer, and writes its shapes in `bundle/panel/contract.ts`. The bundle follows them:

- **`status/<shop>.json`** is the panel's `ShopStatus`: `updatedAt`, `deploy {state, at, message}`, `limits {proven, of, unprovable}`, `versions {template, bundle, guard}`, `stopped {at, requestId}`, `backups {lastCopyAt, lastDrillAt, drillOk}`, with more detail beside them that its checker ignores (`refusal` by rule, per-Guard proof, webhook addresses). The panel says "Not confirmed yet" when `updatedAt` is old, so the deployer's loop moves it every minute **only if the runtime and all three Guards answer and have run their tripwires**; one that does not answer is left alone, and a Guard whose tripwires failed is written at once as fewer limits proven than there are. `deploy.state` is `in-progress` while a deploy runs, `applied` after the running Guards agreed with what was checked, `failed` with the rule names in `message` (500 characters at most, the panel's limit) when it was refused.
- **`requests/<shop>.stop.json`.** The deployer reads it, sets the kill switch on every Guard of the shop (and stops that shop's agent at the model Guard), writes `stopped {at, requestId}` into the status, and only then removes the file; if a Guard cannot be reached the request stays and is tried again. A stop for a shop with no Guards yet is recorded and applied at its first deploy. A deploy never undoes a stop.
- **`exports/<shop>/{record,bookings}.json`**, every quarter of an hour, from one short-lived container that reads each runtime database in a single read transaction. The files leave the shop's volume, so a booking's `customer` and a record entry's `conversation` become a keyed fingerprint of themselves (see "Fingerprints nobody outside the shop can work back"; the report's own digest of an entry already leaves the conversation out, so nothing in a digest changes). The shapes are what `scripts/client-report.ts` reads.
- **`shops/<shop>/pins.json`** (the ids the panel's checks confirmed) are the exact allowlists when present, in the Guards **and** in the runtime's configuration, so they cannot disagree; a runtime.json that names another id is told so. The Razorpay key handed in must be the key id (and mode) the check confirmed.
- **The read-only routes.** WhatsApp `GET /{version}/{phone_number_id}` (`read_number`) and Calendar `GET /calendar/v3/calendars/{calendarId}` (`get_calendar`) are in the specs with the same exact-id rule as the routes beside them. Each Guard has an agent `panel-<shop>` limited (in `guard.toml`, per-agent `operations`) to the reads the panel's checks make: `list_links` at Razorpay, `read_number` at WhatsApp, `get_calendar` and `list` at Calendar. `list` is there because the panel's calendar check asks for one event (`maxResults=1`): the access role (can it write?) only comes back with an events list. That lets the panel's agent read the events of that one calendar (Guard's exact-id rule confines it to the shop's own) which is more than "the calendar exists"; the panel's checker keeps only the role and drops the body. **One token, not one per Guard:** the panel reads a single token file (`golive.ts`) and presents it to every Guard, so `secrets/panel/guard_agent_token` is mounted only into the panel and each Guard keeps its hash under `panel-<shop>`. A leaked token is therefore valid at every shop's Guards for these reads and nothing else; per-Guard tokens would need the panel to read a template (a one-line change there) and are listed in Deferred.md.
- **Keys the panel loads.** `data_key` is 32 random bytes as hex (`vault.ts`); `signing_key` is an Ed25519 private key in PEM, 0600 (`modules/report/sign.ts`, `loadPrivateKey`). Both were checked by starting main's real panel on them (below).
- **`check` and `panel invite`.** `check` runs `services/connection-check.ts` inside the panel container; it calls the panel's own `golive.run(shop)` (the same checks as its button, so the panel's page shows the result and, when all confirm, `pins.json` is written and the next apply re-pins the Guards; a check with nothing to check with, such as WhatsApp for a shop that has no business number in the panel, is "NOT RUN" and not a failure: found by running the panel without that data), instead of building the panel's `ConnectionTargets` a second time from files the deployer should not read (the business number and the Razorpay key id are in the panel's own data). `panel invite --role builder|partner` runs the panel's `invite` in its container.
- **The panel's place on the network.** A network of its own, `panel` (internal), holds the panel and, for each shop's three Guards, their forwarder at a second address, with the Guard's name as an alias. The forwarder still listens for the admin port on the admin address alone, so on the panel's network only the Guard's agent port (and its health port) answers. The panel is also on `front` for Caddy. It is not on `admin`, `egress` or any shop network, and it is mounted with the folders in the README's list and nothing else. **Not done:** the panel's optional look at a runtime's `/status` (Deferred.md).
- **Who the panel runs as.** The panel insists that its key files are 0600 and that the files it writes into the inbox are 0600 and its own, so a different user could not read them. The deployer's user therefore runs the panel container (`user: uid:gid`), and so the deployer can read what the panel wrote. A root deployer cannot give a root-run container's files to anyone sensibly; it runs the panel as 1000 and hands the panel's folders and keys to 1000.
- **The server-wide Google key** (`geometer google-key`) is used for a shop that hands in none: its token is made for that shop's Calendar Guard like any other. The panel is given the key's address (`client_email`, not a secret) so it can say who to share a calendar with.
- **A shop name whose inbox already holds files** is refused by `shop add`: that setup was started by someone else.
- **The panel is served at the root** of the domain (it builds absolute paths, and its public address has no path), with `/c/*` going to the inbox; without a panel the root answers 404.
- **Main's real panel, started on the deployer's files (4 November, no Docker).** A scratch tree made from `git merge-tree` of main and this branch; a deploy against the fake machine made the keys and token; main's `bundle/panel/main.ts` was then started with the environment the compose file sets (a stand-in Guard on a local port in place of `http://g-{shop}-{kind}:8080`). Results: `/healthz` answers 200 (so `signing_key` loads as an Ed25519 key and `data_key` as 32 bytes of hex); `main.ts invite --role builder` prints a link; `services/connection-check.ts` confirmed WhatsApp, Razorpay and Calendar and wrote a `pins.json` in the panel's own shape; the stand-in saw the one token on every request (`Authorization: Bearer`) and the Calendar calls were `GET .../calendars/{id}` then `GET .../events?maxResults=1`; with a wrong token all three came back `not_allowed`. `docker compose config -q` accepted the generated file with the panel service in it (no container started). The real Guard binary then compiled and verified (`verify-bundle`, all tripwires) the three Guards of a panel-enabled shop **with the new `panel-<shop>` agent blocks in their `guard.toml`** (`operations = ["list_links"]`, `["read_number"]`, `["get_calendar", "list"]`, one shared token hash): 4 of 4, 2 of 2 and 6 of 6 limits proven. **Which commit the full proof covers:** the 148 checks ran on the earlier shape (one token per Guard, a single calendar read, a hex `signing_key`); the checks added since for the calendar `list` and for another shop's calendar being refused are in `test/proof/run.ts` but have not been run. What covers the changes after it: the unit tests, the native panel run, the real-binary verify above and `compose config -q`. **What this did not do: the panel was never run in a container, behind Caddy, on the `panel` network, read-only and as another user**; the Guards' real answers to its reads were exercised in the proof (with this branch's stand-ins), not with the panel's code.

## Bring your own agent (5 November, B51 first slice)

The builders' headline: an agent built with Claude Code, Lovable, n8n or the builder's own code runs behind the same limits, checks and record as a template. `geometer agent add <name>` puts the bundle's Guards in front of the services the agent calls (Razorpay, WhatsApp, Google Calendar: the ones the templates use), prints the three addresses and the one credential the agent must use in place of the services', and the rest of this section is what that does and does not do. **Geometer never rebuilds or hosts the agent (plan decision 5).** How to use it: [README.md](README.md), "Bring your own agent". What is left out: [Deferred.md](Deferred.md), the section of the same name.

**Where an agent lives.** `agents/<name>/` beside `shops/<name>/`: `agent.json` (which of the three services, the shop's own WhatsApp number id and calendar id, and the caps settings do not carry) and `settings.json`, the templates' own settings file read by the templates' own validator. Not inside `shops/`: the panel's shop list, the shops' exports and backups, the panel's status refresh and the go-live certificate all assume a runtime, and none of them is touched. In `state.json` an agent is under `agents`, not `shops`, and takes its network index from the same pool, so a shop and an agent never share an address and never share a name (container names would collide). `status/<agent>.json` is written in the panel's shape (with `versions.pathway` = `own-agent`) so `geometer status` and anything reading it work.

**One source for the limits.** `agent add` does not write limits. It writes the settings, and `planAgent` (`agent/plan.ts`) calls the functions a shop's plan calls (`razorpaySpec`, `whatsappSpec`, `calendarSpec`, `guardToml`). A test builds a shop and an agent from the same settings and compares the three specs byte for byte; another, run once against `main` with the same input, compared the shop-only output of the generator before and after this work: specs, guard.toml files, the compose file, the Caddyfile and the inbox, relay, refresher and ops configs are byte-identical (16-character digests equal). What changed in shared code, so that this holds: `razorpaySpec` takes the daily refund caps as an optional fifth argument (a shop passes none), guard.toml's listen addresses and file paths are options (the container's are the defaults; a test running the real binary gives its own), and the compose, config and deploy steps take agents as a separate, optional list. The checked deploy's tail (compose up, recreate a Guard whose forwarder was recreated, restart a service whose files changed) moved into `bringUp`, which a shop's deploy and an agent's both call.

**What Guard can and cannot enforce here.** The settings' deposit and refund limit become the deposit bound and the owner's approval threshold on the Razorpay Guard; the caps become counts; the WhatsApp number and the calendar are pinned exactly. Guard has no rule for prices or opening hours, so those two are in the settings (and in the report's policy digest) and **nothing checks them for an agent we did not write**. A template's agent checks them in its own code. The README says so; Deferred.md lists it.

**The network.** The builder's agent is not on our network: it may be a laptop, Lovable's cloud or n8n's. It reaches a Guard through Caddy at `https://<domain>/g/<agent>/<service>/...` (`handle_path` cuts the prefix; the Guard sees the service's own path). The Guards' forwarders join a new internal network, `gate`, with Caddy and no one else; they are **not** put on `front`, so the existing claim that Caddy reaches the inbox, the relay and the panel and the Guards' agent ports are on no network those can reach stays true (the inbox, relay, panel and ops are not on `gate`, and `gate` has no way out). A Guard still reaches its service through `egress`, and the deployer and the relay reach its admin and agent ports on the `admin` network, as for a shop. The Guard's agent port is therefore reachable from the internet through Caddy, and what protects it is the credential (a long random token Guard stores as a hash), the limits, and Guard's own caps. A server that holds only agents has no model Guard in its compose file and needs no model key (the deploy of an agent does not ask for one unless a shop is deployed).

**Credentials.** One token for the builder's agent, the same hash in all three Guards (`secrets/agents/<name>/agent_token`, printed by `agent add`, never in a generated file). Three more are the bundle's own and are never given to the agent: `relay-<name>`, allowed `send` at the WhatsApp Guard; `record-<name>`, allowed `list_links`, `read_link`, `read_payment` and `list_refunds` at the Razorpay Guard and `list` and `get` at the Calendar Guard (it can look, and Guard refuses it a refund: seen in the captured output, "agent record-demo is not authorized for refund"); and the owner's approver `owner-<name>`, whose secret signs the owner's answers. The service's own keys (`razorpay_key`, `whatsapp_token`, the Google key) go in the same inbox names as a shop's and to the same one container each.

**What Guard's own lists give, found by running the real binary** (`test/fixtures/own-agent-facts.json` is a capture, 5 November 2026, production profile, the bundle's specs, the stand-ins behind): `GET /admin/decisions` (newest first, at most 500, no "since") has for each call its id, the agent that made it (`principal.workload`), the operation, `allow`, `deny` or `hold`, whether it was sent, the arguments in typed form (`["int","20000"]`, `["map",{...}]`; a calendar event's title and start are in it), each rule's verdict with its words, and in `reasons` the answer the service gave as words: `dispatched once; the provider answered 200`. `GET /admin/approvals` has each hold's state (`pending`, `approved`, `consumed`, `denied`), the approver who decided it, when, and the decision that used it. `GET /admin/intents` has the refund's state and the service's refund id. Two things the capture showed that were not obvious: a call held again while it waits is the same approval (one hold, however often the agent sends it); and **a refund sent again after it was made is held again under a new approval**, so the owner would be asked a second time. The README tells the builder to stop at HTTP 200, and the example does.

**The record.** `agent/facts.ts` (run inside `ops`, which holds the admin credentials and is on the network where the agent ports answer) reads each Guard's decisions, approvals and intents, then asks the services, through the reading agent, for what they hold: the payment link by the `reference_id` the agent sent, the payment on a paid link, the refunds against a payment, the calendar's events. `agent/record.ts` folds that into the templates' record format (`modules/record/record.ts`), so the report and certificates read it unchanged:

| In the record | From |
|---|---|
| `create_deposit_link`, `confirmed` | an allowed `create_link` whose reference Razorpay's own list shows |
| `record_deposit`, `confirmed` | a payment on that link, from Razorpay's single read of the link (the list shows `payments: []`), at the payment's own time |
| `refund`, `held_for_owner` | a `hold` decision, once for each approval |
| `owner_decision`, `confirmed` (approve or deny) | an approval Guard shows as approved, consumed or denied by the owner's approver. **Never a message**: the owner's reply reaches Guard as a signed notification, and the record reads Guard's state |
| `refund`, `confirmed` | an allowed refund whose amount (and receipt) Razorpay's list of refunds for that payment shows, with Razorpay's refund id |
| `confirm_booking`, `reschedule_booking`, `cancel_booking` | an allowed insert, patch or delete, confirmed by the calendar: an insert by the events around the booked time (a day either side; an event with that title and start), a patch or delete by asking for that event by its id (a patch: it has the new start; a delete: the calendar has none, or only a cancelled one) |
| `send_message`, `confirmed` | an allowed WhatsApp send the service accepted (HTTP 2xx, from Guard's reason). WhatsApp has no read-back; the agent's messages are to the customer and the relay's to the owner |
| `blocked` | any refused call, with Guard's reason; a refund rule becomes the report's `refund-limit`, so "Refunds over your limit" counts it. The other rules' refusals (a wrong amount, another calendar, another number, a payout) are in the record's rows and the report's table by action but not in its "what the limits stopped" counts: that list is the template's nine rules |

A call the service does not show (yet) is `unconfirmed`, never `confirmed`, and a service that could not be asked confirms nothing. Because the record is only ever added to, an unconfirmed entry is written only after ten minutes, so a service that is a moment behind does not leave a false one; when the service shows it later a confirmed entry for the same thing follows (the report marks the earlier one "settled later"). A provider answer that is not 2xx is `failed`. The reading agent's own reads and the calls of anyone but the builder's agent and the relay are not the agent's record.

**Guard's list of recent decisions is the weak point, and the record says so.** `GET /admin/decisions` gives the 500 most recent, newest first, with no "since", and every question the record asks a service through a Guard is itself a decision in that list. So the record (a) reads every five minutes, (b) does not ask the services about what it has settled (the deployer passes `ops agent-facts` the decisions whose entry is final and the references whose deposit is in; a link nobody has paid for in a day and a half is let go), and (c) remembers the time of the newest decision it has read at each Guard. If a pass finds the list full and its oldest entry newer than that, calls fell out of the list unread: the record gets an entry (`record_gap`, `unconfirmed`, so the report lists it among what could not be confirmed) and `agent record` and the deployer's log say so. It cannot get those calls back from the admin API; Deferred.md has the way out. A customer's number is never kept: the record holds a keyed fingerprint of it, like the exports of a shop, and a reference the builder's agent chose that looks like a phone number (a receipt, a `reference_id`) is fingerprinted too, under the agent's label key (a key derived from its own, which ops and the deployer both hold), the same way everywhere, so the report still joins the link, the deposit, the hold and the refund. Unlike a shop's record, these labels are in the entry's `booking` and `refs`, so they are chained: a label made before B69 stays as it was. The deployer keeps it in `state/records/<agent>.json` (0600) and exports `exports/<agent>/record.json` and `bookings.json` (what is waiting for the owner now) every five minutes, so the report reads it the way it reads a shop's. `geometer agent report` runs the templates' own report and certificate code on it; the one change to that code is an optional `pathway` on the report's input (two lines), so the page and the certificate say the agent is `own-agent` and not the bookings template. With the go-live certificate of the crash test (below) the report says what the go-live checks ran on; without one it lists the go-live checks as not given, as a template's does before its checks have run.

**The owner's approval without a runtime.** The relay is the templates' own (`templates/commerce/bookings/approvals/relay.ts`, unchanged). It asked its runtime for the booking behind a held refund; for an agent we did not write, `agent/relay-context.ts` answers instead. What the owner is asked to approve (the payment and the amount) is Guard's held call, as before. Who paid is the `contact` on Razorpay's own record of that payment and when is its `created_at`, read through the reading agent; the "service" is the payment itself. So the owner reads: `Approval needed: refund ₹200 for +919800000000 (payment pay_2, Thu 5 Nov, 6:00 pm). Reply "approve K7M2QX" or "deny K7M2QX" within 24 hours.` The only thing the agent's own say-so is used for is the `receipt` on the refund, which finds the held call; a payment Razorpay has no record of means nobody is asked and the builder is told. The owner's "approve" never reaches the agent: it sends the identical call again and Guard releases it. The templates' wording "...and they will be told" after an approval is true only if the builder's agent tells the customer (Deferred.md).

**The inbox for an agent.** `agent/inbox.ts`: WhatsApp's webhooks come to `/c/<agent>/webhooks/whatsapp`. The signature (or the secret address, for a provider that does not sign) is checked over the raw bytes before anything is read; a body that names another number is dropped; the owner's messages go to the relay with the relay's own token; the whole webhook then goes on, byte for byte and with Meta's signature header, to `--forward-whatsapp-to` if the builder gave one, so the agent can check it again and read it as it always did. If the relay or the agent does not take it the answer is 503 and the provider sends it again (the relay drops a message id it has seen). There is no Razorpay route: the agent takes its own payment webhooks.

**The heartbeat and the alerts.** In `ops.ts` only (`heartbeat.ts` is untouched): an agent is one more entry in the heartbeat, with `pathway` = `own-agent`. It has no runtime, so `up` means every Guard answers, `ready` that every Guard is ready, and `since_last.steps` is the calls its Guards have decided on (each Guard's own count, so it only grows; it includes the reading agent's reads and the relay's sends). `errors` is 0, `tasks` are 0 and `bookings` is empty: the status Guard gives is a count of decisions, not of the service's failures. The fleet alert for a Guard that does not answer says "runtime" because it reads `runtime.up`; it means the agent's Guards. A held refund counts as a held call on the Razorpay Guard. **Billing:** fleet sees an agent as one more entry in the heartbeat (`pathway` = `own-agent`, with an `up` and `ready` like a shop's), so its month report and the live-day rule (B13) may count it as a live shop; whether an agent we did not write is invoiced like a shop is the billing change's to decide (Deferred.md). The relay's own alerts to the builder (a request that could not be made, a hold it will not ask about) work as for a template.

**What the tests show.** `test/agent.test.ts` (flags and refusals; the same specs as a template, byte for byte; caps; names used once; the compose file and its networks; deploy on the fake machine: the credential as a hash in all three Guards, the reading agent limited to reads, no service key in the agent's folder or any generated file; a shop's deploy keeping the agent's Guards; a broken tripwire or a missing key refusing with nothing started; the deployer's loop and the record job), `test/agent-record.test.ts` (the fold on the real captured Guard output, append-only, grace and late confirmation, a failed provider answer, the report), `test/agent-services.test.ts` (configs, the heartbeat against fleet's own validator, stop, the relay's look at the payment, the inbox), `cli.test.ts` (the commands) and `test/own-agent.test.ts`. The last is the one that matters: the example agent (`examples/own-agent/agent.js`, plain Node) takes a booking and a deposit through the **real `geo-guard`** (production profile, the generated specs and guard.toml, compiled by the binary) in front of the stand-ins; its refund above the limit is held (HTTP 202); the relay asks the owner once, through the WhatsApp Guard, with who paid and when from Razorpay's record; a reply from another number and a webhook signed with the wrong secret approve nothing; the owner's signed reply, through the inbox and the relay, approves it; the agent's identical call goes through; **one refund** is at the stand-in (and one approval, consumed); the inbox passed every accepted webhook on to the agent with Meta's signature unchanged; the record has the link, the deposit, the booking, the hold, the owner's decision, the refund (with the stand-in's refund id) and the refused refund above one deposit, and no phone number; and the monthly report counts a deposit of ₹200, a refund of ₹200 that the owner approved (asked 1, approved 1), one booking, and one refund the limit stopped. It is skipped, saying why, when the built binary (`monorepo/target/debug/geo-guard`, or `GEO_GUARD_BIN`) is not on the computer.

## Update every client at once (5 November, B53)

The builders' page says: "Update every client at once, each checked on its own settings first." `geometer update` is that sentence. It reuses what B20 already had by hand, and adds the check and the record.

**The pin is what was already there.** A client's version is `shops/<shop>/pathway.lock` (`bookings@0.1.0`); the pins before it are the shop's `lockHistory` in `state/state.json`, which the checked deploy has always pushed to when a lock changed. `pathwayDirFor` finds the code of a pinned version (this checkout's `templates/<domain>/<name>`, or `<server>/templates/<domain>/<name>@x.y.z/` beside the server, or the older `<server>/pathways/<name>@x.y.z/`). Nothing new was invented for pins. What is new in the state file is `update` and `rollback`, the last run of each, step by step (`lib/state.ts`, `Step` and `Run`).

**The check is the template's own.** For each client, `update` starts `<that version's folder>/scripts/hand-check.ts --settings <the client's settings.json>` through the Runner (`handcheck.ts`), once at the version the client runs and once at the new one, and reads the lines it prints: "Held N of M", one line per situation with a tick or a cross, and under a failed one the first check that failed. Each version brings its own situations, so a version that adds, drops or renames one shows up in the comparison. The reading is held to the real script's output by a test that runs the real hand check, and the stand-in used in the other tests prints the same lines.

**What holds a client back.** (1) A situation that held at the version it runs and fails at the new one. (2) A situation that held and is not in the new version's answer ("no longer checked", said apart from "now failing", because it is not the same thing to a builder). (3) A situation that fails at the new version and was not failing before: a new one, or one that was not run on these settings before. A situation that failed in both is not counted: the client is no worse off, and holding it back would make one old failure stop every update. Other reasons, each in words: the new version is not on this server, the hand check cannot run at either version, the folder cannot be read, or the pin and what runs differ because an earlier change did not finish.

**Moving a client is the checked deploy.** The new pin is written and `deploy(ctx, shop)` runs, the same code as `geometer deploy`: the same compile and tripwire checks on the shop's Guards, then `docker compose up` for what changed, then the running Guards asked ("12 of 12 limits proven to bite"). Nothing was added to restarts: a client's runtime is recreated because its compose entry changed (its template folder is mounted from the new version), as for any deploy, and it is built to be restarted (events saved before they are answered, steps saved whole; the template's tests stop it between a payment link and its payment and finish the booking once after the restart, and the Docker proof restarts it, and its Guard, with a refund held for the owner).

**Written down before it is done.** A client's step is saved as "moving", with the pin it had and the pin it will have and its lock history, before the pin file is touched; it becomes "moved" or "held-back" when the deploy has gone through. So a run that stops anywhere (the machine, a cut-off deploy) leaves a record that says exactly which client was half-way. The same command again (the same `--to` and `--shops`) finishes that one and starts none of the finished ones again: no second hand check, no second deploy. The state file is read fresh before each write and never held across a deploy, because the deploy reads and writes the same file. A refused deploy puts that client's pin and history back, starts its earlier version again if the refused one had been brought up, and stops the rollout: at most one client is affected, and the next run carries on with those not started.

**Rollback** takes `lockHistory`'s last entry, writes it as the pin and deploys, through the same code. It takes that entry off the history (the deploy pushes the version it leaves, and that push is removed again), so rolling back twice goes back twice, and a rollback is never a way to go forward without a check. With no names it takes the clients the last update left on the version it names and that have an earlier pin: the ones it moved, and the ones a repeat of it found already there (running `update` again, to look at a held-back client, would otherwise empty the list). It is refused, before anything is touched, when the version that runs wrote its saved data in a layout the older one does not know: the runtime refuses such data on start (`store.ts`, `SCHEMA_VERSION`), so the rollback would quietly stop the client. An `update` to an older version is held back by the same test, and an `update` with no `--to` never takes a client to a version older than the one it runs (the checkout is usually the older of the two when a new version was put beside the server). The layout is asked of each version by importing its `server/store.ts` in a child process, and the update says in a note when it moves a client across a change, so nobody finds out at rollback.

**The panel no longer moves a client.** The panel's setup save used to write `pathway.lock` as the version the panel itself builds, even when editing a shop that already had a pin. Any edit of a held-back client's settings in the panel would have moved it to the new version, and the next `apply` would have deployed it unchecked. An edit now keeps the pin the shop has (`bundle/panel/server.ts`, `shops.ts`: `lock(id)`, and `checkFolder` accepts any version for a pin that already exists; the deployer's own `pathway-pin` rule still refuses a version this server does not have). A test in the panel's setup tests covers it.

**What the tests show.** `test/update.test.ts` (14 tests: 10 answer the hand check with a stand-in that prints the real lines, 3 run the real hand check, and 1 only reads text): three clients where one fails a situation at the new version, so two move and one is held back with the situation and the reason; a situation that held and is no longer run; a version missing from the server, a hand check that does not start, and a pin that differs from what runs; a bare `update` that does not take a client back to an older version, and an explicit move to an older one that is held back by the saved-data layout; a dry run that leaves every file under the server folder byte for byte as it was and asks docker nothing; a run cut off while a client's deploy is bringing services up, then run again (nobody checked twice, one deploy); a refused deploy that puts the pin back and stops; an agent with no command to start it skipped with a note (the agents that can be crash-tested are in update-agent.test.ts); rollback with no name, by name, and that it cannot go forward; rollback refused across a saved-data layout change; two clients moved with the real hand check at both versions; and a real fault (a copy of the template with one line changed so a 48-hour cancellation window is miscounted) that the real hand check finds only for the client with that window, so that client is held back and the other moves.

**What was not run.** Docker: every deploy in these tests is against the fake machine, as the other deployer tests are; no real Guard started, so "12 of 12 limits proven to bite" in the output is the fake Guard's. No client was updated with a live booking in the middle, and `update` does not wait for a quiet moment. The real-Docker proof (`test/proof/run.ts`) was not run for this change. `update` and a running `apply --watch` can deploy the same client at once (Deferred.md).

## A second template (5 November, B16: Fees)

Everything in the bundle used to import Bookings: its settings check, its Razorpay limits, its runtime check, its inbox and relay, its hand check and papers. A Fees shop needs the same pipeline with different pieces and one Guard fewer, so the bundle now asks `lib/kinds.ts` (`kindFor(lock.pathway)`) instead. The choices:

- **One registry, not `if fees` in each file.** A template is an entry: its Guards (`razorpay`, `whatsapp`, and `calendar` only for Bookings), `validateSettings`, `validateRuntimeConfig`, `razorpaySpec`, and the hand-check papers the panel will use. `hasOwn` guards the lookup, because a lock may say `constructor@0.1.0`.
- **The lock decides, and a missing lock changes nothing.** `readShop` reads the lock first (quietly) to know which settings check to use; a missing or unreadable lock is still said where it always was, and until it is fixed the settings are judged as Bookings' have always been, so no existing message moves. A lock for a template the bundle does not run is said by name, with the ones it does.
- **No calendar means none of its parts.** `planShop` builds no calendar spec and writes no `services.calendar`; `ensureCredentials` makes no calendar credential, no admin token for the refresher and no folder for a calendar Guard; `missingSecrets` asks for no Google key (even when the server holds one for every other shop); `webhooksFor` says `hasGoogle: false`, so the refresher's config has nothing for the shop; the ops config lists the Guards the shop has. A `services.calendar` left in a Fees shop's panel runtime.json is left out of the generated config and a note says so (the runtime would refuse it as an unknown setting and not start).
- **The generated config is judged by the template's own check, and a refusal is not silent.** `withReport` and `withFleetAi` add their keys only if the pinned version's validator accepts the result; if a Fees runtime refused `services.calendar`, both would quietly skip their keys. `test/fees-shop.test.ts` runs Fees' validator on the generated config and asserts `report` is there.
- **The relay and the heartbeat.** `relay.json` carries the template (`fees`; left out for Bookings, as it was), and `services/relay.ts` picks the voice. A Fees runtime's status calls its cases `fees`; the fleet's contract has one map (`runtime.bookings`), and the heartbeat sends whichever the runtime has.
- **The export hides a child's name.** `backup/export.ts` writes `dues.json` for a Fees centre: the parent's number and the student's name are fingerprinted with the centre's key on every fee, and the student's name inside a record note ("the fee for Rohan Mehta, ...") is too, because a child's name should not leave the centre's data volume for a report that only counts. Only a name spelled exactly as the centre's list has it is replaced.
- **The panel asks the shop's lock, not the template folder, which template a shop is.** `panel/shops.ts` reads `pathway.lock`, and `settings()`, `checkFolder()` and the go-live checks (`panel/golive.ts`) use that template's entry in `lib/kinds.ts`. The Fees pages are in their own file (`panel/views-fees.ts`) and the form logic in `panel/fees.ts`, so `views.ts` stays Bookings' and gets only a few dispatch lines. Two details a later template will meet: the settings the check hands back are in another shape from the ones a builder writes (a Fees student's `batch` becomes `batchId`), so the panel writes the shape it checked from (`raw`), not the checked one; and a Fees runtime.json that names a calendar is refused, so the panel's stand-in Guard addresses are added only for the services the template has.
- **`shop add --template <id>`** starts a shop from the template's example settings (or `--settings <file>`, checked first), pins it to the version in this checkout and writes a `runtime.json` naming the WhatsApp number (and the calendar, for a template that has one). Nothing is made if the settings fail.

## The licence lease and wind-down (8 November: the bundle's half of B13), and the heartbeat's three counts

Fleet's half is merged in the monorepo (ADR-0059; the contract is `apps/fleet/README.md`, "What the bundle does with the lease"). This is the other half. Guard's own check of the same lease came after it (8 November, monorepo ADR-0062): see "Guard checks the lease too" below.

**Who does what, and why that way.** Three parts can each write only one place, and the design follows that:

| Part | Writes | Does |
|---|---|---|
| ops (container) | `fleet/lease` | On a 200, keeps the answer's `lease` as it came (only something shaped like `gl1.…`, at most 64 KB), and fleet's unsigned `shops[id].licence` in `fleet/<shop>.json` for the panel. It trusts nothing in either. |
| the deployer (host) | `state/licence/`, `generated/shops/<shop>/client/licence.json`, `status/<shop>.json` | On every loop (`runLicence` in `apply.ts`) and every deploy (`writeServer`): checks the inbox token with the key pinned in `geometer.json` (`licence.keys`, from `init --licence-key`), for this server's own id, newer than the kept one (`newerThan`: a higher serial and an issue time no earlier, judged against `seen.json` so a deleted lease file lets nothing older back in, while the same lease again puts a lost file back). Then hands each deployed shop its entry and writes the state the panel shows. |
| the runtime (container, `/client` read-only) | its own record | Reads `licence.json` by its modified time (`licenceReader`, like the `ai` switch) and works the state out **with its own clock** at every call (`effectiveState` at `serverNow`), so a lease that runs out while the deployer is not running still takes effect, and a clock set back is judged no earlier than the newest `issued_at` taken. |

The licence never goes through `runtime.json` or the shop's desired state: a change there would redeploy the shop (every Guard checked again, the runtime restarted) each time a lease arrived, and an older pinned template's validator refuses a key it does not know. `licence.json` is a file of its own in the client folder; nothing restarts for it.

**The port** (`modules/licence/`): `rules.ts` is fleet's `newerThan`, `serverNow`, `effectiveState`, `takesNewWork`, `allowsRecovery` and the version-1 shape, with no crypto, because the agents import it and the browser demo has no `node:crypto`; `token.ts` is `checkToken` with `node:crypto` Ed25519, the same checks in the same order. `bundle/test/fixtures/licence-vectors.json` is fleet's file, copied; a test fails if it differs from fleet's when the monorepo is at hand, and every good token, every refusal (with its reason), every replay case and every state case (the server clock set back among them) gives fleet's answer.

**A shop the lease does not list, and a server with no lease, are not restricted.** With no key pinned, no lease is kept at all, and no `licence.json` is written.

**What the runtime does** (both templates; the words are in each template's `templates.ts`, four languages):

- **Wind-down**: no new work. Bookings: a request to book (or a greeting, which would offer the menu) gets "Online booking is paused for now. Please contact <shop> directly.", a `new_work` entry `blocked` with the decision `subscription_suspended` (Guard's reason, so the two read the same later), and no draft is kept, so nothing is a promise. A request that was waiting for "yes" is cleared the same way. Fees: no new fee link (`currentLink` refuses with the same decision), no month's fees opened, no late fee, and reminders that fall due are passed over (never sent later). Refunds owed, cancellations, reschedules of existing bookings, reminders of existing bookings, recovery steps and payments from links sent earlier go on: a deposit paid on a link sent before the wind-down still books.
- **Final stop**: as the wind-down, and on the clock's beat the open payment links are closed at Razorpay through Guard, once for each `paid_through` (`cancel_deposit_link` / `cancel_fee_link` with `refs.licence`; a UPI shop has none); after that every message is blocked by a gate in `say` and recorded. The monthly report is not sent. Payments already made are still recorded and refunds still go through Guard. **Nothing is deleted, and nothing happens to any key:** Guard's Razorpay and WhatsApp secret files are not removed, moved or changed at the final stop, so the shop's own accounts and keys stay the shop's and refunds owed and payments from earlier links still pass through Guard. The only thing the final stop does besides blocking messages is cancel the open payment links.
- **Back in order**: one `licence` record line says so; nothing from the wind-down is replayed.
- One `licence` record line at each change (wind-down, stop, back), so the record keeps the suspension.

**The owner's notice** (`modules/licence/notice.ts`, run by the runtime core on the clock's beat like the monthly report): one plain WhatsApp notice for each `paid_through`, in the owner's language, naming the partner (the shop's `preparedBy`), never about money. The record is the memory: a claim, a save, the send, the ending (a claim with no ending is closed as "may have gone" and not sent again; a refusal is tried again an hour later, three tries). Outside the owner's window it goes as a utility template: `owner_service_paused` / `owner_service_stopped` (Bookings) and `owner_fee_service_paused` / `owner_fee_service_stopped` (Fees), in the generated `whatsapp-templates.json`. The stop's notice (9 Nov, the owner's decision) says, plainly and without money or blame, that online booking (or fee collection, or ordering) has stopped because the service from the partner or builder (named) has ended, how many bookings (or fees, or orders) are still open, and that the owner can write to hello@geometer.dev and Geometer will connect them with another local partner. It offers no copy or export of the records: the 90-day export goes only to the builder or partner, through the panel or `geometer export`, and nothing is sent to the owner automatically. A wind-down caused by an expired lease sends the notice too (the lease's own `notice` is then null): the owner should hear why bookings paused either way. Fleet's README proposed keeping this in `state/licence/notices.json`; the runtime cannot write there, and the record is exported and signed, so it is kept there.

**Reschedules in the wind-down** go on: moving an existing booking makes no new booking or link. **"Stop sending" in the final stop** covers every message the agent sends, except the stop's own notice; refunds still move, and the agent's confirmations of them are held back and recorded. The approvals relay is a service of its own and still asks the owner about a refund Guard holds, because a refund owed must still go through.

**The monthly report** never counts a licence refusal as one of the shop's limits that held (a rule it does not list is left out of "what the limits stopped"), and a month whose only entries are the licence's own lines (its state line, the owner's notice) is a quiet month with no report. In the final stop no report is sent.

**The panel** (`panel/licence.ts`): the shop page shows the state the server worked out from the signed lease (an offline expiry can differ from fleet's last word), in the partner's language, with the dates from fleet's unsigned copy (fleet's own local days; otherwise the signed times as days in India), fleet's renew link (https only) when something is owed, and "not refreshed since <day>" once the kept lease is more than 2 days old. The shops list shows the state when it is not in order. A shop the lease does not list shows nothing. Fleet's `licence_*` warn codes are not repeated in the plan's warnings: this block says them.

**The heartbeat's three counts** (fleet ADR-0059 decision 12; optional fields, so fleet must be deployed first):

- `since_last.reports_sent`: the record's report message read back (`send_message` with `refs.report`, `confirmed`; not the claim, a failed try or the certificate document after it), counted by the 15-minute export with the cost meter's counts and sent as a difference against `fleet/usage-baseline.json`.
- `usage.replies_by_language`: messages to customers read back, by the entry's language; a UPI QR picture beside the words is not a second reply. Inside `usage`, never alone in it.
- `open_obligations`: `countsByKind` from the same exported record and cases the to-do list reads, worked out by the export job and kept in `status/<shop>.json` (`obligations`), sent on every heartbeat, `{}` when none is open. Kind ids fleet would refuse are dropped, not the heartbeat.

A baseline written before these counts keeps the cost meter's nine and starts the new ones at the shop's current totals (`EXTRA_FIELDS`, optional on both sides), so an upgrade drops nothing and replays no report or reply. **So a shop that sent a report before this bundle gets fleet's First report sent badge with its next report**, dated then, not today: the honest date, chosen over replaying history.

**Tests**: `test/licence.test.ts` (the port on the vectors, keeping the lease, replay, a lost lease file, extensions, the clock set back), `test/heartbeat-counts.test.ts` (the three counts, the baseline upgrade, fleet's own validator, ops keeping the token and the unsigned entry), each template's `test/licence.test.ts` (the wind-down, a deposit from an earlier link booking, back to normal with nothing replayed, the stop's link closing, the owner's notices once each through the runtime, the reader), and the panel's `test/licence.test.ts` (the view, the page and the list in Hindi, another partner seeing nothing).

## Guard checks the lease too (8 November: D83, the bundle's side of monorepo ADR-0062)

Guard now reads fleet's lease itself (monorepo ADR-0062): a `[licence]` table in `guard.toml`, the public keys built into its binary, and a 402 `subscription_suspended` for new work in the wind-down. The monorepo's Deferred D83 lists the change this repository makes. This is it.

**The block** (`generate/guards.ts`, `TomlOptions.licence`), last in each per-shop Guard's file:

| Setting | Value | Why |
|---|---|---|
| `lease_file`, `seen_file`, `extensions_dir` | under `/run/geometer/licence` | the server's `state/licence/`, which the deployer already keeps |
| `deployment` | the **server's** id (`geometer.json` `id`) | the id fleet's lease names; not the Guard's own name, which stays the top-level `deployment` |
| `shop` | the shop's id, or the id of an agent someone else wrote | a lease lists both; this closes "an agent someone else wrote is not restricted by the lease" |
| `wind_down_refuses` | `["create_link", "insert"]` | a new payment link, a new calendar event |
| `stopped_refuses` | `["create_link", "insert", "send"]` | and a message, in the final stop |
| `owner_numbers` | the owner's WhatsApp number from the settings, and the numbers of the shop's other people who approve refunds (B37, `approvers`) | in the final stop, two kinds of message must still go: the owner's one notice, and the approvals relay's question about a refund Guard holds. The relay asks the shop's other people too, and asks only them when the owner asked for the refund. Without their numbers such a refund could never be approved, and money owed must always go through. Only a number Guard reads as one (6 to 15 digits, `+`, spaces, dashes and brackets) is written, because Guard refuses the whole file for one it cannot read |
| `recipient_field` | `"to"` | Guard's own default, written out so the file says which field the owner's exception reads. The monorepo's templates leave it out; `test/drift.test.ts` knows it as the bundle's own addition |

The model Guard never gets it: it serves every shop on the server.

**When it is written.** Only when `geometer.json` pins `licence.keys` **and** the Guard image reads the table. An older image ignores an unknown table (its top-level settings were not read strictly), so a block written for it would do nothing while reading as if it did. The deployer asks the image itself, once per deploy (`GuardTool.readsLicence`, `generate/verify.ts`). It runs `verify-bundle --config` on a small file whose `[licence]` names a refund, and points at a bundle that does not exist. A Guard that reads the table refuses the file for the refund, naming `[licence]`, before it looks for the bundle. An older one stops at the missing bundle. When the image is older, the deploy says so in a note, and only the runtime refuses new work.

**After the start.** `proveRunning` reads each running per-shop Guard's own account (`licence` in `/admin/status`). It must name this server and this shop, and the key ids built into its binary must be exactly the ids of the keys `geometer.json` pins (`kidOf`). A Guard built with other keys would take no lease fleet signs, and so would restrict nothing, while the panel shows the shop wound down. A mismatch fails the deploy and names the Guard, but **does not pull the kill switch**, because the kill switch would stop refunds owed as well.

**The folder** (`generate/compose.ts`): `Dirs.licence` is `state/licence/`. It is mounted read-only at `/run/geometer/licence` on every per-shop Guard (a shop's, and an agent's someone else wrote), and not on the model Guard. The folder is mounted, not single files, because the deployer replaces the lease and `seen.json` by rename, and a single-file bind mount keeps showing the old file. `writeServer` makes `state/licence/` and `state/licence/extensions/` (0755) before `compose up`, for both deploy paths. Otherwise Docker would make them as root, and the deployer could not write the lease. The files are 0644, so the Guard's user (65532) can read them. Guard reads them again within a second when they change, so a lease never restarts anything.

**The runtime** (`modules/`, and Bookings, Fees and Orders): Guard's 402 is a `GuardSuspendedError`. It is never tried again and is recorded once, as `blocked`, with the licence rule. The template takes it as its own pause. modules/Explanation.md has the detail.

**Where Guard and the runtime differ** (Deferred.md has each): a Fees centre or an Orders shop that takes UPI makes its new work with a WhatsApp message, which Guard holds back only in the final stop. In the wind-down Guard also refuses an `insert` the runtime would allow: a hold taken again after a late payment, or an existing booking whose calendar event went missing.

## Records anyone can check, in the bundle (B28, B35, B36; 8 November 2026)

**Fingerprints nobody outside the shop can work back (B69).** A plain sha256 of a phone number hides nothing: India has about 4 billion mobile numbers, so anyone holding the hash can try them all in minutes, and a class's names can be guessed. Every person's value that leaves a shop's volume is now an HMAC-SHA256 under a key only the shop has (`modules/record/fingerprint.ts`: `c-`/`p-`/`s-`/`b-` and 12 hex digits).

- **The key.** One per shop, 32 random bytes as hex, `secrets/person-keys/<shop>`, mode 0600 (`lib/secrets.ts`). It is made at deploy, or by the next export job for a shop made before B69, so such a shop gets one and nothing crashes. A shop's other secrets are 0644 inside a 0700 `secrets/`, because each container's fixed user must read them; this one is read only by root job containers and the deployer's own user, so it can be 0600.
- **Who gets what.** The export and snapshot jobs mount `secrets/person-keys` read-only; the job file names the file and never holds the key. The panel gets a 0600 copy (`secrets/panel/person-keys/<shop>`, `PANEL_PERSON_KEYS_DIR`), to match a number typed for a statement and the owner's number for a handover. A runtime never holds the key: it gets `record_key`, an HKDF of it for one purpose, in `secrets/rt-<shop>/` (0644 like that folder's other files, because the runtime is uid 1000 whoever runs the deployer) and `RECORD_KEY_FILE`. It uses it for two things that are chained and so cannot be rewritten at export: the digest of an action's inputs (`k-<16 hex>`) and a WhatsApp message id (`m-<12 hex>`), which can carry the sender's number. A live runtime without the key refuses to start; a local run with stand-ins needs none. Ops gets `label_key` the same way for an own agent's references.
- **Backups and restore.** The nightly snapshot carries the key inside its manifest (`backup/snapshot.ts`), so it is encrypted to the owner like the database and costs no extra bucket request; the manifest is already read on a restore. `geometer restore` takes the key out (`restore-snapshot.ts`, `--job`) and puts it back with its copies before the runtime starts (`restorePersonKey`, `lib/secrets.ts`). On a new machine the first deploy will have made another key, which nothing has used: the snapshot's replaces it and the new one is kept beside it as `<shop>.before-restore-<time>`. A snapshot older than the key has none, and the shop keeps the one it has; the restore says so. By hand, `restore-snapshot.ts <folder> --identity ... --out ...` writes it as `person_key`. If the key were ever lost, the live database still holds the numbers, so the next export is consistent under a new key; what stops matching is the older papers and packages, and the older keyed digests in the chain.
- **After a restore the panel's key changes at once, and `exports/` a quarter of an hour later.** `person-form.json` names the key that made the export (`keyIdOf`, which shows nothing of the key), and the panel refuses a statement while they differ, rather than come back empty.
- **Twelve digits stay, with a check.** With a key in place nobody outside can try values, so the length only has to keep two people of one shop apart: 48 bits gives odds of about one in ten million for a few thousand people. The export job checks anyway, and refuses a shop where two different people land on one fingerprint rather than merge them.
- **Each export says which form it uses.** `exports/<shop>/person-form.json` names the form and counts the entries whose digest is keyed and whose message id is fingerprinted; the package's manifest (`personFingerprints`) and README say the same. No marker means an export from before B69, and the manifest and README say that one can be worked back. Older entries are never rewritten, because they are chained.
- **What it does not cover** (the README in every package says so): `settings.json` and the settings history hold the shop's own list of people as written (the owner's and approvers' numbers, a Fees centre's students and parents); free text the shop or a customer wrote is not replaced, apart from a student's name spelled as the list has it.

**The ledger.** The export job (`backup/export.ts`, every quarter of an hour) also writes `exports/<shop>/ledger.json`: the shop's record chained into geometer-verify's ledger format (`modules/record/ledger.ts`), made from the shop's OWN database before anything is hidden. Its entries leave out the number, the note and a page's secret address, so it carries no customer's number, and its head equals the head of the exported `record.json` (`test/fees-shop.test.ts` checks it on a Fees record whose notes name students). The tenant is the shop's id everywhere: the export, the daily fingerprint, `report.tenant` in the generated runtime.json (so the owner's monthly report is anchored), and the panel's papers.

**The daily fingerprint** (`backup/fingerprints.ts`, run by `apply` once a day after the first export, or `geometer fingerprints`): the head of each shop's ledger is appended to `state/fingerprints/<shop>.jsonl` (`modules/record/publish.ts`), never its data. The deployer holds no key, so it asks the panel (`main.ts anchor <shop>`) to sign the checkpoint over the head; the line then carries a geometer-verify anchor. With no panel or no panel key the line holds the head alone and says so. A record that no longer matches what was published is refused, nothing is written, the deployer logs it, and the shop's status carries `fingerprint.ok: false` with the reason. The last fingerprint (day, entry, head) also goes into the shop's status, which is how the panel (which cannot see `state/`) puts it on the identity paper.

**Outside targets** are set in `<server>/fingerprints.json`: a git working copy (its remote is the public place) and OpenTimestamps calendars. Both are off unless that file turns them on AND records the owner's yes (`"yes": { "by": "...", "at": "..." }`); nothing is published otherwise, and the deployer's line says "waiting for the owner's yes". They run through the deployer's runner and a fetch, and were built and tested against a local bare repository and a local calendar only.

**The weekly restore drill** now also chains the restored record and compares its hash at the last published fingerprint's entry with the published head (`backup/drill-check.ts`): a copy that was rewritten, or that is shorter than what was published, fails the drill; both records empty while a fingerprint was published fails too; a shop with no fingerprint yet passes and says none was compared. (Since 9 November the copy is a nightly snapshot, so it is compared with the fingerprints it can hold; see the last section.)

**The shop's export (B38) carries the record anyone can check.** `record/ledger/pack.json` is the evidence pack (signed by the panel's key, with its key log and checkpoint), `record/ledger/anchor.json` the anchor over its head when the package was made, `record/ledger/fingerprints.jsonl` the shop's daily fingerprints (the deployer copies its file beside the exported record, because the panel cannot see `state/`), and `identity.json` the agent's id and its public fields. The manifest and the README list them, and the README says how to run geo-verify. `node bundle/export/check.ts` runs geo-verify on the pack when `GEO_VERIFY_BIN` names it, against the package's anchor and every signed fingerprint line's: a changed record is a problem, no usable anchor is said and is not one.

**`geometer paper dispute|identity|ledger <shop>`** asks the running panel (it holds the signing key, the go-live certificate and the export) for the paper and writes the files here (`backup/papers-cli.ts`), like `geometer export`. A person's statement is made only in the panel, so their number never sits in a command line.

## No continuous copy: the nightly snapshot is the backup (9 November 2026)

**The decision.** The owner's, on 9 November: stop copying each shop's database to a bucket second by second (Litestream), and keep the nightly snapshot. The proof of the same day had measured what the continuous copy cost in bucket operations: about 1,350 to 1,750 a shop an hour under load and 700 to 800 when quiet, roughly 1 million a month, about $5 (₹410) a shop a month at Google Cloud Storage's Class A price as remembered, so about ₹10,000 a month at 25 shops: more than the server itself, and growing with every shop and every busy hour. The owner's reasons: a shop's conversation is on WhatsApp, on the customer's and the owner's phones; what the agent decided is in the hash-chained record with its daily fingerprint; the providers (Razorpay, the calendar) keep their own records of every payment, refund and event; and the infrastructure's cost must not be able to balloon. A day-old copy, opened carefully, is enough. (The B14 numbers above are left as they were measured, with Litestream running.)

**What one night costs, held by a test.** `backup/snapshot.ts` now writes one object per database file: the runtime's database gzipped, each Guard's backup folder as one `.tar.gz`, and a gzipped manifest. File by file, a Guard's backup would have grown by an object every 500 decisions (its evidence ledger's segments) and a busy shop's nightly writes with it. `test/backup-cost.test.ts` counts every HTTP request the S3 client makes against an in-memory bucket (a LIST is paged at 1,000 keys, as S3's is) for 35 nights: an empty shop and one with 3,000 record entries and Guard ledgers of 40 files each make exactly the same requests, night for night. Per shop with G Guards: G + 2 PUTs, 1 LIST, and from the 31st night G + 2 DELETEs. With three Guards that is about 150 writes and 30 lists a month, plus the deletes when the key may make them (free on Google Cloud Storage, as remembered) and the drill's reads, one per object of the newest snapshot each week (about 20 a month). With a create-only key the night is the same writes, one refused LIST and no DELETE; the test holds that too. In bytes: a made-up runtime database of 3,000 similar record entries (1.4 MB after `VACUUM INTO`) gzipped to 76 KB, about 19 times smaller; a real shop's entries differ more from each other, so expect less (not measured on one).

**Compressed, then encrypted.** gzip (`node:zlib`) before age, never after: encrypted bytes do not compress. A snapshot from before the change has plain `.age` objects; the reader tells the two apart by the name (`.tar.gz.age`, `.gz.age`, `.age`), not by gzip's magic bytes, because a Guard's own file can start with them (a test has one). Both kinds restore, by the folder (`restore-snapshot.ts`) and from the bucket; a test writes an old-style snapshot and restores it through the new code.

**The drill checks a snapshot without opening it; a person opens one each month.** The owner's age key is kept off the server by design, so nothing on the server can open a snapshot (the old drill and `restore` read Litestream's plain copy instead). A first version of this change gave the server a second key of its own (a "drill key", a second age recipient) so the drill could open snapshots there; it was taken out the same day, because it would have let whoever takes over the server read 30 days of snapshots, and the owner's rule is that the key stays off the server. What the drill checks instead, on the server, is everything that can be checked without the key: the objects in the bucket are the ones uploaded (sha256 read back), the plain copy passed SQLite's integrity check before it was encrypted, and the copy's record (from its seal) is the start of the live record and matches the published fingerprints. What it cannot show is that a snapshot decrypts and restores: that is the full restore test, `restore-snapshot.ts` with the owner's key on the owner's own machine, monthly, and `restore --identity` on the server when it is needed. Nothing reminds the owner to do the monthly test yet (Deferred.md).

**The drill, against a day-old copy.** Litestream's copy lagged by a second, so the drill allowed 100 entries of lag (`maxLagEntries`); a snapshot is up to a day behind, so that bound is gone. The copy must be the START of the live record: the live entry at the snapshot's last sequence number has the same digest. The fingerprint comparison changed with it: a fingerprint published after the snapshot covers entries the snapshot cannot have, which is normal, so the drill now requires the copy to hold the last fingerprint published BEFORE the snapshot was taken and to match the newest fingerprint it holds. The drill gets the shop's last 60 fingerprint lines, not only the last.

**After a restore, nothing is sent twice.** A restored shop is up to a day behind: a refund sent this afternoon may be "waiting to be sent again" in the restored data. What was already true, and is now tested with the stand-ins (`templates/commerce/bookings/test/restored.test.ts`): every money and calendar write looks first at the provider's own record (`modules/payments/refunds.ts` looks for a refund by its receipt on Razorpay's list before sending; `links.ts` for a link by its reference; Bookings' calendar for the booking's events), and Guard's own store, which `restore` does not touch, refuses a second refund of a payment. A refund waiting to be retried in last night's snapshot, sent today, is found on Razorpay's list and recorded as made; it is not sent again. Two gaps were found and closed:
- **A hold whose time ran out said "nothing was refunded" without looking.** In a restored shop a refund Guard held, which the owner approved and Guard sent after the snapshot, is back as "waiting for the owner"; the relay will not say again what it already said, and when the hold's time ran out the customer was told nothing was refunded and the builder asked to make a new request. `expireGuardHold` now looks at Razorpay's list first and records the refund as made.
- **Ids came back.** Each store's counters (`nextBooking`, `nextDue`, `nextRequest`, `nextOrder`) went back with the restore, so the next booking took an id used after the snapshot, and "look first" then found ANOTHER customer's payment link (same reference, same amount: paid, so the new booking would have been confirmed with someone else's money) or calendar event. `restore` now leaves `restored.json` beside the database; at its next start the runtime (`modules/runtime/restored.ts`, before any step) moves every `count` field of the store on by 100,000 (the codec knows which fields are counters), writes one `restored` entry naming the snapshot (an append: the record is never rewritten), and renames the note. A test in each layer: the module's own with a toy template (and the case of a stop between saving and renaming), and Bookings' with a third customer who would otherwise have been handed the second customer's paid link.

**Still open, said in Deferred.md:** what a shop did after the snapshot is not in its record, so a booking cancelled this afternoon is "confirmed" again (its reminder can go out) and a UPI payment the owner marked this afternoon is unmarked; a restore behind the last daily fingerprint makes every later fingerprint and drill say the record no longer matches what was published; a Guard's own store is not put back by `restore`.

**Compaction of conversation text, never of the record.** What the runtime keeps of a conversation once it is over: a done task's event (the message as written) is emptied the moment the task is done; the record keeps digests of inputs, never message text; the window table keeps a time per number. Two things were kept for ever: a FAILED task keeps its event for a person to look at, and Orders keeps a delivery address as the customer wrote it on the order. Once a day, on its own clock's beat (the runtime is the only writer of its database, so the snapshot container cannot do it), the runtime now empties a failed task's event 30 days after it arrived, and Orders takes the address off an order that is over and whose slot ended 30 days ago, keeping its place on the delivery list (`area`). There is no per-shop retention setting yet, so every shop gets the 30 days. The `record` table is not touched: it is append-only (its triggers refuse an update or a delete), and geo-verify and the daily fingerprints depend on it whole. The other tables were left as they are: `state` (the cases themselves, which the owner's report and the unfinished-work list read), `window` (a time per number) and the store's lists of seen message and event ids, which are ids, not words.

**Checkpointing.** With Litestream gone nothing needs the runtime's WAL left alone. The runtime never turned SQLite's automatic checkpoint off (it never checkpointed by hand, as Litestream asked); the test that checked "no checkpoint by hand" now checks that the automatic checkpoint is on.
