# Explanation: the open panel and the phone setup (B10, B25, B26)

One panel, zero dependencies, pages rendered on the server with no JavaScript. A builder runs it on their own server for their shops (`PANEL_MODE=own`); Geometer runs the same code on its own server for the partners' shops (`hosted`). It reuses the demo's page shell and style (`templates/commerce/bookings/demo/page.css` is read, not copied), the demo's shop form (`personalise.ts`: `settingsFromForm`, `formFromSettings`, `languageOptions`), `validateSettings` as the last gate on every setting, the report's strings for the certificate line and "Show what we did", and `report/` for the go-live certificate and the monthly report.

## What it is, file by file (`bundle/panel/`)

| File | What it does |
|---|---|
| `main.ts` | Starts the panel, or makes an invitation link (`invite --role builder\|partner`). |
| `config.ts` | Everything is an environment variable (`PANEL_SERVER_DIR`, `PANEL_MODE`, `PANEL_PUBLIC_URL`, `PANEL_DATA_KEY_FILE`, `PANEL_SIGNING_KEY_FILE`, `PANEL_CALENDAR_SHARE_ADDRESS`, `PANEL_RUNTIME_URL` and `_TOKEN_FILE` with `{shop}`, `PANEL_GUARD_URL` and `_AGENT_TOKEN_FILE` with `{shop}` and `{kind}`, `PANEL_WEBHOOK_URL`, `PANEL_TRUST_PROXY`, and the cost line's settings). Reads the server's model from `geometer.json`. |
| `contract.ts` | Every file shape shared with the deployer, with a checker for each: `ShopStatus`, the stop request, `owner.json`, `pins.json`, `report.json`, the secret names, `preparedByOf` (the one place "Divya, Sri Sai Digital" or "Divya, local partner" is made, for this panel and the deployer; the company is optional, from the account), and `liveView`, the one function that decides what a shop's life is called. |
| `vault.ts`, `store.ts` | AES-256-GCM (node:crypto), a fresh nonce per write, the record's name as authenticated data, the key in a file named by the environment and refused if it sits inside the panel's folder or is readable by others. Everything the panel keeps (accounts, invitations as hashes, drafts, which secrets arrived, the last checks, and the papers it makes: certificates and monthly reports) is sealed when there is a key; in hosted mode there must be one, and a test sets a shop up, checks it and makes its certificate in hosted mode and then looks at every file under `panel/`. What is not the panel's own data and so is not sealed by it: `shops/<shop>/` (the deployer must read it), `secrets-inbox/` (transient, mode 0600, owned by the panel's user, so the deployer must run as root or as that user) and `requests/`. A changed file, a wrong key or a plain file where a sealed one belongs is an error, never "no accounts". |
| `accounts.ts`, `session.ts`, `ratelimit.ts` | Roles `builder` and `partner`. scrypt passphrases. An account exists only through a one-use invitation link (only a hash of the token is kept; the link is a path the log blanks out). Sessions are signed cookies (HMAC-SHA256, `HttpOnly`, `SameSite=Strict`, `Secure` and `__Host-` over HTTPS) carrying the account's session version, so "sign out everywhere" kills them all. CSRF: a token derived from the cookie in every form, an anonymous signed one for the sign-in and invitation forms, and an Origin check. Login limit: 5 failures per name and address, 20 per address, in a sliding window; once over, even the right passphrase waits. |

| `setup.ts`, `secrets.ts` | The five steps (the business; deposit and cancellation; languages and the owner's number; the shop's accounts; checks) as functions: each step's refusals in the person's language, then `buildSettings`, which is the demo's `settingsFromForm` with the chosen languages, owner and cancellation window on top and `validateSettings` last. The secrets intake writes a file per secret into `secrets-inbox/<shop>/` (0600, atomic) and notes that it arrived; it has no way to read anything back (a test checks the source), validates every box before writing any, and never puts a value in a message. |
| `templates.ts` | Finds templates by `templates/<domain>/<name>/template.json` (accounts the template uses, steps, an example settings file). ## The partner's setup, as the partner sees it (English)

1. **The business.** Shop name; up to four services with name, other names customers use, price (also the lowest the agent agrees to) and minutes; opening time, closing time and the days open.
2. **Deposit and cancellation.** The deposit, and how many hours before a start a customer may cancel and get it back. Under it, each limit as one sentence of what the shop gains: "It can't go below your prices, and it asks you before any refund." "It never books outside your opening hours." "The deposit is ₹200, never more than your cheapest price, and the slot is held 15 minutes while it is paid." "If a customer cancels at least 24 hours before, the deposit goes back. Anything later, or any refund above ₹200, waits for your OK on WhatsApp." "When it says booked, the slot is in your calendar and the deposit is in your account." "Your customers are answered in their language, with the right price and date." "You stay in charge from your phone."
3. **Languages and your number.** The main language of the customers and any others; the owner's language; the owner's own WhatsApp number (the one that approves refunds).
4. **Connect the shop's accounts.** Only the accounts the template uses. WhatsApp: the shop keeps its number and app; type the shop's number, the phone number ID, the access token and the app secret. Calendar: share the calendar with the address shown, choose "Make changes to events", type the calendar's ID (or paste the builder's key file if the server has no shared address). Razorpay: the shop's own account; live or practice; the key ID and secret; the webhook secret.
5. **Checks.** Save and connect (a name taken in the meantime gets a fresh id before any key is written, an inbox file that is already there is never overwritten, and a shop folder that appears before the save is not touched);  the tests on this shop's own prices and hours ("Held N of M situations. 0 failed. J not tested."); the server's update and "N of M limits proven"; the three connection checks; the cost line; then **Ready to go live**, which makes the certificate.

## Connection checks (B26): read-only, pinned

`checkConnections` is exported; the bundle's CLI can call it. It takes base URLs and the ids the shop gave, never a provider key (in production the base URL is the shop's Guard, which holds the keys, and the panel presents only its own Guard credential). It uses the live adapters' `createHttp`, so Guard's answers (refused, held, unavailable, unauthenticated) are told apart in the one place the adapters tell them apart. Every call is a GET (a test records them all and checks the stand-ins' outbox, links and calendar are untouched). A different account is its own error code (`account_mismatch`, `not_found`, `wrong_mode`); what was found is never adopted. What a read cannot show is named in `notChecked`. A reply that contains the credential is thrown away. The ids the providers reported are `pins`; they are written to `pins.json`, and a calendar id is pinned as Google writes it.

| Service | Calls | Docs |
|---|---|---|
| WhatsApp | `GET /v26.0/{phone-number-id}?fields=id,display_phone_number,verified_name`. The id must be the one given and the number must be the shop's own business number (digits compared), not the owner's. | https://developers.facebook.com/docs/whatsapp/cloud-api/reference/phone-numbers/ |
| Razorpay | `GET /v1/payment_links?reference_id=geometer-connection-check`: an empty list when the key is good. Also: a key id with the wrong mode (`rzp_test_` for a live shop) is refused with no call, and a key id different from the one confirmed before is `account_mismatch`. | https://razorpay.com/docs/api/payments/payment-links/fetch-all-standard/ |
| Calendar | `GET /calendar/v3/calendars/{id}` (the id Google reports must be the one given; its name and time zone), then `GET /calendar/v3/calendars/{id}/events?maxResults=1`, whose top-level `accessRole` must be `owner` or `writer`. `writerWithoutPrivateAccess` is refused: the agent writes its booking ids into private properties. | https://developers.google.com/workspace/calendar/api/v3/reference/calendars/get and .../events/list |

**What is not proven for Razorpay, plainly.** Razorpay documents no call that tells an ordinary merchant key which account it belongs to (`GET /v2/accounts/:id` is for Route linked accounts and partner sub-merchants). So the check proves the key works and is in the right mode, and the page says it could not tell whose account it is and tells the person to look at the first test payment link, where the shop's name must appear. The account id arrives in the `account_id` of every signed webhook; pinning that id and refusing events from any other account is the next step (Deferred.md). I did not add an invented endpoint to the stand-ins for this.

Stand-in changes (small, nothing the agent uses changed): `GET /{version}/{phone-number-id}` answers with the number's own details, and `GET /calendar/v3/calendars/{id}` with the calendar's metadata, for the id the stand-in is given (404 for any other, as Google does); `accessRole` of the events list is an option (default `owner`).

## The monthly running-cost line (B26)

Rules from Lorelei's cost calculator: exact arithmetic (a BigInt in micropaise, so ₹0.115 a message is 11,500,000 and nothing is a float; each line is rounded up once, to the next paisa, and the total is the sum of the rounded lines); an unknown price is `unknown`, never ₹0, and a total with an unknown line is called a subtotal and says how many items have no price; "early estimate" until the record has real bookings; and every rate comes from a dated, versioned file. A line is an amount or `unknown`.

**Who pays whom (owner, 4 Nov; plans on 5 Nov; two price lists on 9 Nov, in force from the list of 9 Nov; the builder licence raised on 10 Nov, decision 36, in the list of 11 Nov).** One rule decides Geometer's line, `chargeOf` in `cost.ts`, and the shop page's cost line, its plan block and the health page all use it. On Geometer's server (`PANEL_MODE=hosted`) a partner pays a monthly plan for each live shop, before GST: Basic (no money moves), Business (deposits, refunds, fees, advances) or Operations, each priced in the list in force (`plan.<plan>.fee`). The shop's plan is the one fleet reports, or else Business when its settings take a deposit and Basic when they do not. **The AI model is in the plan**, up to its message allowance and the month's AI cap. Extra messages and WhatsApp are passed on from the partner's balance and are not in this line, and Geometer never handles anyone else's money. On a builder's own server (`PANEL_MODE=own`) the line is **the builder licence** (`licence.builder.fee`), whatever the plan, with the builder's own AI key: one flat amount per live client business. The panel cannot see which shops a builder groups into one business, so it counts each shop as its own (fleet does the same for a shop with no business named); a list without the licence makes the line unknown, never the plan fee and never ₹0. So each line says who pays: the WhatsApp lines are paid by the builder or partner to their own WhatsApp provider; Razorpay's fee is paid by the shop to Razorpay; Geometer's plan is paid by the partner to Geometer, and the builder licence by the builder; the hosting share is the server's.

The lines: WhatsApp messages (Meta's fee: reminders and owner notices as utility templates, replies inside the window free up to 1,000 a month per number), the WhatsApp provider's own fee (unknown until one is named), Razorpay's fee (2% plus 18% GST on the fee per deposit), **Geometer's plan** (one amount read from the price list, `plan.<plan>.fee`, with the plan's name beside it; a list older than the plans has the flat `geometer.fee` instead; it does not change with bookings and has no model line beside it), and a hosting share (a setting; unknown until the bundle measures it). The assumptions (40 bookings a month, 6 replies per booking and 1 owner notice) are on the page.

`prices/2026-11-04.json` (in `bundle/prices/` until 9 Nov, when the repo's one price folder took every list): every rate has its source URL, the day it was read, and a quality (`official`, `official-undated`, `second-hand`, `assumed`, `conflicting`) with a note. The sha256 of each committed price list is pinned in `test/cost.test.ts`, so editing one fails a test; a changed price is a new file with a new date, and the panel uses the newest. That is why the fee is in a new file and not added to `2026-11-03.json`: the 3 Nov list is kept as it was (every rate of it is copied across unchanged, each with the day it was read) and `geometer.fee` was the one new rate, from `https://geometer.dev/pricing`, read 4 Nov (a history of that list; the plans replaced it on 7 Nov). Second-hand: ₹0.115 for utility and service messages (three vendors show three figures). Assumed: ₹90 per US$ and ₹100 per € (the research's round numbers). Conflicting: Razorpay's fee on payment links (2% is used). The model prices stay in the committed lists as history (a list is never edited); the cost line never reads them. There is one table of model prices now, `modules/understanding/rates/<date>.json`, which the runtime and the evaluation script read, and a test here (`cost.test.ts`) fails if any model price in any committed list disagrees with it. A new list carries no model lines. A changed plan price is a new price list, and the cost line follows it with no code change.

For Glow Salon at 40 bookings a month the page shows (nothing else set): WhatsApp messages ₹13.80; provider's fee unknown; Razorpay's fee ₹188.80, paid by the shop; Geometer's plan ₹299.00 (Glow Salon takes a deposit, so Business; this was a flat ₹199.00 until the list of 7 Nov); hosting share unknown; subtotal ₹501.60 with "2 items have no price yet". `cost.ts` went from 280 to 254 lines, with the same arithmetic for the lines that stayed.

## The plan on the shop page (B48, B56; 5 Nov)

When `fleet/<shop>.json` exists (ops writes it from fleet's answer; the panel mounts the folder read-only) the shop page shows a Plan block between the settings and the cost line: the plan's name, the messages a month it includes, the Innovator badge when fleet says the shop's owner is one (a badge, not a price), Geometer's charge (from the price list in force: the plan's fee, or the builder licence on a builder's own server; with the note that a shop counts for a month when it was live on 15 or more days), a notice when the AI is paused and why (button menus instead), and the warnings fleet sent. `plan.ts` makes the facts, `views.ts` says them, and the words are in all four languages (`words*.ts`, `plan.*`; Hindi, Malayalam and Kannada are machine-written, in section 7 of the REVIEW sheets). A missing or unreadable file shows nothing at all, which is different from "no plan": fleet saying `plan: null` shows "No plan is set for this shop yet". The running-cost line reads the same list. A list still marked proposed is skipped by `latestPriceList()`, so a proposal never prices a shop until the owner's decision is put in force as a new list (as the list of 7 Nov did for the 5 Nov proposal). `cost.ts` grew by 25 lines for the `count` rate form, the list `status` and the proposal link.

## Others who approve refunds (B37; 8 Nov)

Step 3 (languages and the owner's number) asks, as an option, for up to two other people who approve refunds: each one's WhatsApp number and language, and the amount above which two people must approve. `setup.ts` checks them in the person's language: a number with the country code, not the owner's, the shop's or another person's, and a whole-rupee amount that needs at least one other person. `approversFromDraft` writes them into the settings as `approvers` (ids `approver-1`, `approver-2`, in the order given); `validateSettings` is still the last word (the amount may not be below the refund limit). Editing a shop shows them again (`approversDraftOf`). A draft saved before has neither field and reads as none. The words are in all four languages, machine-written, and in section 7 of the review sheets. More people, or names other than `approver-<n>`, can be written in the settings file by hand.

## Unfinished work (B31, 7 Nov)

`inbox.ts` + the "To do" tab (`/inbox`) + a section on each shop's page. One list across the shops this person may see (`shops.visibleTo`: a partner sees only the shops they serve, a builder every shop on the server). It is read from `exports/<shop>/record.json` and `bookings.json` (or `dues.json`), which the deployer writes every quarter of an hour and which carry no customer's number, by the kinds in `modules/unfinished` (the registry, its six kinds and how to add one are in `modules/Explanation.md`). Nothing is saved: the page says "Read from the record of <time>", and a shop that has no export yet says that and not "nothing to do". Each item is one plain sentence in the reader's language ("Deposit of ₹200 received, booking b-3 is missing: review recovery") and the time it began; a kind with no words is still listed, under a fallback sentence.

**Buttons.** An item offers only the recovery actions its kind lists. Pressing one `POST`s `/shops/<shop>/recover`; the panel checks that the list itself offers that action for that case right now (anything else is refused and nothing is filed), then writes `requests/<shop>.recover.<id>.json`: a name and an id, never a message, a number or an amount. The deployer (`apply.ts`, `processRecoveryRequests`) carries it to the shop's runtime through `ops`, which holds the runtime's token; the panel never has that token and never reaches the runtime for this. The runtime's agent does it through Guard and the normal limits and writes a `recovery` entry in the record. The list changes after the next export of the record (up to a quarter of an hour), and the page says so.

**The wait limit** for "an approval waiting too long" is `PANEL_APPROVAL_WAIT_HOURS` (default 12; Guard's approvals live 24 hours by default). It is not part of the shop's settings. Asking the owner again starts the wait again.

## Taking a shop's files out (B38, 7 Nov)

`GET /shops/<shop>/export` (a link on the shop's page) and `geometer export <shop>` make the same package from the same builder (`bundle/export/build.ts`): `manifest.json` (every other file with its sha256 and size), `SHA256SUMS` (for `sha256sum -c`), a `README.txt`, `settings.json`, `limits.json` (the policy digest, the refund and payment-link limits in Guard's own shape, how many limits were proven at the last deploy), `history/settings-history.jsonl`, `accounts.json` (which WhatsApp number, calendar and payment mode; names, never keys), `record/record.jsonl` and `record/cases.jsonl` (JSON lines, from the deployer's export of the record: customers' numbers and, for Fees, students' names are the same keyed fingerprints as in the monthly reports; the manifest says which form, and the README what they do not cover), `assignment.json` (only if the shop was ever moved), `status.json`, `reports/<month>/` and `certificates/go-live/` (the signed `.json` and the readable `.html` the panel made, byte for byte). The download is a `.tar.gz` (a ustar writer in `export/tar.ts`; `tar`, 7-Zip and the Finder open it); `geometer export` also unpacks it into a folder.

**What is never in it:** the secrets inbox, the panel's accounts, sessions, vault and data key, the signing key, any token or webhook secret, and the Razorpay key id (half a key). The builder reads only the files it names, and then refuses to hand over anything that looks like a private key, a service-account key, an access token or a Razorpay key (`SECRET_SHAPES`). A test plants known secrets in the places they live and searches every byte of the archive.

**It reads files only.** It never asks the runtime or a service, so a shop that is stopped, whose runtime is down, or whose plan lapsed exports like any other (the builder or partner can export for 90 days after a final stop; nothing here asks fleet or the licence, and the export is never sent to the owner: only a signed-in builder or partner, or `geometer export` on the server, gets it, and after a move the new partner does). `geometer export` on a server with a panel asks the panel container to build it, because the papers are in the panel's own store, sealed when the panel has a data key; a server with no panel builds it from its files and says that the panel's papers are not in it.

**Checking it.** `node bundle/export/check.ts <folder or .tar.gz>` re-hashes every file against the manifest and `SHA256SUMS`, finds missing and extra files, and runs the report verifier's check (`verifyEnvelopeText`) over every signed paper. The papers are in the report format (`geometer-document/1`), which `templates/commerce/bookings/scripts/verify-report.ts` reads; `geometer-verify` (Guard's receipts) does not read them, and the README says so. The test runs `verify-report.ts` on a report taken out of the download, for a Bookings shop and a Fees centre, and a changed byte fails.

**The limits' history** starts when the panel first saves a shop after this feature (`shops.recordSettings`: one line per version with who saved it and the sha256 of the settings written with sorted keys; a version the same as the last is not written twice). Nothing is made up for earlier versions: the manifest's notes say when the history starts, or that none was kept.

## Moving a shop to someone else (B38, 7 Nov)

`handover.ts`, `/shops/<shop>/handover`. Whoever serves the shop (or a builder on the server) types the new person's sign-in name and picks why: stopped paying, stopped serving, or the owner asked. The new person must be an account on this server, a partner or a builder; an account whose sign-in name or name says Geometer (or fleet, server, system, admin) is refused ("never to Geometer"). The panel then shows a one-use code once (kept only as a hash, 72 hours) and tells the person to ask the owner to send `move CODE` from their own phone to the shop's WhatsApp number. When the agent has recorded that message (`handover_agreed`, from the owner's number, with the code's hash) and the panel finds it in the shop's exported record after the request and before it ran out, the panel writes `shops/<shop>/assignment.json` and the move is done (it looks on the shop pages, the list and the shops list, so it completes even if nobody opens the handover page). Not accepted: the code from another number, another code, a line from before the request or after it ran out, a line that is not `confirmed`, a different action. A used code cannot move the shop again.

**What moves:** who can see and change the shop (`shops.servedBy`, which `visibleTo` and `find` use: the new partner sees it, the old one gets the same 404 as for a shop that is not there), and the name on the owner's monthly report (`resolvePreparedBy` now reads `assignment.json` first, then `report.json`, then `owner.json`; the deployer reads the same function, so the next deploy puts the new name in the runtime's config; a test reads it through `readShop`). **What does not:** `owner.json` (who set the shop up; written once), the shop's WhatsApp, payment and calendar accounts (they are the shop's own), and any key: the secrets inbox is write-only and never read, the move writes only `assignment.json`, and whoever serves the shop now enters the keys again. The page says all three plainly. The history (who, to whom, when, why, and the hash of the owner's code) is in `assignment.json` and in the shop's export.

## Languages

English is the source. Hindi, Malayalam and Kannada are machine-written, each marked `machine-written` in `languages.ts` (`REVIEW_STATE`), and every page in them ends with a line saying so. The seven limit sentences are the product's one-source table (four are verbatim from `gtm-and-revenue.md` and a test pins them in all four languages); the certificate line and "Show what we did" are the report's. Section 7 of `REVIEW-ml.md` and `REVIEW-kn.md` is made by `node bundle/panel/review-sheet.ts ml > templates/commerce/bookings/REVIEW-ml.md` (the template's script writes sections 1 to 6, and the template's review test now allows section 7 after them); `test/words.test.ts` fails when a sheet is behind the words, when a language lacks a sentence, when a value (an amount, a name, an address) is not shown as given, or when a line is left in English.

## Secrets and tokens (B26)

Written once to the inbox, never read back, never in a page, a redirect, a log, the panel's data or the shop folder (a test finds nothing of any marker anywhere but the inbox). A box left empty keeps what arrived; a changed Razorpay key id needs its secret again; a form with one bad box writes nothing. Invitations and sessions are one-use or signed and expire; there is no OAuth or sign-in code here, so PKCE and refresh-token rotation have nothing to apply to yet. Encryption at rest with the key outside the data folder is built (hosted mode requires it).

## UPI as the way customers pay (B33, 8 Nov)

**Setup, step 4 (accounts).** A new shop (Bookings or Fees) starts on UPI. The partner chooses UPI or Razorpay (a radio, `payMod`). For UPI they type the shop's own UPI ID and the payee name customers see in their UPI app; both are checked by `vpaProblem` / `payeeProblem` (modules/payments/providers/upi/link.ts) and refused in the person's language (`upi.problems` in the four word files). No Razorpay key, secret or webhook secret is asked or written for UPI, and the settings get `payment: {module: "upi", upi: {id, payee}}`. The page says plainly that a UPI ID cannot be checked without paying it, so the partner reads it back to the owner. A form that sends no choice (not a browser) is a Razorpay shop, as before UPI. A draft made before this, or from a saved Razorpay shop, is Razorpay: Bookings leaves `payment` out of its settings, Fees keeps writing `{module: "razorpay"}` (a saved block is written back as it was), so editing a Razorpay shop changes nothing unless the partner switches. A shop switched to UPI drops the Razorpay key id from its notes; the write-only inbox is not touched. Fees' limit lines on the rules step are worked out before the UPI ID is asked, so until it is given they are built as for Razorpay (they do not depend on it; the save cannot be reached before step 4).

**Go-live.** `golive.ts` leaves Razorpay out of the connection targets for a UPI shop, so there is no Razorpay check, no pin, and "connections" is met by WhatsApp and the calendar alone. Nothing else in readiness asked for Razorpay. The monthly report's `source` is "live" for a UPI shop (it has no test mode and no pin).

**Cost.** A UPI shop has no Razorpay line; the cost table says "No gateway fee: customers pay the shop's own UPI ID" (caveat `no-gateway-fee`, words in `upi.noGatewayFee`). `shop-pays-razorpay` stays only for Razorpay shops, whose lines are unchanged.

**Words.** One `upi` block at the end of each word file (setup choice, refusals, cost note) and two inbox kinds, `upi_payment_unconfirmed` and `upi_refund_owed`. Hindi, Malayalam and Kannada are machine-written and wait for a native reader, like the rest.

**Tests.** `test/upi.test.ts`.

## The papers page (B28, B35, B36; 8 November 2026)

## Orders in the panel (B55, 9 Nov)

A partner sets up an Orders shop (a tiffin service, a bakery, a caterer) on a phone in the same five steps as a Fees centre, and the shop then shows and behaves like one everywhere: the shop page, the checks and "Ready to go live", the monthly report (page and WhatsApp text), the unfinished-work list, the papers, the licence wind-down and `shop add --template orders`.

**One table instead of two-way branches.** Fees had about fifteen `isFees` / `template.setup === "fees"` branches in `server.ts` and `views.ts`; a third template would have been a third `if` in each. `setups.ts` now holds one row for each template with its own forms (`SETUPS`: fees, orders) and one for each monthly report (`REPORTS`: bookings, fees, orders). A row has the draft (new, and from a saved shop), what each step refuses, how the draft becomes settings, `runtime.json`, the limit lines, the two forms, and the pieces of the shop page and the checks page. `server.ts` and `views.ts` ask the row; Bookings is the default when there is no row. The pieces are plain text already in the reader's language (`TemplatePieces` in `views.ts`), so the page does not know which template made them. A new template is one more row. Branches replaced: shop page (summary, activity, cost or messages, live-state labels, live counts, limit lines), shop edit (draft), report (certificate reader and writer), start page, new draft, step view, checks view, step apply (two), save (settings, runtime, lock version), the case list, the inbox's cases, the case source for the papers, the export reader. Fees' pages are the same as before, byte for byte (the pieces are built from the same strings in the same markup).

**The form.** Step "business": the shop's name, its address, and the menu as one box with an item on each line, "name, price, daily stock" (at most 30; the last two commas are the price and the stock, so a name may hold a comma; the id is made from the name, or `item-3` for a name with no Latin letters; the name is the item's name in every language the shop speaks). Step "deposit" (the rules): cut-off (days before, time), pickup slots and delivery slots (one per line, "12:00-13:00" and optionally ", lunch"), the delivery area (commas or lines; empty slots and empty area means the shop does not deliver, one without the other is refused in words), the advance (part with a percent, or all of the order, and the minutes an order is held), most orders a day, most items in an order, days ahead, the cancellation window, the refund limit and the owner approval line (0 never). Languages, accounts and checks are the shared steps. UPI is the way customers pay unless the partner picks Razorpay (the shared payment block). `validateSettings` of the Orders template is the last gate; every problem it could raise that a person can cause is said in the person's language first (including "one order could come to ₹X, more than the ₹5,000 that can be refunded in a day", with the numbers).

**Slot ids and editing.** The pathway wants a slot's id to be its own across pickup and delivery together, so a delivery "lunch" becomes `lunch-2`. Editing a shop through the form keeps what its orders point at: a menu item or slot keeps the id it had when its name is unchanged, and a slot keeps its own cut-off. Per-language names, synonyms and a slot's other settings are not in the form (see Deferred.md).

**Messages line.** The cost line for a Fees shop is "reminders and receipts"; an Orders shop sends no reminders, so its line is a planning figure: most orders a day × 31 days × about 3 messages for each order (the customer's confirmation, the notice to the owner, and one follow-up such as a refund or a hold that ran out), with the plan's allowance beside it as for Fees. It says "plan for up to", not "at most": in the template's busy month (10 orders) the agent started at most 2 messages for any one order, but a long-lived order (cancelled late, refunded, reminded) could need more, so no hard limit is claimed. Replies inside the 24-hour window come on top, as for Fees.

**The export.** `readExport` reads `orders.json` after `bookings.json` and `dues.json`; the cases for the unfinished-work list, the papers and the case list come from one function (`casesOf`) by the shop's template. The unfinished-work sentence for a big order waiting long has its noun ("a big order") in four languages.

**Words.** `setup.orders.*`, `ordersShop.*`, `templateNames.orders`, `inbox.variants.big_order` in four languages. Hindi, Malayalam and Kannada are machine-written and wait for review, exactly as the rest of the panel's words are; section 7 of the Bookings review sheets for Malayalam and Kannada was regenerated to carry the new lines.

**Tests.** `test/orders-form.test.ts` (the form's logic), `test/orders-flow.test.ts` (the five steps, the checks, the certificate, the report, the shop page in four languages, editing), `test/orders-resolves.test.ts` (an `orders@` lock is an Orders shop in the kind, the hand check, the export's cases, the inbox, the papers, the report, the shop page and the drafts; each assertion is one that a fall-back to Bookings would fail).

## Client health and margin (B32) and the template vote (B56; 9 Nov)

**What a partner sees.** "Health and margin" in the tab bar lists the partner's shops, those that need a look first, and the sum of what they keep. A shop's page (`/health/<shop>`) has three parts:
- **What needs a look.** The unfinished-work items by kind (the same list as the to-do page, `inbox.ts`), the licence when it is not in order, the last heartbeat (fleet's last answer, with a note after 2 days), fleet's warnings and button mode, and the age of the last restore drill when the deployer wrote one (`status.backups`).
- **The running cost this month.** Geometer's charge from the price list in force, by the shop page's own rule (`cost.ts` `chargeOf`: the plan fleet reports, else the one the shop's settings point to, at its fee on Geometer's server; the builder licence on a builder's own server, whatever the plan), WhatsApp at cost and the model, both counted from **this month's entries** of the exported record with the same `lib/usage.ts` the cost meter uses (the status file's counts are cumulative, so they cannot say "this month"), and the support time the partner types in. On Geometer's hosted server the model is inside the plan fee, so that line reads "Included"; on a builder's own server it is the cost the runtime recorded, a floor when some calls had no price.
- **What you charge.** A monthly price per shop and an optional one-time setup fee, plus support minutes for the month and what an hour of the partner's time is worth to them. **Margin** is the price minus the known costs.

**Unknown is never 0.** A price not entered gives "unknown", not ₹0. A cost line with no number (no record shared, no minutes or no hourly value entered, a rate missing from the list) is "unknown", the running cost is called a subtotal, and the margin is said to be "before" those lines. The total over shops adds only the shops that have a margin, says how many that is, and, like each shop's card, says it is "before the costs that are not known yet" while any cost line is unknown. Nothing is a forecast: every figure is arithmetic on a price the person typed and counts the record holds, and the words are "margin", "what you keep", "your price" and "running cost".

**Where it is kept.** The partner's entries are in the panel's own store (`panel/data/health/<account>/<shop>.json`, sealed by the data key when there is one), under the person's account: a builder who can open a partner's shop does not see her price, and a handover starts the new person clean. They are never sent to fleet, which keeps counts only, and the log never holds an amount. A shop that is not the person's is a 404 to read and to save, like every shop page.

**The vote.** `vote-options.json` is the one data file (round, option ids, a label in four languages). `/vote` is a 404 unless fleet flags a shop the person serves as an Innovator (`fleet/<shop>.json`); the "Vote on the next template" link shows only to them. A vote is one file per account, so a new choice replaces the old one; the counts are shown only after the person has voted, as counts without names. The votes stay local: `votes.heartbeatField()` is the exact `template_votes` field the heartbeat will carry when fleet accepts it (`bundle/Deferred.md`).

**Files.** `health.ts` (arithmetic and entries), `health-data.ts` (puts a shop together), `views-health.ts` (pages), `words-health.ts` (four languages; Hindi, Malayalam and Kannada machine-written, waiting for native review, and added to the review sheets as `health.*` and `vote.option.*` by `review.ts`), `votes.ts` and `vote-options.json`.

**Tests.** `test/health.test.ts`: the arithmetic on fixed numbers (Geometer's charge on both kinds of server, WhatsApp, model, support, margin, sums), unknown staying unknown, this month only, a partner seeing only her shops (404), the vote hidden from a non-innovator, one vote each and changeable, counts without names, and no banned word in any of the four languages.

## This server: the panel's first run (11 Nov 2026, plan item 14b part 2a)

The one-step install (`install.sh`) leaves the server's own keys to the panel. A builder on their own server (never Geometer's hosted panel, and never a partner) gets **This server** (`/server`, linked from Shops, with a notice there until it is done): `server-setup.ts` (the panel's side), `views-server.ts` (the pages), `server-contract.ts` (the files it shares with the deployer, `bundle/server-settings.ts`).

- **The panel never writes `geometer.json`** (it is mounted read-only). It writes a request, `requests/_server.model.json` or `_server.backup.json`, which the deployer checks again, writes into `geometer.json` only when the bundle's whole check passes, and answers in `status/_server.json`: applied, or refused with the reason, which the page shows. The same pattern as a shop's desired state and its status. Until the deployer takes a request, the page says it is waiting, and that a request that stays means the deployer is not running.
- **The model**: OpenAI, Anthropic, another provider that speaks OpenAI's API (its host:port, chat path and price-table name), or a model the builder hosts (B73's `model.selfHosted`: its address, https or plain http only to a private address, and the builder's own price per million tokens). The form's shape is the one geometer.json takes; it is checked here and again by the deployer. A model the builder hosts is refused by a bundle that cannot run one yet (B73 is on its own branch), because its model Guard would send the builder's key to OpenAI. The model of a server that already runs shops is not changed (each shop's runtime names it).
- **Keys** (the model's, the bucket's, a server-wide Google service account) go through the same write-only inbox as a shop's (`secrets.ts`, `createServerInbox`: written, never read back; `secrets-inbox/_server/`). The deployer checks each by shape again, moves it to the one container that needs it, and deletes it; the status file says which keys are in place and when, never a key. The model's key waits in the inbox until the model is chosen (its file depends on the wire).
- **The backup bucket and its test write.** The bucket (s3://, with the storage service's address and region), its key, and the key the snapshots are locked with. On each change the deployer writes a small object with that key, reads it back and deletes it, and the page shows the result; "Test the bucket again" asks once more. A key that may not delete passes and says the bucket's lifecycle rule removes the test object.
- **The backup key, shown until confirmed.** The bundle's rule is that the key that opens a backup is not on the server. "Make one for me" makes an age key pair in the panel; the public half goes into the request, and the secret half is kept in the panel's store, sealed with the panel's data key, until the builder says it is somewhere else. Its own page shows it (and downloads it as a file), and the builder confirms by typing its last 6 characters from where they saved it (which shows they have a copy without asking for the whole key again) and ticking that it is off this server. Then the panel deletes it and never offers it again; only the public half stays. Until then the server page and Shops say plainly that the secret half is still on the server. A builder who has an age key already gives only its public half ("I have an age key"); a pair made here and not yet confirmed is never replaced by another key, because backups may already be locked with it.
- **Google** is optional: one service account for shops that hand in none of their own. Its address (the one calendars are shared with) shows once the deployer has it in place; on a server with no shop yet the deployer brings its own services up again so the panel's setup page names it.
- **The model a shop's runtime names** is read from geometer.json when the shop is written (`config.ts`, `readServerModel`), not only when the panel starts, because on a new server the first run chooses it while the panel runs.
- The pages are English only for now (a builder's pages, used once); Hindi, Malayalam and Kannada wait (Deferred.md).

## The panel at phone width (11 Nov 2026)

Partners and builders use the panel on phones of 360 to 390 px. A pass on `panel.css` and the views, still with no JavaScript:
- **No sideways scrolling.** Long words (a shop's id, a key's public half, a web address, a long compound in Malayalam) wrap anywhere in `main`; `pre` wraps; a table other than the two-column cost tables has fixed columns (the confirm page's four); images and tables never pass the width; below 420 px two fields side by side become one under the other.
- **Forms.** Every field is 16 px, so a phone does not zoom when it is touched; radio choices and the confirm box are 44 px rows with their help under them; a long button label wraps.
- **Focus.** A visible ring on every link, button, field and `summary`; inside the fixed tab bar it is drawn inside the tab, where an outside ring would be cut off. The open tab is marked `aria-current="page"` (read out, and highlighted).
- **Up to six tabs** share a phone's width: below 420 px their words are smaller and may wrap to two lines.
- **Five inline `style=""` attributes did nothing.** The panel's Content-Security-Policy lets in only its own nonce'd stylesheet, and an inline style attribute is not that, so the sign-out tab, two full-width buttons, a margin and the to-do list's inline forms were drawn without them. They are classes now (`tabform`, `wide`, `mt`, `inline`), and a test fails on any `style="` in a view.
