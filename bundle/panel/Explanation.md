# Explanation: the open panel and the phone setup (B10, B25, B26)

One panel, zero dependencies, pages rendered on the server with no JavaScript. A builder runs it on their own server for their shops (`PANEL_MODE=own`); Geometer runs the same code on its own server for the partners' shops (`hosted`). It reuses the demo's page shell and style (`pathways/bookings/demo/page.css` is read, not copied), the demo's shop form (`personalise.ts`: `settingsFromForm`, `formFromSettings`, `languageOptions`), `validateSettings` as the last gate on every setting, the report's strings for the certificate line and "Show what we did", and `report/` for the go-live certificate and the monthly report.

## What it is, file by file (`bundle/panel/`)

| File | What it does |
|---|---|
| `main.ts` | Starts the panel, or makes an invitation link (`invite --role builder\|partner`). |
| `config.ts` | Everything is an environment variable (`PANEL_SERVER_DIR`, `PANEL_MODE`, `PANEL_PUBLIC_URL`, `PANEL_DATA_KEY_FILE`, `PANEL_SIGNING_KEY_FILE`, `PANEL_CALENDAR_SHARE_ADDRESS`, `PANEL_RUNTIME_URL` and `_TOKEN_FILE` with `{shop}`, `PANEL_GUARD_URL` and `_AGENT_TOKEN_FILE` with `{shop}` and `{kind}`, `PANEL_WEBHOOK_URL`, `PANEL_TRUST_PROXY`, and the cost line's settings). Reads the server's model from `geometer.json`. |
| `contract.ts` | Every file shape shared with the deployer, with a checker for each: `ShopStatus`, the stop request, `owner.json`, `pins.json`, the secret names, and `liveView`, the one function that decides what a shop's life is called. |
| `vault.ts`, `store.ts` | AES-256-GCM (node:crypto), a fresh nonce per write, the record's name as authenticated data, the key in a file named by the environment and refused if it sits inside the panel's folder or is readable by others. Everything the panel keeps (accounts, invitations as hashes, drafts, which secrets arrived, checks) is sealed when there is a key; in hosted mode there must be one. A changed file, a wrong key or a plain file where a sealed one belongs is an error, never "no accounts". |
| `accounts.ts`, `session.ts`, `ratelimit.ts` | Roles `builder` and `partner`. scrypt passphrases. An account exists only through a one-use invitation link (only a hash of the token is kept; the link is a path the log blanks out). Sessions are signed cookies (HMAC-SHA256, `HttpOnly`, `SameSite=Strict`, `Secure` and `__Host-` over HTTPS) carrying the account's session version, so "sign out everywhere" kills them all. CSRF: a token derived from the cookie in every form, an anonymous signed one for the sign-in and invitation forms, and an Origin check. Login limit: 5 failures per name and address, 20 per address, in a sliding window; once over, even the right passphrase waits. |
| `shops.ts` | The only place that touches `shops/`, `status/`, `requests/`. `find(account, id)` is the one visibility rule (a builder sees all, a partner only shops whose `owner.json` names them); a shop that is not yours is a 404, exactly like one that does not exist. `owner.json` is written with flag `wx`: the first account to set a shop up is its attribution for good. |
| `server.ts`, `views.ts`, `html.ts`, `panel.css` | The routes and the pages. `html.ts` escapes every value by default. CSP with no script at all, no framing, no referrer, no caching. The log line is method, path, status and time: no query, cookie or body, and an invitation's token blanked. |
| `setup.ts`, `secrets.ts` | The five steps (the business; deposit and cancellation; languages and the owner's number; the shop's accounts; checks) as functions: each step's refusals in the person's language, then `buildSettings`, which is the demo's `settingsFromForm` with the chosen languages, owner and cancellation window on top and `validateSettings` last. The secrets intake writes a file per secret into `secrets-inbox/<shop>/` (0600, atomic) and notes that it arrived; it has no way to read anything back (a test checks the source), validates every box before writing any, and never puts a value in a message. |
| `templates.ts` | Finds templates by `pathways/*/template.json` (accounts the template uses, steps, an example settings file). Setup asks only for those accounts, so a new or contributed template appears on its own; one whose `setup` form the panel does not have is listed as "set up by a builder". |
| `checks.ts` | The read-only connection checks (below). |
| `cost.ts`, `../prices/2026-11-03.json` | The monthly running-cost line (below). |
| `golive.ts`, `activity.ts` | The hand check on the shop's own settings, the connection checks, "Ready to go live" (writes the go-live certificate, signed when the panel has a key), and the month's counts from the exported record. |
| `words.ts`, `words.hi.ts`, `words.ml.ts`, `words.kn.ts`, `languages.ts`, `review.ts`, `review-sheet.ts` | Every word in four languages; see Languages. |

## The partner's setup, as the partner sees it (English)

1. **The business.** Shop name; up to four services with name, other names customers use, price (also the lowest the agent agrees to) and minutes; opening time, closing time and the days open.
2. **Deposit and cancellation.** The deposit, and how many hours before a start a customer may cancel and get it back. Under it, each limit as one sentence of what the shop gains: "It can't go below your prices, and it asks you before any refund." "It never books outside your opening hours." "The deposit is ₹200, never more than your cheapest price, and the slot is held 15 minutes while it is paid." "If a customer cancels at least 24 hours before, the deposit goes back. Anything later, or any refund above ₹200, waits for your OK on WhatsApp." "When it says booked, the slot is in your calendar and the deposit is in your account." "Your customers are answered in their language, with the right price and date." "You stay in charge from your phone."
3. **Languages and your number.** The main language of the customers and any others; the owner's language; the owner's own WhatsApp number (the one that approves refunds).
4. **Connect the shop's accounts.** Only the accounts the template uses. WhatsApp: the shop keeps its number and app; type the shop's number, the phone number ID, the access token and the app secret. Calendar: share the calendar with the address shown, choose "Make changes to events", type the calendar's ID (or paste the builder's key file if the server has no shared address). Razorpay: the shop's own account; live or practice; the key ID and secret; the webhook secret.
5. **Checks.** Save and connect; the tests on this shop's own prices and hours ("Held N of M situations. 0 failed. J not tested."); the server's update and "N of M limits proven"; the three connection checks; the cost line; then **Ready to go live**, which makes the certificate.

## Connection checks (B26): read-only, pinned

`checkConnections` is exported; the bundle's CLI can call it. It takes base URLs and the ids the shop gave, never a provider key (in production the base URL is the shop's Guard, which holds the keys, and the panel presents only its own Guard credential). It uses the live adapters' `createHttp`, so Guard's answers (refused, held, unavailable, unauthenticated) are told apart in the one place the adapters tell them apart. Every call is a GET (a test records them all and checks the stand-ins' outbox, links and calendar are untouched). A different account is its own error code (`account_mismatch`, `not_found`, `wrong_mode`); what was found is never adopted. What a read cannot show is named in `notChecked`. A reply that contains the credential is thrown away. The ids the providers reported are `pins`; they are written to `pins.json`, and a calendar id is pinned as Google writes it.

| Service | Calls | Docs |
|---|---|---|
| WhatsApp | `GET /v26.0/{phone-number-id}?fields=id,display_phone_number,verified_name`. The id must be the one given and the number must be the shop's own business number (digits compared), not the owner's. | https://developers.facebook.com/docs/whatsapp/cloud-api/reference/phone-numbers/ |
| Razorpay | `GET /v1/payment_links?reference_id=geometer-connection-check`: an empty list when the key is good. Also: a key id with the wrong mode (`rzp_test_` for a live shop) is refused with no call, and a key id different from the one confirmed before is `account_mismatch`. | https://razorpay.com/docs/api/payments/payment-links/fetch-all-standard/ |
| Calendar | `GET /calendar/v3/calendars/{id}` (the id Google reports must be the one given; its name and time zone), then `GET /calendar/v3/calendars/{id}/events?maxResults=1`, whose top-level `accessRole` must be `owner` or `writer`. `writerWithoutPrivateAccess` is refused: the agent writes its booking ids into private properties. | https://developers.google.com/workspace/calendar/api/v3/reference/calendars/get and .../events/list |

**What is not proven for Razorpay, plainly.** Razorpay documents no call that tells an ordinary merchant key which account it belongs to (`GET /v2/accounts/:id` is for Route linked accounts and partner sub-merchants). So the check proves the key works and is in the right mode, and the page says it could not tell whose account it is and tells the person to look at the first test payment link, where the shop's name must appear. The account id arrives in the `account_id` of every signed webhook; pinning that id and refusing events from any other account is the next step (Deferred.md). I did not add an invented endpoint to the stand-ins for this.

Stand-in changes (small, nothing the agent uses changed): `GET /{version}/{phone-number-id}` answers with the number's own details, and `GET /calendar/v3/calendars/{id}` with the calendar's metadata, for the id the stand-in is given (404 for any other, as Google does); `accessRole` of the events list is an option (default `owner`).

## The monthly running-cost line (B26)

Rules from Lorelei's cost calculator: exact arithmetic (a BigInt in micropaise, so ₹0.115 a message is 11,500,000 and nothing is a float; each line is rounded up once, to the next paisa, and the total is the sum of the rounded lines); an unknown price is `unknown`, never ₹0, and a total with an unknown line is called a subtotal and says how many items have no price; "early estimate" until the record has real bookings; and every rate comes from a dated, versioned file. A line is an amount, `included`, or `unknown`. The lines: WhatsApp messages (Meta's fee: reminders and owner notices as utility templates, replies inside the window free up to 1,000 a month per number), the WhatsApp provider's own fee (unknown until one is named), model use against the included allowance (unknown until the allowance is set; the would-be cost is still shown), Razorpay's fee (2% plus 18% GST on the fee per deposit, shown as paid by the shop to Razorpay), and a hosting share (a setting; unknown until the bundle measures it). The assumptions (40 bookings a month, 6 replies and 6 model calls per booking, 600 and 100 tokens a call) are on the page.

`bundle/prices/2026-11-03.json`: every rate has its source URL, the day it was read, and a quality (`official`, `official-undated`, `second-hand`, `assumed`, `conflicting`) with a note. The sha256 of each committed price list is pinned in `test/cost.test.ts`, so editing one fails a test; a changed price is a new file with a new date, and the panel uses the newest. Second-hand: ₹0.115 for utility and service messages (three vendors show three figures). Assumed: ₹90 per US$ and ₹100 per € (the research's round numbers). Conflicting: Razorpay's fee on payment links (2% is used). `eval/models.json` is untouched: a test checks that every model price in it equals the price list's, and making the eval read the list is the next step.

For Glow Salon at 40 bookings a month the page shows (with the server's model set to `claude-haiku-5-5` and nothing else set): WhatsApp messages ₹13.80; provider's fee unknown; model use unknown (about ₹2.38 of use, allowance not set); Razorpay's fee ₹188.80, paid by the shop; hosting share unknown; subtotal ₹202.60 with "3 items have no price yet".

## Languages

English is the source. Hindi, Malayalam and Kannada are machine-written, each marked `machine-written` in `languages.ts` (`REVIEW_STATE`), and every page in them ends with a line saying so. The seven limit sentences are the product's one-source table (four are verbatim from `gtm-and-revenue.md` and a test pins them in all four languages); the certificate line and "Show what we did" are the report's. Section 7 of `REVIEW-ml.md` and `REVIEW-kn.md` is made by `node bundle/panel/review-sheet.ts ml > pathways/bookings/REVIEW-ml.md` (the pathway's script writes sections 1 to 6, and the pathway's review test now allows section 7 after them); `test/words.test.ts` fails when a sheet is behind the words, when a language lacks a sentence, when a value (an amount, a name, an address) is not shown as given, or when a line is left in English.

## Secrets and tokens (B26)

Written once to the inbox, never read back, never in a page, a redirect, a log, the panel's data or the shop folder (a test finds nothing of any marker anywhere but the inbox). A box left empty keeps what arrived; a changed Razorpay key id needs its secret again; a form with one bad box writes nothing. Invitations and sessions are one-use or signed and expire; there is no OAuth or sign-in code here, so PKCE and refresh-token rotation have nothing to apply to yet. Encryption at rest with the key outside the data folder is built (hosted mode requires it).
