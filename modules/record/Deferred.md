# Deferred: the record's ledger and fingerprints

What is not done, and what it would take. geometer-verify reads the ledger as it is (Explanation.md); nothing below needs a change to geometer-verify unless it says so.

| What | Why it waits | What it would take |
| --- | --- | --- |
| **Key rotation.** The pack's key log holds one `genesis` event for the shop's key. A new key would make every anchor kept under the old one fail (`wrong_key`), and a lost key cannot be replaced in the log. | One key per panel or runtime today, no rotation anywhere in the bundle (the reports' Deferred says the same). | Keep the key log beside the shop's state and append `rotate` events (signed by the old and the new key) and, after a loss, `recover`; geometer-verify already reads all of them. Then sign checkpoints with the newest key and keep old anchors valid. |
| **The customer's number and the note are not chained.** Changing them changes no hash (Explanation.md, "What an entry's body holds"). | Putting the number in the body would put it in every pack, and a fingerprint in the body would tie every entry to one person for anyone holding the pack, even though the export's fingerprint is keyed now (B69). | geometer-verify's `payload` field: a salted commitment `sha256(salt ‖ bytes)` and the size, with the payload and its salt kept apart by the shop. The salt needs a home in the shop's store (and a deletion story under DPDP: destroy the salt, the commitment stays), so a dispute can later reveal one entry's number to one reader. |
| **Deleting one person under the DPDP Act (nothing built).** The chain can survive it, because it commits to no raw value of a shop's customer: `conversation`, `notes` and `refs.page` are outside it, so removing them changes no hash. What it holds of a person is a keyed digest and a keyed message id, which nobody can read without the key (an entry from before B69 keeps a plain digest and the raw id). | The `record` table refuses every UPDATE and DELETE (triggers in `modules/runtime/store.ts`), the entry JSON holds the number beside the column, and an erasure must reach everything else: the state snapshot (cases, customers), the `window` table, a failed task's payload until the daily compaction empties it, and the 30-day nightly snapshots. Lifting an append-only rule is too large to do alongside the fingerprints. | **The smallest design:** one maintenance step, with the runtime stopped, in one transaction: drop the triggers, replace `conversation` (the column and the JSON) with a fingerprint and blank `notes` for that person's entries, put the triggers back, append an entry listing the redacted seqs, scrub the snapshot and `window`. The body bytes stay identical, so `geo-verify` still passes. Say how long the backups keep the old copy (30 days), and that a fingerprint left in the chain is pseudonymous, not erased. Destroying the shop's key makes every fingerprint unmatchable at once, which fits closing a whole shop, not one person. The owner should take legal advice on whether a keyed digest kept in a chain counts as erased. |
| **An entry written before B69 stays as it was.** Its `inputsDigest` is plain and its `refs.messageId` is the id as WhatsApp gave it. | They are chained: rewriting them changes every hash after them. Nothing is live, so nothing real is affected. | Nothing, unless a shop goes live with such entries: then start its record again, before its first fingerprint is published. |
| **One person cannot check their own entries against the published head without the whole pack.** A linear chain can show an entry is in it only by giving every entry after it. | geometer-verify's ledger is a hash chain, not a Merkle tree; the statement carries the head it was made at, which a person can hold against the published fingerprint, but not the path to their own entries. | A Merkle tree over the entries beside the chain (the head of both published), and inclusion proofs on the statement. That is a new record type in geometer-verify's contract (additive inside `geo/2`), so it is geometer-verify's call. |
| **Post-quantum signatures.** Checkpoints are classical (`geo-ed25519/1`). | `node:crypto` has no ML-DSA-65 yet in a form this repository can use without a dependency. | Version 2 checkpoints with `geo-profile/hybrid/1` once `node:crypto` signs ML-DSA; geometer-verify already verifies them. |
| **The papers themselves are not geometer-verify records.** The statement, the record of one case and the identity paper are `geometer-document/1` envelopes (`modules/report/sign.ts`), which `geo-verify` does not read; what ties them to the ledger is the `anchor` they carry (tenant, entry, head). | geometer-verify's strict schemas are generated from its `contracts/schemas/core.toml`; adding records there is that repository's change. | Either a `geometer.agent-paper` record in the contract (format, document bytes, digest, the anchor), or the papers written as assessment bundles. Until then: check the paper with the site's checker or `verify-report.ts`, and the anchor's head against the pack with `geo-verify`. |
| **A published line names the shop's id and its entry count.** Anyone watching the public file can see roughly how busy a shop is. | It is what makes the line checkable against a pack (the anchor names the tenant and the count). | Publish under a per-shop public label instead of the id, or only the head; decide before any public target is switched on. |
| **The git target pushes to whatever remote the working copy has.** It never adds or changes a remote. | Choosing the public repository is the owner's decision (and a deploy yes). | The owner names the repository; `fingerprints.json` records it with the yes. |
| **A day whose push failed is not pushed again.** The line is in the local file; the git target's answer says "not pushed" and the deployer logs it, but the next day pushes only the next day's line. | Nothing is public yet. | On each run, push every local line the public file does not have yet. |
| **OpenTimestamps answers are kept, not upgraded.** A calendar's first answer is a pending timestamp; it completes later on the calendar's side. | Upgrading needs the OpenTimestamps client (a dependency) or its upgrade protocol written by hand. | Fetch the completed timestamp a day later and keep it beside the first. |
