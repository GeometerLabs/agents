# Deferred: shared modules

What is not done, and why. Each item says what it would take.

| What | Why it waits | What it would take |
| --- | --- | --- |
| **Modules are not versioned on their own.** A template is pinned (`bookings@0.1.0`), the modules it imports are whatever the app or the server holds. | One template and one version so far, and `geometer update` moves templates, not code beside them. | `pathway.lock` lists modules with a pin (the plan already says "plus any modules, each pinned"). `bundle/lib/pathways.ts` then looks for the right modules folder, and `update.ts` hand-checks a client at both module versions. Until then the server keeps one `modules/` beside its `templates/`, and a module change is a change to every template. |
| **The runtime's status names its cases differently in each template.** `runtime/core.ts` takes the name from the template (`bookings`, `fees`), so Bookings' `/status` is as it was and Fees' has `fees`. The fleet contract has one map, `runtime.bookings`; the bundle's heartbeat sends whichever the runtime has under that name. | Fleet's contract was written for Bookings. Changing it is fleet's decision, not this folder's. | Fleet's contract names the map after what it counts (cases), and the runtimes say `cases`. |
| **The runtime config reader is shared, so an old pinned version reads the current one.** `runtime/config.ts` is what an older Bookings or Fees version checks `runtime.json` with, when it is kept beside the server. A version from before a setting existed would accept it. `bundle/test/report-block.test.ts` simulates a version that does not know `report` by editing the copy of `modules/` beside the server. | The same reason as the first row: modules are not versioned. | `pathway.lock` pins modules. |
| **The HTTP Guard stand-in checks refunds only.** `modules/standins/guard.ts` decides holds and refusals for the refund route. The in-process model (`payments/guard-model.ts`) also bounds the amount of a link. | The stand-in is used by `npm run stack` and a few tests, which only ask for refunds. | Call `decideLink` on `POST /v1/payment_links` and answer 403 with the rule's id, as the real Guard does. |
| **The Guard model does not count the caps** (`links-per-hour`, `refunds-per-day`, `refund-paise-per-day`). It reads the spec's bounds and its approval threshold. | The real Guard counts them, and `approvals-guard-binary.test.ts` checks the real binary when it is installed. | Count calls per window in the model, from the spec's `limits`. |
| **Some word lists hold Bookings words.** `language/words.ts` has `book`, `cancel` and `reschedule` beside the shared lists (yes, no, STOP, dates). | Moving them is a rename with no gain until a third template adds its own. | Split the file by template when the third arrives. |
| **Most tests of module code are still in `templates/commerce/bookings/test/`.** Only the ones that needed nothing of Bookings moved (`dates`, `record`), with new tests for the new code. | The rest drive the module through the Bookings agent, which is how it is used; moving them needs the Bookings harness. | Add module-level tests for `payments/refunds.ts` and `messaging/say.ts` with a toy template, as the Fees tests do through the Fees agent. |
| **No type check.** Types are comments here, as in the rest of the repository (Node strips them). A `Reading` or a `RelayVoice` that does not fit is found by a test, not by a compiler. | The repository has no TypeScript compiler, on purpose (no dependencies). | Run `tsc --noEmit` from a pinned install in CI, outside the repository's dependency-free rule. |
| **`understanding/model.ts` shows the cost field names for Bookings.** The record fields the cost meter reads are listed in `templates/commerce/bookings/Explanation.md`. | The meter reads them from the record whatever the template. | Move that table into this folder when a third reader of it appears. |
| **A recovery step is not refused while a shop is wound down.** `onRecovery` in both agents does what its name says whatever the shop's licence state. | B13's wind-down mode (a licence per deployment, `subscription_suspended`) is not built, so there is no state to read. | When the licence lease lands, the runtime refuses `ask_owner_again` and `retry_booking` while wound down (they send messages or make bookings) and keeps `recheck_payment` and `recheck_refund` (they only read and record), as B13 says refunds, cancellations and reconciliation still go through. |
| **"Ask the owner again" cannot reach a refund Guard is holding.** The approvals relay asks the owner once by design; the agent does not ask a second time, so `approval_waiting_long` on a Guard hold has no button. | The relay's ask and its one-use code are the relay's own state (`approvals/relay.ts`), and a second ask means a new code and a new message there. | A relay verb "ask again" (new code, same approval, only while the approval is live), called by the runtime or the deployer; then `guard_hold` joins the kinds that offer `ask_owner_again`. |
| **The owner is not told that a handover code arrived.** `move CODE` is recorded and nothing is sent back. | An owner-bound message outside WhatsApp's 24 hours needs a Meta-approved template (`meta-templates.ts`), and a new template needs approval first. | Add `owner_handover_noted` to the Bookings and Fees templates and to `whatsapp-templates.json` in four languages; the agents send it when they record the line. |
| **UPI requests are unsigned personal-style requests.** The `upi://pay` link carries `pa`, `pn`, `am`, `tn` and `cu`; no `tr`, `mc`, `mode`, `orgid` or `sign` (`payments/upi/link.ts`). | NPCI's signed merchant request needs a merchant account with a bank; a partner shop's UPI ID is often personal. Payment apps may also block or warn on prefilled payments to a personal UPI ID (the plan's "to test first"). Not tested with real UPI apps yet. | Try the link and the QR with the main UPI apps (GPay, PhonePe, Paytm, BHIM) against a personal and a business UPI ID; for a shop with a business UPI ID add `tr` (the reference) and, with its bank, `mc` and a signature. |
| **The QR picture is sent by its address, not uploaded.** `sendImage` sends `image.link`; the runtime writes the PNG into the served report folder under a random name. The pictures are never cleaned up. | Uploading media to WhatsApp needs a second Guard route (`POST /{phone_number_id}/media`) and a multipart body through Guard, which has not been tried. | Upload the PNG as media (a Guard route, multipart in `core/http.ts`) and send by id; or remove a request's picture when the request is settled or closed. |
| **The QR picture goes only inside the 24-hour window.** A Fees reminder that goes as a WhatsApp template carries the link and the UPI ID as words, without the picture. | A template with an image header is a different Meta template kind (a media header), and these templates are text. | A reminder template with an image header for UPI centres, approved by Meta. |
| **Every Fees request tells the owner what to look for.** On a reminder day the owner of a centre with 40 students gets 40 "UPI payment to check" messages, each with its code. | The code is how a mark is tied to a fee, and the owner needs it before the money arrives. | A daily digest with one line and one code per open request, or a list the owner opens. |
| **A UPI mark is a whole number of paise, but the words show it as rupees.** "received K7M2QX 150.5" is marked as ₹150.50 and written "₹150.5". | Owners mark whole rupees in practice. | Format paise as "₹150.50" in `language/format.ts` if it is ever needed. |
| **Live UPI codes are kept in plain text in the runtime's snapshot.** `store.upi` holds each request's and refund's live code, so they are in the shop's SQLite file and in its off-site backups; the approvals relay keeps only hashes of its codes. Nothing in the record, the exports or the link carries a code. | A code only counts from the owner's own number, and a forged mark can book a slot but never moves money. | Keep a hash of each code (as `approvals/store.ts` does) and the code itself only until it has been sent to the owner. |
| **The status does not count UPI refunds owed.** The runtime's refund counts are Guard's (`waitingForOwner`, `needBuilder`); a UPI shop's owed refunds show in the record and the unfinished work, and a late mark counts as `late_upi` under `needBuilder`. | The fleet contract's counts are Razorpay-shaped. | Count the ledger's owed refunds in the status beside Guard's, when the fleet contract has a place for them. |

**The UPI obligation function**, for the unfinished-work inbox (B31). Both are merged now, and the kinds are registered (`unfinished/builtin.ts`); this is their shape.

```ts
// modules/payments/upi/obligations.ts
export function upiObligations(entries: readonly RecordEntry[]): UpiObligation[];
export interface UpiObligation {
  kind: "upi_payment_unconfirmed" | "upi_refund_owed";
  case: string;        // the booking or fee ("b-3", "f-3")
  customer: string;    // the record's conversation (the customer's number); the registry's facts leave it out
  amountPaise: number; // still to be confirmed, or owed back
  since: string;       // ISO time of the entry that opened it (the claim, the part mark, the refund owed)
  id: string;          // the request or refund in the shop's store ("upi-3", "upr-5")
  title: string;       // "UPI payment not yet confirmed by the owner" / "Refund owed by the owner, not yet marked done"
}
export const UPI_OBLIGATION_KINDS: readonly ObligationKind[]; // the two, as registry kinds: facts { case, amountInr, ref }, actions ["ask_owner_again"]
```
