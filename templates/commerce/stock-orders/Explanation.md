# Stock orders: what was built, and why

## 17 November 2026: the first version (stream W3, branch `stock-orders-17nov`)

**What it is.** T07 of the template catalogue (owner decisions 49/50): a salon, small retailer or input dealer reorders from approved suppliers on WhatsApp. It starts from the shape of the Purchasing example (one order per request even if the supplier's reply is lost; an order the buyer has not approved is not placed) but is written in TypeScript from the shared modules, like Orders.

**The order of events, and what is judged from what.**

1. The owner's message is read by rules (`src/reading.ts`): item, supplier, unit, quantity. What it cannot tell it asks (a list of the ways to order the item, or "how many"); it never guesses and never converts a unit (a box is not ten pieces).
2. The checks run (`src/limits.ts`): approved supplier, whole quantity, per-order cap, the month's budget. A block gives the owner the plain reason and makes no order.
3. An order exists in `awaiting_approval`; a **card** is shown (`modules/assistant/cards.ts`, used as it is): its fields are the supplier and the supplier's number, item, unit, quantity, unit price and total in paise, the currency and the budget month. Its digest is over those fields.
4. On the owner's yes the order is read again as it is now and compared with the card. A changed quantity (made by "change po-3 12"), a changed catalogue price (settings edited and the shop restarted) or a turned month gives a different digest: nothing is sent and a new card is made. A card used twice, replaced, declined or run out does nothing.
5. **Approval and reservation are one synchronous step** (`approve()` in `src/agent.ts` has no `await` between the checks and the state change). The month's reserved total is *worked out from the orders* each time (`reservedPaise`), never kept as a counter, so two approvals racing for the last of the budget cannot both get it, and a restart cannot leave a number that disagrees.
6. The order message goes out once through `modules/messaging/say.ts`, whose gates include `send-only-when-approved`. The result is read as `say.outcome()`: `accepted` (sent), `maybe` (the provider's reply was lost: `send_unknown`; the order is **never sent again as an order**), `not_sent` (refused outright: `send_failed`; the owner may say "send po-3" once more) or `held_back` (a gate stopped it: `send_blocked`).
7. A silent or unknown-state order is asked about again by reminder messages that carry the same order number and say they are not a new order (`modules/reminders`), at the settings' follow-up hours; the owner is told once after the last.
8. The supplier's answer counts only from the supplier's own number: a button names its order; a typed "ok" counts only when exactly one order of theirs waits, otherwise they are asked which; "no" releases the budget. A stranger or another supplier changes nothing.
9. Delivery is the owner's mark: "received po-3" (all), "received po-3 6" (part), "wrong po-3". "paid po-3" is the owner's note that they paid outside the chat: the agent pays nothing and cannot check it. Evidence is labelled in the record (`supplier_reply` for the supplier, `owner_marked` for the owner), so the record never mixes the three questions: did the supplier accept, did it arrive, was it paid.

**Why the cap is a hard stop.** The owner approves every order anyway, so the cap is for the order the owner would approve by mistake; the owner's yes cannot raise it, an Operator changes it in settings. This is deliberate and recorded as a `per-order-cap` block.

**Why the template, not a module, owns the order.** Nothing here is shared with a second template yet. Generic things Orders also has (the reading words, the plan of a crash test) were written again as small parts of this template rather than moved, because another stream was editing Orders. If a second template needs the same, they should move to `modules/` (the catalogue-line resolver in `src/reading.ts` and the budget-from-orders derivation in `src/order.ts` are the candidates; the generic card-with-a-code message is another).

**What was reused.** `cards` (the approval card and its digest, state, one-use code), `messaging/say.ts`, `messaging` fakes and the template mechanism (`language/meta-templates.ts`), `limits` (STOP, record match), `reminders`, `record`, `crash-test` frame and print, `core` time and clock, the shared yes/no/STOP words. **Not used, and why:** `accounting` has no purchases or bills account, so a purchase bill is Deferred, not a shared-module edit; `report`, `channels`, `unfinished`, `runtime`, `inbox`, `approvals` (the relay is for Guard-held refunds, and nothing here is held by Guard) are Deferred.

**Shared files touched.** `modules/module-map.ts` (a "Stock orders" row so the module tables count it), `modules/README.md` (regenerated by `node modules/module-map.ts --write`), `templates/README.md` (one table row). Nothing else outside this folder.

**What the lead should know about testing.** The tests were written but not run in this stream (one pass at the end). The stream did run the hand check and one smoke script while writing, to find its own bugs; the hand-check result line is not quoted in any doc, so no doc can fall behind it. The shop's `template.json` uses `setup: "stock-orders"` with no row in `bundle/panel/setups.ts` and no row in `bundle/lib/kinds.ts`: the panel lists it and a builder sets it up (templates.ts: "any other template is listed but set up by a builder"). A test that expects every discovered template to have a kinds row, if there is one, will tell the lead.
