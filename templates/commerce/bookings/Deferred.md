# Deferred: what the Bookings template v0 core leaves open

3 November 2026. Each item is left out on purpose, with the reason and what would make it worth doing. Nothing here is claimed as done anywhere else in this folder.

## Real services and the engine

| Left open | Why | Revisit when |
| --- | --- | --- |
| Adapters for a real WhatsApp provider, Razorpay and Google Calendar (superseded: the adapters now exist, see "Live services") | Phase 0 here is local, zero cost, no network. The fakes are shaped like the real services (Razorpay field names and paise, WhatsApp message ids and the 24-hour window, a calendar that can lose or drop a write) so each can be swapped for an adapter without changing the agent | Test-mode accounts exist (the plan's Phase 0 prototype against real test-mode services) |
| Guard enforcing the limits outside the AI | Guard needs its fail-closed production minimum first (W14). The limits are written as pure functions so they can move | Guard passes its fail-closed minimum |
| The engine's crash test: simulated services, injected faults at every step, exact replay, saved checks | Phase 2 work (W1 to W5, W8). The situations here are hand-written stand-ins, and they try only the faults listed | Phase 2 starts; then port the situations as saved checks |
| Webhook signature checks (done in the inbox, see "Live services") | The fake events carry no signature. The inbox verifies Razorpay's and Meta's | Done |
| Message delivery status (sent, delivered, read, failed) | The product says a message counts when WhatsApp reports it delivered. v0 treats "the provider's outbox holds it" as the read-back | A provider with status callbacks |
| Retrying a message whose reply was lost | There is nothing to look it up by (no client reference), and a resend could duplicate a message. It is recorded as `unconfirmed` and not sent again | A provider that accepts a client reference |

## Live services (Phase 0: adapters, inbox, stand-ins, dev forwarder)

3 November 2026. What the live code does is in Explanation.md, "Live services". Nothing below has been run against a real Razorpay, Google or WhatsApp account.

| Left open | Why | Revisit when |
| --- | --- | --- |
| **Any run against real test-mode services** | The adapters were read against the providers' own sample payloads and run against stand-ins that speak the same formats. A real account may differ (the docs disagree with themselves in places, for example `payments: null` against `[]`) | The founder has test-mode keys: run the dev forwarder |
| **Choosing the WhatsApp provider; a provider mapping** | The adapter speaks Meta's Cloud API shape. A provider sandbox with other paths or bodies needs its own small file | Plan B22 picks the provider |
| **`getMessage` reads a local copy, not WhatsApp** | There is no endpoint to read a message back. A live "confirmed" means WhatsApp *accepted* the message, not that it was delivered; after a restart the copy is gone | Status webhooks are handled (below) |
| **Delivery statuses (sent, delivered, read, failed) and failed-send errors that arrive by webhook** | `parseWhatsAppWebhook` ignores `statuses`. The inbox answers 200 and forwards nothing for a statuses-only webhook. The product says a message counts when WhatsApp reports it delivered | A runtime step and a record entry for statuses exist |
| **Templates: fifteen messages have one, the customer's other messages do not** | Meta wants fixed wording; each template carries one message exactly. Customer: booking reminder, confirmed, not confirmed, rescheduled, deposit refund approved, deposit paid twice. Owner: nine, see below. Every other customer message (the menu, the quote, "not available" ...) goes out as a template only if the window is open; outside it the provider refuses and the send is recorded as failed (fail closed). They answer something the customer just wrote, so the window is open; a customer who writes and then waits more than a day for an owner's decision gets only the decision's template | The reminder and confirmation templates are approved; then add the rest |
| **Owner notices: a second way to reach the owner when the template is refused** | Done on 3 Nov: every notice the agent sends the owner on its own has a template (nine, see Explanation.md, "Joining it up", 6), so an owner who has not written today is told. The other options in the design (keep the owner's window open with a daily message from them; one generic "needs your attention, reply to read" template with a queue of what to say next) were rejected for the reasons given there | Before the first live client: an email or SMS to the owner, or the builder's panel, for a notice WhatsApp refused |

| **Calendar race between the agent's look at conflicts and its insert** | Google never refuses an overlapping insert (no 409), so two bookings for one time can both be inserted if they arrive within the same moment. A fixed event id per booking does not help: a deleted event's id stays reserved | A re-check after the insert (release the hold if another event now overlaps), or one step at a time per calendar in the runtime |
| **Calendar details** | Times are written in UTC; an all-day event uses the calendar's zone from the list answer (UTC on a single get); only one calendar; attendees, recurring events written by us and `free` events beyond "blocks nothing" are not handled | A client with several chairs or a shared calendar |
| **Razorpay: a duplicate `reference_id` may leave a booking id stuck** | Razorpay answers "payment link creation with reference ID already attempted" even when the earlier try made no link. The agent then finds no link and retries into the same error | A real account shows whether it happens; then use a fresh reference per attempt |
| **Razorpay: refund edge cases** | A `failed` refund is hidden and a `pending` one counts as made; `expire_by`, partial payments and a payment on a cancelled link are not handled; `fetchPaymentLink` makes one call per payment, which Guard's call cap counts | A real account; Guard's caps are set |
| **Razorpay events beyond three, and secret rotation** | Only payment_link.paid, payment.captured and refund.processed are read (payment_link.expired and cancelled, payment.failed, and refund.failed are answered 200 and dropped). There is no replay window (neither provider signs a time); duplicates are handled by event id in the runtime | More than one number; images and locations if a shop needs them |
| **The inbox in production** | No rate limit and no allow-list of Razorpay's or Meta's addresses (a reverse proxy should), no HTTPS entry in this folder, and no spool: it relies on the provider's retries (Razorpay 24 hours, Meta 7 days). The agent's own reconcile-from-the-record covers a missed payment event while the hold is open | The deploy bundle (B13) |
| **A per-request code for owner approvals when WhatsApp is verified by path-token** (superseded: built, see "Approvals on WhatsApp" in Explanation.md) | The code is made by the approvals relay, is one use, and is the only thing between a leaked callback URL and a forged approval. | **path-token has no end-to-end test through the stand-ins** | The stand-ins deliver only Meta-signed webhooks to `/webhooks/whatsapp`. The inbox's two modes are covered by the inbox tests | The stand-ins get a `--whatsapp-path-token` option |

Everything else (the calendar, WhatsApp, the model, the deposit link in a deployment) has been exercised only against stand-ins, and Guard's own fail-closed minimum (B14) is not run. The fake's `conflicts` fault is not reachable over HTTP (use `list`) | The engine's doubles (B1 to B3) replace them |

## A refund is never more than one deposit (the `refund-at-most-deposit` rule)

4 November 2026. What it does is in Explanation.md, "A refund is never more than one deposit". Run against the real `geo-guard` binary (two integration tests), the Guard model and the stand-ins. Nothing below has run against a real Razorpay account.

| Left open | Why | Revisit when |
| --- | --- | --- |
| **A true cap for each payment**: a refund may not be more than what that payment captured, less what was already refunded | Guard's rule is one fixed number (the deposit in the settings). A per-payment cap needs Guard to know each payment's captured amount and keep a running total of what it has refunded against it, so it is a new stateful rule kind in the engine, not another use of `argument_bound`. It is not built here. The fixed deposit is the right ceiling only because every payment this agent can receive is exactly one deposit, and a second refund of the same payment is already stopped by `refund-once`. Razorpay itself refuses a refund above the captured amount (and the stand-in does the same), so the rule is a second, earlier check on the agent's own side, not the only one | The engine has a per-key running-total rule, or payments of different sizes, or part refunds, are allowed |
| **A lowered deposit refuses the refunds of older, larger deposits** | The owner lowers the deposit (say ₹200 to ₹150). Guard is given the new spec, and its two deposit bounds move together: new links can only be ₹150, and a refund can only be up to ₹150. A booking paid at ₹200 earlier, and not yet refunded, asks for ₹200 back (the deposit on its own record), and Guard refuses it with `refund-at-most-deposit` (HTTP 403, in Guard's words: "amount 20000 is above the highest allowed value, 15000"). The agent reads it like any refusal by a rule: nothing was sent, the booking's entry in the record is `blocked` with that note, the refund is not tried again, the owner is not asked, and the builder sees a `refused` issue (`refunds.needBuilder` in `/status`). The customer was told "We are checking your ₹200 refund" and hears nothing more until the builder refunds it by hand in Razorpay or the booking is settled some other way. This is on purpose: Guard has no way to know that a ₹200 payment was a deposit when it was made. It is tested (Guard model and real binary) | Lower the deposit once the bookings paid at the old one are over, or refund them by hand. The per-payment cap above would remove the problem, because it would not need a number from the settings |
| **The monorepo's shipped Razorpay template does not have the rule yet** | `deploy/pathways/bookings/razorpay/spec.json` in the monorepo lists `deposit-amount`, `refund-needs-owner`, `refund-once` and `no-payouts`, but not `refund-at-most-deposit`. A client whose spec comes from `scripts/guard-spec.ts` (this folder) has it; one who starts from the shipped file does not. That file is the monorepo's, and this change does not touch it. It needs `{ "id": "refund-at-most-deposit", "kind": "argument_bound", "operation": "refund", "field": "amount", "min": "1", "max": <the highest deposit that template allows, in paise>, "units": { "amount": "paise" } }` | The monorepo's template is next changed |
| **The hand check's Guard is a model of this rule too** | "Customer asks for more back than they paid" runs on `guard-model.ts`, which follows the spec and is checked against the real binary in two integration tests. It is not the binary. The go-live certificate's not-tested list says nothing new about it | The engine's crash test runs the real Guard |
| **The new situation is written in one language** | It uses the shop's English (or its first language where it does not speak English). The amount in the message is a number, and the cancel is read the same way in every language, but the Hindi, Malayalam and Kannada sentences would be new machine-written text for a native speaker to review (every sentence the hand check types in Malayalam and Kannada is on the two review sheets, and `says.ts` would need a new line in each) | A reviewer is ready for more lines |

### Running Laya on a shop server (the exact steps, not run here)

Laya is `convaiinnovations/laya` on Hugging Face (Apache-2.0; the multilingual one is about 322M parameters). Run it on the shop server (or any machine with a CPU), not on a laptop with little disk. Needs Python 3.10 or newer.

1. Make a folder and a virtual environment, and install torch for the CPU only (a few hundred MB, no GPU):
   `python3 -m venv laya-env && . laya-env/bin/activate && pip install torch --index-url https://download.pytorch.org/whl/cpu`
2. Install the packages the model card names for `laya-serve`, and download the weights (`huggingface-cli download convaiinnovations/laya`, which needs `pip install huggingface_hub`). **The package name and `laya-serve`'s flags come from the model card, which was not readable from the build machine, so check them there.**
3. Start it on the shop server's own address: `laya-serve --host 127.0.0.1 --port 8080` (the flag names are the part to check on the card). It must listen on `127.0.0.1` so nothing outside the machine can reach it.
4. Check it speaks the System One API (the question and answer shapes are in `modules/understanding/system-one.ts`):
   `curl -s http://127.0.0.1:8080/v1/systemone -H 'content-type: application/json' -d '{"state":"I want a haircut tomorrow","model":"laya","questions":{"intent":{"type":"choice","instructions":"What does the customer want?","criteria":{"book":"wants to book","cancel":"wants to cancel","other":"anything else"}}}}'`
   The answer must hold `answers.intent.choice` and a `probabilities` map that adds up to 1.
5. Point the shop at it, in its `runtime.json`: `"decision": { "provider": "laya", "baseUrl": "http://127.0.0.1:8080", "model": "laya" }`. The `model` is the name the server serves it under.
6. Before Malayalam or Kannada go to it, run the eval on it: put `LAYA_BASE_URL=http://127.0.0.1:8080` in the repo-root `.env` and run `node templates/commerce/bookings/scripts/model-eval.ts --only laya`. The table is per language. If Malayalam and Kannada pass, add `"ml", "kn"` to `decision.languages`; until then those messages go to the language model.

## Under the deploy bundle (added 3 November 2026)

See [bundle/Deferred.md](../../../bundle/Deferred.md) for everything the bundle leaves open. What touches this template:

- **Model calls are counted per server, not per shop.** The model Guard has one cap; this template's record has each action's model cost, and nothing yet stops one shop from using the server's whole cap.
- **The runtime's single `services.timeoutMs`** applies to every service. The bundle needs it above Guard's 15 s for payments; WhatsApp, Calendar and the model are then also given that long. A per-service value would let the model parser keep its 8 s.
- **`steps` does not count clock ticks.** A tick that sends a reminder is work, but is not counted as a step, so a shop that only sends reminders shows no steps. Revisit when: fleet wants a "ticks" count.
- **On a UPI shop the situations written around a Razorpay link do not run.** Thirty-eight are named as not run, with the reason, and nine UPI situations run instead
  (`crash-test/upi.ts`); the calendar faults, the reminders, rescheduling and the AI situations are not repeated with a UPI deposit. Revisit when: a UPI shop goes live
  (make the world's "the customer pays" mean "the owner marks it" so every situation runs either way).
- **A part payment on a UPI booking does not tell the customer.** The owner is asked for the rest; the customer's request still asks for the whole deposit (the hold
  ends, or the owner books by hand). Revisit when: owners ask for a "please send the other ₹50" message.
- **UPI and the browser demo.** The demo runs Glow Salon's Razorpay settings; it has no QR maker (no `node:zlib`) and is not offered a UPI shop. Revisit when: the demo
  shows the UPI option.
